# Decision NN: The operations a start ends are announced

**Each operation a start ends as failed with `daemon-stopped` is announced as any failed operation is, to the notification rules for its failure: a backup as `backup.failed`, a forget, a prune or a check as `forget.failed`, `prune.failed` or `check.failed`. It is announced once, only after the log has its end, so a start that couldn't write the end announces nothing and the next start, which finds nothing left to end, announces nothing again. The news names the time of the start that ended it** (recorded 2026-11-14, §5, §9, §11; amends decisions 40 and 74). From #547.

## Why

Decision 40 ended what a stopped daemon left running "with no hooks and no event": the event bus didn't exist yet. Once notifications did (decision 74), the failures that most need a person's attention, a crash, an out-of-memory kill or a power cut in the middle of a backup, were the ones never told. On a Raspberry Pi, a backup killed by `kill -9` of the daemon was recorded as failed with `daemon-stopped` when systemd started the daemon again ten seconds later, and the plan's `backup.failed` rule stayed silent: from outside, nothing seemed wrong.

## Decided

1. **What is announced.** Every operation a start ends as failed with `daemon-stopped`: the running ones recovery ends (decision 40), and the queued ones the persistent queue can't run again (decision 73: the plan is gone, its repository changed, the configuration can't be read, or the log doesn't keep the job of its kind). Each is the same news as any failed operation's end (`OperationFailed`, code `daemon-stopped`, §4.4), so the rules see the event its kind makes when it fails (decision 74): maintenance operations too, because a check or a prune that died is one that didn't happen, and a rule that names `check.failed` asked to hear of it. An adopt makes no event, as before.
2. **Once, after the write.** `OperationStore::recover` hands back the IDs of the running operations it ended, in the transaction that ended them (`Recovered::ended`), and only then are they announced; a store that refuses the transaction ends nothing and the daemon refuses to start, so nothing is announced, and the next start ends and announces them. A queued operation the queue ends is announced only once `save` took its end; a refused save leaves it queued, said in the daemon's log, for the next start to end and announce. Nothing records that a notification went out: a daemon that stops again between the write and the delivery loses it. That is at most once, not at least once: an outbox would be the second persistent queue decision 74 turned down, for a window of milliseconds.
3. **The time.** When the daemon stopped is unknown, and the log keeps `finished_at` NULL for a running operation recovery ended (decision 40). The news, and so a template's `{time}` and a webhook's `time`, carries the time of the start that ended it, read from the clock when recovery ran. A queued operation the queue ends has that time as its `finished_at` already.
4. **When.** The event bus and the notifier are made before recovery, after the configuration and the log (§9, "Startup recovery"), so the notifier listens when recovery announces; no page is connected then, and a page reads the history when it connects (decision 68). The queued ones are announced when the persistent queue takes them up, once the daemon listens.

Left as they were: recovery still runs no hooks, since they belonged to the process that is gone, and a backup a start ended is not retried: decision 76 retries a run that failed, and the scheduler hears the ends of runs, not of recovery.
