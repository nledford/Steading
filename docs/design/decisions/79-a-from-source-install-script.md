# Decision 79: A from-source install script

**`scripts/install.sh`, run as `curl -fsSL https://raw.githubusercontent.com/nledford/Ladderback/main/scripts/install.sh | bash`, builds the newest release from source and installs it. It installs only what needs no administrator rights, after asking once, and never runs `sudo`** (recorded 2026-11-12, §12). The README's steps stay beside it, as "By hand".

Decided:

1. **From source.** Until M5's release packaging publishes the Linux archives (decision 54), and on macOS until a published archive can be signed with a Developer ID (#344, decision 71), there is no binary to download. The script does what the install guide's steps do: it clones the repository, checks out the newest release and runs `just install`.
2. **What it installs, and what it doesn't.** It checks git, a C compiler (`cc`), Node.js 20 or newer with npm, Rust, just 1.40 or newer and trunk. rustup comes from its official installer, `https://sh.rustup.rs`, with `-y` only when the person passed `--yes`, so rustup asks its own questions otherwise; just and trunk come from `cargo +stable install --locked`, as the install guide says. Before any of that it lists what it will install and how, and asks once, on the terminal (`/dev/tty`: standard input is the script itself); `--yes` skips the question, and with no terminal and no `--yes` it refuses. A missing C compiler, git or Node.js (or one older than 20) it never installs: it prints the command for the system's package manager (`xcode-select --install` and Homebrew on macOS, apt, dnf, pacman, else where to get it) and stops before changing anything. On macOS the C compiler and git count only once `xcode-select -p` finds the Command Line Tools: every Mac has `/usr/bin/cc` and `/usr/bin/git`, which without them only offer to install them. Without rustup, the Rust on the `PATH` must be at least the checked-out release's MSRV and have the `wasm32-unknown-unknown` target, and a missing just or trunk is named with its prebuilt releases, as the install guide says. rustup's folder (`~/.cargo/bin`) goes first on the script's `PATH`, as rustup's installer puts it in new shells, so its cargo is used before one the system's packages installed.
3. **Its own source folder, never deleted.** The source lives in `${XDG_DATA_HOME:-~/.local/share}/ladderback/source`, or where `--dir` says. The first run clones it there, later runs `git fetch --tags`. A folder that holds anything but a clone of Ladderback's repository, or a clone with uncommitted changes, is refused and left as it was. The web UI's build rewrites its stylesheet, `crates/web/tw-out.css`, which releases up to v0.2.0 track: after `just install`, whether it succeeded or not, the script puts back that one file when the release tracks it, so the next run doesn't refuse the clone as changed. Later releases ignore the file (#381), and the script leaves it as the build wrote it.
4. **What it builds.** The newest `v*` tag that isn't a release candidate (no `-`), the selection the install guide's `git checkout` line makes; no such tag is an error. With rustup, it builds with the Rust the checkout's `rust-toolchain.toml` pins (decision 78), whatever the person's environment names: `RUSTUP_TOOLCHAIN` outranks the file, and `RUSTC` or `CARGO_BUILD_RUSTC` has cargo run another compiler, so the script unsets them before it builds the release, for the rest of its own run, which leaves the person's shell as it was, and says which it ignored. It installs the pinned version, with the components and targets the file lists, when rustup lacks it (`rustup toolchain install <version> --no-self-update`, naming the version, which works on every rustup that reads the file), rather than relying on rustup's automatic install, which rustup has deprecated (rust-lang/rustup#4836); a release that names no version there is refused. Without rustup it checks the Rust on the `PATH` against the MSRV instead (item 2). On 64-bit ARM Linux with a glibc older than 2.38 it builds the wasm-bindgen the checkout pins first, in the checkout so that the pinned Rust builds it, the install guide's workaround. Then `just install`, with the arguments after `--`; every release from v0.2.0 on has that recipe, and the script builds only the newest. It ends with the installed binary's `--version` and the next steps: `ladderback serve`, `ladderback install-service`, and on macOS the Full Disk Access grant. When the `PATH` the script was started with doesn't lead to the binary, it says to open a new terminal (after installing rustup) or which folder to put on the `PATH`. Running it again updates.
5. **`main`'s script.** The command fetches the script from `main`. The script pins no version itself: it builds the newest release tag, so what gets installed is a release, while fixes to the script reach everyone at once. `main` is protected (§13.8): the script that runs has passed review and CI.
6. **A partial download runs nothing.** The script is a set of functions and its last line calls `main`, so a download cut short defines functions and runs none. Nothing it runs reads its standard input, which is the rest of the script when it is piped into bash.
7. **Tested as `@e2e` scenarios.** `features/cli/install_script.feature`, with steps in `tests/steps/install_script.rs`, runs the script as `curl … | bash` does, bash reading it from standard input, with stand-ins for every tool on the `PATH` that record their calls, a scratch home, and the real git cloning a local repository with releases of the scenario's choosing (the scratch home's git configuration rewrites Ladderback's address to it). Nothing is downloaded or built, and `LADDERBACK_INSTALL_TTY` points the question at a file or at nothing, so no real terminal is asked. They run on Linux and on macOS, whose bash is 3.2. shellcheck isn't a CI check; run it by hand when the script changes.

Why:

- **One command is what people expect** of a self-hosted tool, and the install guide's steps are six tools and a `git checkout` line to copy exactly. The script runs those same steps, so the two can't disagree about what gets installed.
- **No `sudo`.** A script piped from the web that asks for root asks for the most trust there is, and system packages differ in name and version from one distribution to the next (Debian 12's Node.js is 18). rustup, just and trunk install into the person's home; the rest is one command the person runs knowingly, and the script names it exactly.
- **Ask once, or not at all.** Installing rustup and building just and trunk change the person's home and take minutes, so the script says what it will do before doing it. Under a pipe with no terminal it can't ask, and guessing yes would install what nobody agreed to.
- **Never delete a folder.** `--dir` may point at a folder that holds the person's own work; refusing costs a rerun, deleting can't be undone.
- **The pinned Rust, whatever the shell says.** A version manager can export `RUSTUP_TOOLCHAIN` into every shell, and it outranks `rust-toolchain.toml`: the first real run on Fedora built with the 1.99.1 a version manager named, and stopped with cargo's "rustc 1.99.1 is not supported" rather than anything the script said. The release is tested with the version it pins, so the script builds with that one rather than refuse; it names what it ignored, so nobody wonders why their setting had no effect. Installing that version explicitly keeps the script working when rustup stops installing a missing toolchain on its own.
- **Scenarios, not `node:test` or a shell test framework,** because the red-first check (§13.1) and `just test` run only Rust tests and the scenarios in `features/`: tests they can't see would leave a `behaviour` change with no red-first proof and no CI run. A shell test framework would also be a new dependency.

Alternatives:

- **cargo-dist's shell installer**, which downloads a release archive and checks its SHA-256. There is no archive to download before M5. **At M5**, Linux could switch to it, a smaller download and no build, with this script left for macOS until #344 and for building from source; that is M5's decision.
- **`cargo install --git`**: it can't build the web UI the binary embeds (the `Justfile`'s `install` recipe), so it would install a binary with no UI.
- **A script that installs the system packages too, with `sudo`**, as some installers do: one command fewer for a person on a supported distribution, but root for a script from the web, and a table of package names to keep right for every distribution.
- **A URL pinned to a release tag**: the script would match the release, but the README would change at every release and a fix to the script would reach no one until the next.
- **Refusing when the environment names another Rust,** with the script's own message, as the Rust check without rustup does: clearer than cargo's error, but it stops an install that can succeed, and the person would have to unset a variable their version manager sets in every shell.

Cost: the script is a second way in beside the install guide's steps, and both change when the build's tools do. The scenarios replace the tools with stand-ins, so a change in what a real tool prints (`node --version`, `just --version`) shows only when someone runs the script for real. The script itself is not checksum-verified: the person trusts `main` over HTTPS, or downloads it and reads it first, as the README shows.
