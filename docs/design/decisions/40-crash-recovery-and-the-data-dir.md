# Decision 40: Crash recovery and the data-dir lock

**A start ends what the log still shows as queued or running as failed (`daemon-stopped`), and `serve` takes the data-dir lock before it reads the configuration or opens the log** (recorded 2026-11-10, §9; #43, #119). A crash left a `running` row behind for good, and a running maintenance row held its repository's I7 slot with it. Decided: (1) recovery runs once per start, before the listener binds, in one statement, and fails every `queued` and `running` operation with the typed reason `daemon-stopped`: never succeeded, never resumed, with no hooks and no event, and `finished_at` left NULL as migration 0002 left it; (2) it is only safe under the lock, so the lock was built first: a second `serve` on a data dir is refused with the holder's PID, as a command-line message rather than an API code, because no request can reach a process that never listened; `mcp --headless` and `db rebuild` take it when they exist; (3) a log that can't be changed refuses the start. Why: marking a crashed run succeeded or cancelled would be a lie, resuming a queued one needs M2's persistent queue, and recovering without the lock would let a second daemon end the first one's live operations. Cost: recovery ends rows, not processes, so a worker the dead daemon left behind can write for a moment more (§9).

**Amended by decision 73** (2026-11-12, #274): recovery no longer ends the *queued* operations. It ends the running ones as before and leaves the queued ones to the persistent queue, which runs a queued backup again once the daemon listens and ends any other queued operation `daemon-stopped` then.

**Amended by decision 91** (2026-11-14, #547): recovery now sends an event. It announces each operation it ends once the log has its end, as any failed operation is announced, with the time of the start that ended it, and the persistent queue does the same for a queued operation it ends; `finished_at` still stays NULL, and recovery still runs no hooks.
