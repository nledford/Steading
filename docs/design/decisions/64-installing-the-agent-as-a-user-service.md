# Decision 64: Installing the agent as a user service

**`ladderback install-service` writes a service file for the user's own service manager, a systemd user unit on Linux or a launchd agent on macOS, that runs this program's `serve`, and has the manager start it; `ladderback remove-service` has the manager stop it and removes the file** (recorded 2026-11-11, §12; #278). Both run the manager's own program, `systemctl --user` or `launchctl`, behind `app`'s `ServiceManager` port; the adapter is `platform::service::UserService`.

What is written:

- **Linux:** `$XDG_CONFIG_HOME/systemd/user/ladderback.service` (`~/.config` when the variable is unset, empty or relative), with `Type=exec`, `ExecStart=:"<program>" serve`, `CacheDirectory=ladderback` and `CacheDirectoryMode=0700`, `Environment=LADDERBACK_CACHE_DIR=%C/ladderback` (decision 59), `KillMode=mixed`, `Restart=on-failure`, `RestartSec=10` and `WantedBy=default.target`. Its first line is the mark, a comment saying `install-service` wrote it. The calls are `daemon-reload`, `enable <file>` and `restart ladderback.service`; removal is `disable --now`, the file's removal, then `daemon-reload`.
- **macOS:** `~/Library/LaunchAgents/io.github.nledford.ladderback.plist`, with `ProgramArguments` `<program> serve`, `RunAtLoad`, `KeepAlive` `SuccessfulExit=false`, and the log in `StandardErrorPath`, `~/Library/Logs/ladderback.log`. Its third line, after the XML declaration and the doctype, is the mark, as an XML comment. The calls are in the `gui/<uid>` domain: `print` to learn whether the agent is loaded, `bootout` if it is and `print` until launchd has let it go, then `enable` and `bootstrap`; removal is `print`, `bootout` if loaded and `print` until it is gone, then the file's removal.

Why:

- **The user's manager, not the system's, and never as root.** A user service runs as the user, reads the user's configuration and keyring session (where there is one, §12), and needs no `sudo`. Run as root (an effective user ID of 0, as under `sudo`), both commands refuse (`cli-service-as-root`) and touch nothing: the file would be root's, under root's home or a `HOME` that `sudo` kept, and on macOS the agent would go in root's `gui/0` domain, not the user's. A `--system` unit for a server with no login is left for later; the command takes no scope flag until it has two.
- **The program's own path, absolute, as text, by the name the person ran.** The path is parsed into a `ServicePath` (absolute, Unicode, no `..`, no control character, no quote or backslash), so the manager runs the binary that installed it, and no character of the path can end a line and start a setting of its own. A package manager installs the binary in a folder of its version and puts a link to it on the `PATH` (Homebrew's `/opt/homebrew/bin/ladderback` → `../Cellar/ladderback/<version>/bin/ladderback`, Linuxbrew's and Nix's alike), and an upgrade removes the old folder and points the link at the new one. Linux gives `std::env::current_exe()` with its links resolved, so naming it would break the service at the next upgrade. So the file names the path the person ran (the first argument) when it is the same file as `current_exe()` once both are resolved and a `ServicePath` accepts it: the argument itself when it is absolute, or, when it is a bare name, the first folder of `PATH` holding it, as the shell found it. Otherwise (a relative path such as `./ladderback`, a name that leads to another file, or a first argument a launcher or `exec -a` set) it is `current_exe()` as the system gives it, when a `ServicePath` accepts it: macOS gives the path the program was started by, links and all, so the link is still named. Failing that, it is `current_exe()` with its links, `.` and `..` resolved (`platform::service::program_path`). An upgrade in place, or one that moves the link, keeps the service running; a binary moved elsewhere needs `install-service` again.
- **Quoted by each file's rules.** In the unit, `ExecStart=` holds the path in double quotes with `%` doubled (a specifier), and `serve` as its own word: a path can't add a word, a command or a setting. The `:` prefix (systemd 243 and later; every supported Fedora, Debian 12 and Ubuntu 22.04 ship newer) keeps systemd from expanding a `$` in the command line; systemd never expands one in the program's path, so doubling it, as an argument would need, named another file. systemd refuses a quote or a backslash in the path of the program it runs, so `ServicePath` refuses them (`cli-service-program-quote`), as it refuses a `HOME` that has one; it keeps the path with `.` and doubled separators dropped, as systemd wants it. In the plist, `&`, `<` and `>` are escaped; `ProgramArguments` is an argv, so no shell reads it.
- **Nothing of the environment goes into the file**, so no secret can (I4): the service reads its secrets from their sources when it runs, as `serve` always does. `LADDERBACK_CONFIG_DIR`, `LADDERBACK_DATA_DIR` and `LADDERBACK_CACHE_DIR` of the installing shell are not carried over either: the service uses the platform's folders (the unit's cache folder aside). A user who sets them edits the file.
- **The manager is run by name, from the `PATH`, with argv only and an environment of its own.** Only `PATH`, `HOME`, `XDG_RUNTIME_DIR`, `DBUS_SESSION_BUS_ADDRESS`, `LANG`, `LANGUAGE`, `LC_ALL` and `LC_MESSAGES` reach it: what it needs to find the user's manager and to speak the user's language. stdin and stdout are closed; up to 4 KiB of its stderr is kept for a refusal, and the rest is read and dropped so it never blocks. It starts through the spawn gate (decision 58), and a call that has not ended after 30 s is killed and said as such (`systemctl` waits 25 s for the manager itself). A call whose end the system can't report is a refusal, in the system's words.
- **Written beside the file, then renamed over it.** The new file, `.<file name>.tmp`, is made 0600 and set to 0644 whatever the umask once it is written, in a folder made 0700 when it is missing: the manager never reads half a file, and nobody but the user can change what the service runs. A write or a rename that fails removes the new file; a removal of the service removes one an install stopped part way left.
- **Only a file `install-service` wrote is replaced or removed.** Both commands read what is at the service file's place without following a link, and go on only when it is a file whose mark line is where the template puts it (in the first 4 KiB, as a whole line). A unit or an agent the user wrote under the same name, or `systemctl --user mask`'s link to `/dev/null`, is left as it is, the manager is asked nothing, and the command says so (`cli-service-not-ours`) and ends with 1.
- **Installing over an installed service replaces it.** systemd's `restart` and launchd's `bootout` before `bootstrap` both start the new file's program; the command says the service was replaced.
- **launchd is waited for until it has let the old agent go.** `launchctl bootout` returns once launchd has sent the agent's program SIGTERM (in 0.03 to 0.04 s, measured on macOS 27.3), not once the program has ended, and launchd keeps the label until it has: a `bootstrap` of it meanwhile fails with `Bootstrap failed: 5: Input/output error` and leaves no agent loaded, so backups stopped until someone installed the service again (#542). After a `bootout`, install and removal ask `print` every 100 ms until launchd no longer knows the label, for 30 s at most (`STOP_LIMIT`): launchd sends SIGKILL after the plist's `ExitTimeOut`, which ours doesn't set, 20 s by default, so a label still there after 30 s is one launchd isn't letting go. Then neither goes on: the service file stays as it was, no `bootstrap` is tried, and the command says what it waited for and to run it again once the old service has stopped (`cli-service-still-stopping`). Run again while launchd still has the label, the command finds it loaded and sends a second `bootout`, which launchd answers with 0, as it did the first (measured on macOS 27.3), so the rerun waits the same way. systemd needs no wait: `restart` and `disable --now` return once the unit has stopped.
- **A removal deletes the file only once the manager has let the service go.** A `systemctl disable --now` that fails, or a `launchctl print` that neither succeeds nor says the agent is unknown (exit 113, or 3 on older releases), is an error, and the file stays: a manager that can't answer never leaves a running service with no file to remove it by. Removing a service that isn't installed asks the manager nothing.
- **On Linux the command says how to keep it running after logout**, `loginctl enable-linger`, rather than doing it: whether a user's services outlive their sessions is the user's or the administrator's choice.
- **The macOS log is not rotated.** launchd appends to `StandardErrorPath` and never trims it. Rotation (`newsyslog`) is left for later.
- **The command's `--help` is the catalog's** (`cli-help-install-service`, `cli-help-remove-service`), read only when help is said, so no start of the daemon or a worker reads the catalog for it. Moving the other commands' help to the catalog is #299.

Tests run against stand-ins for `systemctl` and `launchctl` (`testkit::service_manager`) on a scratch `PATH` and home, never the real manager; the `launchctl` stand-in can keep an agent it booted out for a few calls of `print`, as launchd does while the program stops. The contract against the real manager runs only with `LADDERBACK_TEST_REAL_SERVICE_MANAGER` set, since it starts a service in the session of whoever runs it, and CI sets it on macOS and Linux (§13.8); its program takes about 2 s to end on SIGTERM, as the daemon takes a while to shut down, so an install or a removal that didn't wait for launchd fails it.
