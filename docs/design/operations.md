## 11. Notifications

Configured on the hub (or on a standalone agent). Each **notification rule** is **events → channel**:

- Events: `backup.started`, `backup.succeeded`, `backup.failed`, `backup.warning`, `backup.missed` (no success within N × interval), `backup.retrying`, `forget.failed`, `prune.failed`, `prune.refused` (`keep-delete` too small for the margin, §7.3), `check.failed`, `check.errors`, `agent.offline` (> N min), `repo.unmanaged_groups`, `repo.claim_rejected`, `repo.maintenance_paused` (lease not renewed, repo now shared, or not configured on the hub).
- **As built.** The agent emits `backup.retrying` when it plans a retry of a failed backup (§5): the operation that failed, its plan, which attempt of how many, and when it runs (`UiEvent::BackupRetrying`, decision 76). `backup.missed` isn't emitted yet.
- Channels: generic webhook (JSON), ntfy, Gotify, Discord/Slack webhook, SMTP.
- **Templates.** Default message text comes from the `notify.ftl` catalog in the configured locale (§8.4). Users may override it with their own templates, which are not localized. Webhook bodies are JSON with stable, unlocalized keys, event names and error codes, plus a localized `message` field. Templates never receive secrets (I4).
- **healthchecks.io-style pings per plan**: `start`, `success` and `fail` URLs. These are the most robust "it silently stopped" detector, because they work even when the whole Ladderback system is down.

**As built (M2, decision 74).** An agent sends the events it emits today: `backup.started`, `backup.succeeded`, `backup.warning` (a backup that succeeded with warnings, told instead of `backup.succeeded`), `backup.failed`, `backup.retrying` (a retry planned after a failed backup, with the failure's code, decision 76), `forget.failed`, `prune.failed` and `check.failed`. The others arrive with the parts of the agent that emit them (the scheduler, the hub). Channels are `webhook`, `ntfy` and `healthchecks`; Gotify, Discord/Slack and SMTP are not built.

```toml
[notifications.channels.ops]
kind = "ntfy"
url-env = "NTFY_TOPIC_URL"            # https://ntfy.example.com/backups
token-file = "/run/secrets/ntfy_token"

[notifications.channels.home-check]
kind = "healthchecks"
url-keyring = "ladderback/home-check"  # the check's ping URL

[notifications.rules.failures]
events = ["backup.failed", "prune.failed"]
channel = "ops"
template = "{event}: {plan} {repository} ({code})"

[notifications.rules.home-pings]
events = ["backup.started", "backup.succeeded", "backup.failed"]
channel = "home-check"
plans = ["home"]
```

- **A channel's URL is a secret**, as its token and password are: whoever knows a webhook's or a topic's URL can post to it. Each is given by exactly one of `-command`, `-keyring`, `-file` and `-env` (`url-…`, `token-…`, `password-…`), with the rules a repository's password follows (§10.2): a file by an absolute path, a command whose program is a name on `PATH` or an absolute path. Never as text in the file: `url`, `token` and `password` are not keys. Each is read when a notification is sent, never kept. `webhook` and `ntfy` may sign in with a bearer token (`token-…`) or with `username` and a password by HTTP Basic; `healthchecks` signs in with nothing and takes none of those keys.
- **A rule** names its `events`, its `channel` and, optionally, its `plans` (only those plans' events; an event without a plan, as a prune's, is sent only by a rule that names none) and a `template`. The configuration is refused when a rule names a channel or a plan it doesn't have. Rules are matched in name order, and each one an event matches sends it once.
- **A template** is text with the placeholders `{event}`, `{plan}`, `{repository}`, `{operation}`, `{code}` (the failure's code, as `operation-failed`), `{time}`, and a retry's `{attempt}` and `{attempts}` (which retry of how many; `{time}` is when it runs); `{{` and `}}` write a brace. A fact the event doesn't have is empty. It reads only these facts, so no secret, location or engine text can reach a message (I4). Without one, the message is the catalog's `notify-<event>` in the agent's locale (`[agent] locale`), or the system's when the agent names none or its locale has no catalog.
- **What is sent.** A webhook is posted JSON: `event`, `plan`, `repository`, `operation`, `code`, `time`, `attempt`, `attempts` (`null` when the event lacks it) and `message`. An ntfy topic is posted the message, titled with the event's name. A healthchecks check is pinged at its URL for a success, at `/start` of it when a backup starts and at `/fail` of it for a failure and for a retry planned after one. A message is cut to 4 KiB, and a URL longer than 8 KiB, or not `http` or `https` with a host, is not sent to.
- **Delivery.** Each request ends within 30 s, after the channel's secrets are read (a secret's command has 60 s of its own); only a 2xx answer delivers it, a redirect is never followed (so a channel can't move a notification and its credentials elsewhere), and the answer's body is never read. A notification that isn't delivered is not tried again: the daemon logs `notification-undelivered` with the rule, the channel, the event and why (`secret-unavailable`, `invalid-address`, `unreachable`, `timed-out` or `rejected`), never the URL, the token or the library's text. An event that comes while the configuration can't be read is logged once, with the configuration's error, and sent nowhere. The notifier reads the configuration for each event, so a rule saved while the daemon runs applies to the next event, and it is subscribed to the events before any operation runs. It takes the starts and ends, and the retries planned, off the event bus as they come, while a slow channel is still being told, and tells them in the order they came: a subscriber's queue on the bus loses its oldest events once it is full (§4.4), and a run that warns often would otherwise push another run's end out of it. An operation the daemon finds cut short when it starts is ended as failed before the notifier subscribes, and is not told.
- **Proxies.** Deliveries go through the proxy the standard variables name (`HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, in either case), as a worker's requests do (§4.1), read once when the daemon starts. A channel on loopback or the local network is sent through the proxy too, unless `NO_PROXY` names its host (`NO_PROXY=127.0.0.1,ntfy.example.com`). The macOS system proxy settings are not read.

## 12. Packaging and deployment

- **Linux:** an `x86_64`/`aarch64` binary that needs glibc 2.35 or newer (Debian 12, Ubuntu 22.04 and later) and no library outside glibc and `libgcc_s`: TLS is rustls and D-Bus is built in (decision 54). `ladderback install-service` writes a systemd **user** unit, `$XDG_CONFIG_HOME/systemd/user/ladderback.service` (`XDG_CONFIG_HOME` is `~/.config` when unset), that runs the installing binary's `serve`, and has the user's manager enable and start it; `ladderback remove-service` stops and disables it and removes the file (decision 64). Both are run as the user the service is for, never under `sudo`, and neither touches a unit of the same name it didn't write, nor a masked one. A system unit for servers (`--system`) is not built yet.
  - On **Bazzite and other atomic Fedora** systems, put it in `~/.local/bin` (or `/usr/local/bin`, which is writable) with a user unit. No layering needed.
  - **A user's services stop when the user's last session ends**, unless the user lingers: `install-service` says to run `loginctl enable-linger` for a service that starts at boot and keeps running while the user is logged out.
  - **SELinux (Fedora, enforcing), not tested on Fedora:** under the targeted policy a user's services run in the user's own unconfined domain, as the user's shell does, so a user unit that runs a binary in `~/.local/bin` or `/usr/local/bin` should need no policy change, and the unit's `CacheDirectory=` is a folder systemd makes and labels. A confined SELinux user (`user_u`, `staff_u`) is not tested either. **firewalld:** the agent listens on loopback by default, which needs no rule.
  - **Keyring under a service:** a user unit shares the session's bus only while the user is logged in to a desktop session; a lingering service at boot, or on a server, has no Secret Service, and a `password-keyring` read says so (the next item).
  - **The `keyring` secret source needs a Secret Service** (#259). On Linux a `password-keyring` entry is read from the Secret Service over the session's D-Bus. A headless machine has none by default: Fedora Server, Debian and Ubuntu servers, and a systemd **system** unit, which has no session bus at all. There every read is refused as `secret-keyring-unavailable`, which says what is missing and what to use instead, with the platform's words as its detail. So is a read the service answers by saying its keyring is locked, or whose unlock prompt was dismissed, and one that finds no entry while the `default` collection is locked (oo7, Fedora's Secret Service, finds no items in a locked collection); a locked keyring whose prompt nobody answers holds the read until the resolver's time runs out, and that is `secret-unreadable`. Either run a Secret Service (GNOME Keyring) in a session bus and unlock it, or keep the secret in a `password-file` (with a system unit, `LoadCredential=`), a `password-command` or a `password-env` instead (§10.2).
  - **An exported profile reads a keyring password with `secret-tool`** (§6.2), which ships apart from the Secret Service: in `libsecret` on Fedora (a Server or Minimal image may lack it) and in `libsecret-tools` on Debian and Ubuntu. `export-profile` warns (`profile-keyring-command-missing`, naming the package) when no folder of its `PATH` holds the command, and still writes the profile, which may run on another machine. With `PATH` unset it looks in `/usr/bin` and `/bin`, as `execvp` does, and it skips an empty or relative entry, which names a folder by the one rustic will run in.
- **macOS:** an `aarch64` binary until cargo-dist can build a universal one (axodotdev/cargo-dist#77; decision 54), with `install-service` writing a launchd agent, `~/Library/LaunchAgents/io.github.nledford.ladderback.plist`, that logs to `~/Library/Logs/ladderback.log` (decision 64). Without a Developer ID, a build from source carries the linker's ad-hoc signature, or a self-signed certificate's when the person names one; a published archive needs Developer ID signing and notarization first (decision 71). The worker needs **Full Disk Access** (TCC) to read `~/Documents`, `~/Desktop`, Mail and so on.
  - TCC ties the grant to the code signature, so an ad-hoc-signed build loses it on every upgrade. A signature that stays the same across upgrades is required, not polish (decision 71).
  - Some macOS versions refuse to add a bare CLI binary to Full Disk Access ([Backrest #986](https://github.com/garethgeorge/backrest/issues/986)); M3 tests this on the current release and documents the workaround.
  - The UI detects permission errors in warnings and links to System Settings → Privacy & Security.
- **Docker:** an image for hub deployments on servers or a NAS.
- **Until binaries are published** (decisions 54 and 71), Linux and macOS build from source: the steps in the [install guide](../guide/install.md), or `scripts/install.sh`, which runs them in one command piped into bash, `curl -fsSL https://raw.githubusercontent.com/nledford/Ladderback/main/scripts/install.sh | bash` (decision 79). It installs rustup, just and trunk after asking once, never a system package and never with `sudo`, keeps the source in `${XDG_DATA_HOME:-~/.local/share}/ladderback/source`, and builds the newest release tag that isn't a release candidate with `just install`; running it again updates. At M5, Linux could move to cargo-dist's installer, which checks the archive's checksum.
- Distribution: GitHub Releases (cargo-dist), a Homebrew tap, and possibly the AUR later.

### 12.1 Versioning and releases

Ladderback follows [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html). The **release unit is the product**: the `ladderback` binary, and from M5 its Docker image. Every crate inherits one version from `[workspace.package]` and none is published, so crate APIs are not a public contract.

**The public contract**, which decides the bump:

| Surface | Breaking (major from 1.0) | Compatible (minor) |
|---|---|---|
| CLI: commands, flags, exit codes | Removing or renaming one, changing a default's meaning | New command or flag |
| CLI `--json` documents (§4.5): keys, error and warning codes | Removing or renaming one | New keys or codes |
| `config.toml` (§6.1) | Dropping the migration from an old `schema`, so a file stops loading | New keys; a new `schema` whose migration runs on load |
| REST and WebSocket API `/api/v1` | Anything that needs `/api/v2` | New endpoints and optional fields |
| Sync protocol `/sync/v1` (§7.2, decision 88) | Dropping a protocol the previous release spoke (a release adding protocol N+1 drops N−1) | New optional message fields; a new protocol in a release that still speaks every protocol the previous one did |
| Snapshot tags `ladderback-plan:` / `ladderback-agent:` (§7.3) | Any change: existing repositories would lose their plan links | — |
| Webhook JSON: keys, event names, error codes (§11) | Removing or renaming one | New events, keys or codes |
| Exported rustic profiles (§6.2) | A profile that the pinned rustic CLI reads differently | — |
| Database and data directory (§9) | A migration with no automatic path | Automatic migrations |
| MCP tools (§4.6): names, input schemas, result fields | Removing or renaming a tool, a new required argument, a result field whose meaning changes | New tools, optional arguments and result fields |

Not part of the contract: UI layout and wording, log text, the CLI's sentences (a script reads `--json`; the daemon's `listening on` line stays as §8.4 says), the worker protocol (both ends ship in one binary), and Rust APIs. Downgrades are unsupported; the config history and the daily database copy are the way back.

**Bump rules.** A release takes the highest bump among its changes, judged by the table, not by commit labels:

- before 1.0.0: a breaking change or a feature bumps the minor version, a fix bumps the patch;
- from 1.0.0: breaking bumps the major, a feature the minor, a fix the patch;
- every breaking change gets an entry under **Breaking** in `CHANGELOG.md`, with the upgrade step.

**Release line.** Nothing is released before M1b; the workspace version stays `0.0.0` until then. The end of M1b releases `0.1.0`, and each later milestone a minor version. `1.0.0` follows M5, once the contract above is declared stable. Release candidates (`X.Y.Z-rc.N`) are tagged before a release that bumps the config `schema` or the sync `protocol`, and run on real machines first. The first release, release candidates and `1.0.0` are versions the commits can't imply, so the maintainer sets them on the release PR's branch with `release-plz set-version <version>`, which moves `[workspace.package] version`. The `ladderback@<version>` form would give that one package its own version and break the inheritance every crate shares.

**Tags.** `vX.Y.Z` on `main`, created only by the release workflow. A tag is never moved or deleted; a bad release is fixed by the next patch, and its GitHub release is marked as such. The "Protect release tags" ruleset enforces this for every `v*` tag, with no bypass: creating one stays open to the release workflow's `GITHUB_TOKEN`, and undoing a mistake means switching the ruleset off on purpose.

**Process.** [release-plz](https://release-plz.dev) in git-only mode (`release-plz.toml`, `.github/workflows/release.yml`):

1. Before `just release-pr`, a docs PR brings `README.md` up to date with what the release can do: the warning, the Backrest comparison and the roadmap, whose milestone is checked and linked to the coming tag. It merges first, so the tag includes it.
2. Running the Release workflow by hand opens or updates a draft **release PR**. It bumps `[workspace.package] version` from the Conventional Commits since the last tag (`feat` → minor; `fix` → patch; `!` or a `BREAKING CHANGE:` footer → breaking) and writes the `CHANGELOG.md` entry. `just release-preview` shows the same result locally, changing nothing. The workflow opens the PR with `RELEASE_PLZ_TOKEN`, a fine-grained token (contents and pull requests: write), because a pull request opened with the workflow's own `GITHUB_TOKEN` starts no CI; without the token the PR still opens, but with no checks. The token is a secret of the `release` environment, whose only deployment branch is `main`, and only the job that opens the PR names that environment, so a workflow edited on another branch can't read it.
3. The maintainer checks the bump against the contract table, since labels only navigate, and edits the notes. `just release-pr [version]` does steps 2 and 3: it runs the workflow, waits for the PR, sets the version if given, opens `CHANGELOG.md` in `$EDITOR`, then pushes to the PR's branch and retitles the PR. A later run of the workflow, the recipe's included, closes a release PR that carries such a commit and opens a new one from the commits alone, so a rerun needs the same version again and the notes redone.
4. Merging the PR to `main` triggers the tag and a GitHub release with that entry as its notes.

Until M5's release packaging, a release is source only. M5 adds the hosting: the cargo-dist archives attached to the same tag and the Docker image; a macOS archive only once it can be signed and notarized (decision 71).

**Release builds.** The archives are built, and not published, from M2 on (§16, decision 54). `just release-build <target>` builds the web UI with `release_flags` and then runs cargo-dist's `dist build` (`dist-workspace.toml`; `scripts/install-dist.sh` installs the pinned dist) for one target: `x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu` or `aarch64-apple-darwin`. The archive, its SHA-256 and dist's manifest land in `target/distrib`, dist's own folder, whatever `CARGO_TARGET_DIR` says. `just smoke-release <binary>` checks the binary (`scripts/smoke-release.ts`): the build its `--version` names, which must be the checkout's (decision 90) unless the script's own `--version <x.y.z>` names another; no pseudolocales in the binary, asked for or looked for, and neither pseudolocales nor the gallery in the wasm it serves; its dynamic libraries, which must be the base system's; on Linux its glibc floor, at most 2.35; then `serve` in scratch folders answering with the UI, a scratch repository initialised and one backup that leaves one snapshot. With `--container` it runs those in clean Debian 12, Ubuntu 22.04, Ubuntu 24.04 and Fedora containers (Docker, no network, images pinned by digest). The `Release builds` workflow (`.github/workflows/release-builds.yml`) runs both for each target every night, by hand, and on pull requests labelled `release`; the Linux builds run on Ubuntu 22.04, so the binary needs no newer glibc than 2.35 and runs on Debian 12 and Ubuntu 22.04. Each archive is a run artifact for 7 days, and a failed nightly run opens an issue. It is not a required check.

**Release build flags.** A release is built with `--no-default-features`, which leaves out the development pseudolocales (§8.4); the component gallery (§4.5) is off unless asked for, so the same build has none. The flags are one definition, `release_flags` in the `Justfile`, and `just --evaluate release_flags` prints them. `just architecture` checks a build made with them: no `fluent-pseudo`, no gallery. The release builds use them: `just web-release` passes them to `trunk build --release`, and cargo-dist, which can't read the `Justfile`, has the same in `dist-workspace.toml`, which `just architecture` checks against `release_flags`. `just install`, the install guide's way to install from a checkout and the one `scripts/install.sh` runs (decision 79), builds `web-release` and passes them to `cargo install --path . --profile dist`, so the installed binary is built as the archives are, with the `dist` profile (thin LTO). The development recipes (`just web`, `just build`) don't use the flags. The Docker image M5 adds must, so the check and the artifact can't drift apart. A feature a release needs is added to `release_flags` and `dist-workspace.toml`, not to a workflow.
