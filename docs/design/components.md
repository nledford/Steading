## 4. Components

### 4.1 Worker process (the engine boundary)

Each operation (backup, forget, prune, check, restore, ls, dump, stats) runs in a **child process**:

```
daemon ──stdin: JobSpec (JSON)──► ladderback worker
daemon ◄─stdout: NDJSON Event stream── (progress, log, warning, result)
daemon ──SIGTERM → (grace) → SIGKILL──► cancel
```

Why a subprocess instead of `spawn_blocking`:

1. **Cancellation.** `rustic_core` has none, but a process can be killed. The worker installs a SIGTERM handler that stops emitting events and exits; without it the grace period would be meaningless. A backup that is archiving winds down instead (decision 50): its source (`CancellableSource`) lists, opens and reads nothing more, so rustic ends the backup its own way, writing its last packs and saving the index of every pack the worker wrote, and the backend that takes a snapshot first (`refusing_snapshots_once_cancelled`: the hot half when there is one, rustic writes the cold half only after it) refuses the snapshot that comes next. A snapshot write that had begun before the cancel finishes, in both halves, and the snapshot stays. The worker then exits with 143 and writes no more events, so the operation ends `Cancelled`. A backup past its deadline winds down the same way (item 4). The daemon's SIGTERM reaches the worker alone, so the `rclone` or `ssh` its backend saves through runs on during the wind-down; a SIGTERM sent to the whole group from outside ends them too, and then the index may not be saved. A file the cancel cut mid-read is left out; the blobs it had chunked, like the trees of the partial backup, are indexed but no snapshot uses them, which a check doesn't warn about and a prune removes while their packs are unused, or repacks past its unused limit once a later backup reuses some of their data. The wind-down lasts until the daemon's SIGKILL at the end of its grace period, or 30 s when the daemon is gone. Killing is safe for data:
   - A backup killed before it saved its index (a SIGKILL, a crash, a wind-down past the grace period) leaves packs no index lists and no snapshot: a check warns about each, and the next prune cleans them up. On the local backend it also leaves `*-tmp-*` files, which nothing in rustic removes. Once a job has opened a repository, the worker deletes the ones older than 24 h from each half that is a local folder (the cold half, and the hot half of a hot/cold repository), but only where the backend writes them: `config-tmp-…` in the half's root and `<id>-tmp-…` in `keys`, `snapshots`, `index` and `data/<xx>`. A job that fails to open its repository (a mistyped path, a wrong password, a missing hot half) deletes nothing.
   - Prune writes new packs and index files, then deletes the old index files, then the packs. A kill at any point leaves extra data or duplicate index entries, not missing data; the next prune deduplicates and finishes the job. This only holds without `early-delete-index` (I2).
   - M1a proves this with a kill test against a scratch repo, for the local backend and for OpenDAL's `fs` service. It kills real workers right after a chosen progress event, of a backup and of a prune that has packs to repack, spreading the kills over the events of an uninterrupted run, and then checks that the repository is sound and still takes a backup. OpenDAL's `fs` service writes in place unless `atomic_write_dir` is set, which can leave half a file under its final name, so the guarantee above holds for an `opendal:fs` repository only with `atomic_write_dir` (a directory on the same filesystem).
2. **No runtime nesting.** The backends' internal Tokio runtimes never meet the daemon's runtime.
3. **Isolation.** Memory from large indexes is returned to the OS when the worker exits, and a panic or out-of-memory kill in the engine can't take down the daemon.
4. **Deadline enforcement** (I3, §7.3; decision 55). `rustic_core`'s `backup()` writes the snapshot itself and offers no hook before that write. Instead, once the worker has written `Started` for a job with a deadline budget, a watchdog thread compares wall-clock time against `index_read_at + budget` and, once it notices the deadline has passed, first asks for the cancel of item 1, so the backend refuses every snapshot write from then on, then writes `Failed { DeadlinePassed }` as the last line and ends the worker with 75. Its first check runs before the job's work starts, so a zero budget stops the job before it writes anything. After that it waits for the time left to the deadline, but at most `watchdog_interval` (5 s by default) at a time, and these waits don't count the time a machine is suspended, so it notices the deadline when it comes, and one that passed during a suspend within one interval of waking. A snapshot write that starts in that gap after a wake is not refused, as it wasn't before decision 55; the prune margin covers it. A writer stuck on a full pipe can't hold the exit back: the watchdog tries the stream once, and goes on whether or not it could write the failure. A job that isn't archiving a backup ends at once (`process::exit(75)`). A backup that is archiving winds down as a cancelled one does (item 1): it starts no snapshot write and saves the index of the packs it wrote, and the job ends the worker with 75 once rustic returns, so a check finds nothing to warn about and the next backup reuses the data; a failure the watchdog couldn't write, the job writes then, as the last line. A snapshot write that had begun at the deadline finishes, in both halves of a hot/cold repository: that write is what the prune margin covers, and ending the worker during it could leave the snapshot in one half alone. The operation is still `deadline-passed`, and in that case its snapshot exists, as after a cancel that comes once the snapshot was written. The watchdog waits for the wind-down 30 s at most, which bounds a worker whose daemon is gone, and then exits with 75. The watchdog stops once the backup has returned: the snapshot is written, and the result goes out before the repository's index is dropped, so a deadline that passes meanwhile can't turn a finished backup into a failure. The daemon also stops the worker at the deadline, with its grace period (below).
5. **Privilege separation (later).** On servers, the worker can run as root to read `/etc` while the daemon and web UI run unprivileged. This uses a small setuid-free helper started via a systemd unit, or `sudo` with a fixed command. Before building it, hooks and `password-command` must be restricted to root-owned config, or the unprivileged UI could escalate to root through them.

Each running worker of a repository whose ID is known gets its own `cache_dir`, a cache slot `<cache folder>/<repo-id>/<slot>`, because rustic's cache has no cross-process locking: the slot is the lowest number no other running worker of that repository uses, and it is free again when the worker exits. The worker also holds an exclusive `flock` on its slot directory for as long as it runs, and a daemon looking for a slot skips directories whose lock is held, so a worker that outlived a restarted daemon never shares its cache with a new one; a worker that finds its directory held runs with `no_cache`. A lock is only taken while the slot's path still names the folder locked, not a link, so a slot removed while its lock was held is never held through the folder that was removed. The daemon passes its cache folder (below, under **Config**) to the engine at start, made 0700 when it isn't there yet; every folder made under it (the repository's folder, the slot, and the cache folder again when it was removed meanwhile) is always 0700. With no cache folder (no home directory and no `LADDERBACK_CACHE_DIR`), or one that can't be made or written to (the daemon makes and removes a file of its own in it at start), it says so once in its log and its workers run with `no_cache`, which costs each job a fresh read of the index and nothing else (§16, decision 59). Without a known ID, the worker runs with `no_cache`; a daemon job of a saved entry that records none therefore runs after an identify, with the ID it found (§16, decision 81), so only an identify, an initialisation and a job of a repository a request gave run that way. When the daemon has a cache folder and gives a job that opens a repository no slot, its log says why in one line at the info level, with the operation's ID and the job's kind: the job names no ID, or none of the repository's slots is free (a look at the slots that fails is logged the same way). A worker that finds the lock of the slot it was given held runs with `no_cache` without a line of its own: the daemon gave it a slot. rustic itself treats a cache it can't write (a full or read-only disk) as a warning and goes on. Each time it starts, before it listens, the daemon tidies the cache folder: it removes every slot no worker holds of a repository no entry records (and that folder once empty), every other repository's slots above the highest one in use (slot 0, a slot another process's worker holds, or one whose lock can't be looked at), and rustic's unfinished `<id>-tmp-` files over a day old in the slots kept. While an entry records no ID, no repository counts as one no entry records, since the tidy can't tell which folder is that entry's: every repository keeps its folder until the entry's next job records the ID. It touches a slot only while it holds the slot's lock, only folders named as a repository ID and slots named by their number, and never follows a link; the log says what went and its size (§16, decision 61). It runs with `nice` (and `ionice` on Linux) as configured per agent.

**Event protocol** (module `engine::job`, §8.3):

```rust
enum WorkerEvent {
    Started { op_id: Uuid, pid: u32, index_read_at: Timestamp }, // taken just before the index is read
    ProgressStart { key: u32, kind: ProgressKind /* Spinner|Counter|Bytes */, prefix: String },
    ProgressLength { key: u32, len: u64 },
    ProgressInc { key: u32, inc: u64 },    // coalesced: at most ~4 msgs/s per key
    ProgressTitle { key: u32, title: String },
    ProgressFinish { key: u32 },
    Warning { item: Option<String>, during: String, code: WarningCode, detail: String }, // from Progress::error; detail = rustic's text
    Log { level: Level, message: String },   // logs are never localized (§8.4)
    Snapshots { snapshots: Vec<SnapshotResult> }, // a batch of a listing, before its Result (below)
    Result(OpResult), // BackupSummary | ForgetSummary | PruneStats | CheckReport | …
    Failed { code: ErrorCode, args: Vec<(String, MsgArg)>, detail: Option<String> }, // codes from `api` (§8.4)
}
```

`ProgressBars` is implemented by `EventProgressBars`, which writes these events. Per-file errors raised through `Progress::error` become **warnings**, so an operation can end as `Succeeded`, `SucceededWithWarnings` or `Failed` (§3.1). The worker builds a `Redactor` (§3.1) from its `JobSpec`'s repository and `repo_hot`, password, options, `options_hot`, `options_cold` and resolved secrets (`RepositorySpec.secrets`, copied from `RepositoryAccess.secrets`) and passes every `Log`, `Warning` and error through it (I4); §10.2 lists what it masks. A worker stopped by its watchdog emits nothing more; the daemon records the operation as `Failed { reason: DeadlinePassed }`.

**Message cap.** The daemon reads the worker's stdout one line at a time and the worker reads its stdin to the end, and each side reads at most `MAX_MESSAGE_BYTES` (1 MiB, in `engine::job`) of a message plus one byte to tell it from a longer one (§13.5, rule 2). An event line past the cap fails the operation as `EngineFailed` with the cap in its detail, and the daemon kills the worker; a worker answers a `JobSpec` past the cap with `InvalidJobSpec`; the daemon refuses to start a worker for a spec it would reject. A line that never ends therefore never grows a buffer past the cap. The worker keeps its own lines under the cap: it cuts each text field (log messages, warning items and details, failure details) to 64 KiB, after redaction, so a cut can never keep the start of a secret.

**What does not fit the cap is split by its sender (decision 32).** The cap stays at 1 MiB, and no list in a message grows with a repository: whoever sends one splits it, with a bound on each piece.

- *A job names at most `MAX_JOB_IDS` snapshots* (5,000, in `app::ports`; an ID is about 70 bytes of the spec). `RunMaintenance::execute` splits a forget's or an adoption's list into jobs of at most that many and runs them one after another as one operation, with one summary: the IDs removed (or the copies made) of every job, in order. The first job to fail, or a cancel during a job or seen as one ends, ends the operation as it would a single job and starts no more. A cancel that fired before a job's engine was up ends the operation cancelled, even when the job's result is ready at once. Every job touches only snapshots the selection named, so what earlier jobs did stays done and is not the operation's to undo; the operation records a warning that says how many were done, and the next run selects what is left. The engine refuses a job that names more with `EngineError::Unavailable`, as it does a spec past the cap.
- *A listing is a series of `snapshots` events.* `Ls` emits `Started`, then `Snapshots { snapshots }` events, newest first, each serialized to at most 512 KiB (one snapshot alone in an event may be longer, up to about 800 KiB), then `Result(Snapshots { count })`, where `count` is what the events carried: the daemon hands the list on only when its own count agrees, and fails the job (`EngineFailed`) otherwise, so a listing that lost a batch is never taken for the whole. This replaces "`Ls` emits `Started` and one final result". A repository with more than `MAX_LISTED_SNAPSHOTS` (200,000) fails the listing with its count in the failure's detail rather than being listed in part, and the daemon refuses a listing whose texts weigh more than `MAX_LISTED_BYTES` (256 MiB): the list it holds is bounded in both, and a partial list would make forget decide on history it can't see.
- *A snapshot is cut to a size one message holds.* A listed snapshot carries at most 64 paths (`api::MAX_SNAPSHOT_PATHS`) and 64 tags (`api::MAX_SNAPSHOT_TAGS`), and no text (a path, a tag, the host, the label) of more than 1 KiB, a cut text ending in `…`. That is under 800 KiB for any snapshot, even with every character escaped, so each fits a message alone. The worker sets `paths_truncated` or `tags_truncated` when it left something out or cut it, and the DTO carries both (the UI does not show them yet); a cut host or label ends in `…`. When tags are cut, the `ladderback-*` tags that say who owns a snapshot are kept first, so a forget never takes an owned snapshot for an unowned one. The DTO validates the 64 limits (it refuses a snapshot beyond them); the worker is who cuts, for transport.
- *A repository's reads wait a bounded time.* `RunMaintenance::assess` gives up an identify or a listing after `READ_TIMEOUT` (10 minutes) with `MaintenanceError::TimedOut`, which stops the worker, holds no slot and writes nothing.

**What is implemented of this protocol (M1a, plus the secrets work of M1b):**

- A job is `Fake | Identify | Backup | Prune | Check` (decision 80 adds `Probe`, which opens one location with its own credentials and reports the repository ID it holds, so a location that hangs is killed rather than the job). The repository password travels as a plain string on stdin only, and `JobSpec` also carries `cache_dir` and `watchdog_interval_ms`.
- A repository with a hot half (`repo_hot`) is opened through both halves. `options` apply to both, `options_hot` to the hot half only and `options_cold` to the cold half only (rustic's own rule), and the job's repository string is the cold half. rustic reads the hot half's config first and requires the keys of the halves to match, so a missing hot half fails the job at the open. It keeps keys, snapshots, index files and tree packs in the hot half and reads them from there, so a check fails when a snapshot is missing from it; file data is in the cold half only. A `RepositorySpec` that leaves the hot fields out, as an older daemon's would, is refused as `InvalidJobSpec` (`options_hot` and `options_cold` have no default) instead of being opened as a cold-only repository.
- The first line of a worker's stream, once its spec has parsed and the redactor is installed and before it opens anything, is a `Log` at the debug level reading `job accepted`, with nothing of the job in it: it is the proof of life the daemon's start timeout waits for (below). A spec that doesn't parse gets `Failed(InvalidJobSpec)` alone. `Started` is written when the job's clock starts: right before `to_indexed_ids()` for a backup, before `prune_plan` for a prune, before `check` for a check, and after opening the repository for `Identify`. Progress that rustic begins earlier (listing snapshots) never reports, and only `Log` and `Failed` can precede `Started`.
- `ProgressInc` is coalesced on the leading edge: the first goes out at once, the rest are added up and sent at most every 250 ms per key, and the remainder is flushed before `ProgressFinish`. A source rustic could not read (`scan`, `archival`) is a `SourceUnreadable` warning; any other `Progress::error` is `Unknown`.
- `Failed.code` is `deadline-passed` only when the deadline ended the job (the watchdog writes it, or the job as the worker ends when the watchdog couldn't); the codes the engine adapter reads from what rustic reports (`repository-not-found`, `repository-replaced`, `credentials-refused`, `password-not-accepted`: `translate` in `client.rs`) aside, all else rustic reports is `operation-failed` with `detail` = rustic's one-line message, after redaction. Exit codes: 75 deadline (the watchdog's, or the job's once a backup has wound down at its deadline), 143 SIGTERM, 74 events could not be written. The client maps `Failed { DeadlinePassed }`, and EOF with exit code 75, to `DeadlinePassed`.
- Stopping a job sends SIGTERM, waits the grace period (10 s by default), then SIGKILL; `stop()` returns once the process has exited, and the job's events end without a result. While it waits, `stop()` reads and drops what the worker still writes: a backup winding down (item 1) whose events went unread until the pipe was full would otherwise stay blocked writing one, and the SIGKILL would leave its packs unindexed. Dropping a running job kills the worker at once, but after a result it has 10 s to finish. At the deadline the daemon stops the job, with the grace period, so a backup that archives can wind down (item 4), and so it does when the worker reports the deadline first; it checks the deadline on every event too, so a stream that never pauses can't hold it off. Once the worker has exited, the operation is recorded `deadline-passed`, whatever the exit code, so its end time can be up to the grace period past the deadline, as a cancelled one's is past the cancel. A result stands even when it arrives past the deadline: its snapshot is already written.
- Two timeouts keep a hung worker from holding the daemon. A new worker has one deadline of 30 s (`WorkerEngine::with_start_timeout`), counted from the start of the write of the job to its stdin, to take the job: it ends with the worker's first complete line of any kind, which is normally the `job accepted` log line above. Opening the repository, which a slow backend can make take longer, comes after that line and is not bounded by this timeout. A worker that doesn't read a spec larger than the pipe's buffer (64 KiB on Linux) leaves the write blocked, so `run` kills it with its process group and fails with `EngineError::StartTimedOut`. A worker that took its job and then says nothing is killed with its group by the job's event stream, which ends with a single `Failed(EngineStartTimedOut)`; `run` doesn't wait for it, because that would delay a user's cancel until the first event. Either way the operation fails as `EngineStartTimedOut` without having started. After its first line a worker is not on this clock: how long it takes from there is for the job's deadline and for cancel. A timeout too long to represent, such as `Duration::MAX`, never passes. Once a worker's event stream has ended, the process has 10 s to exit (`with_exit_timeout`): one that stays alive is killed, and the operation fails as `EngineExitTimedOut`. The wait inside `Control::stop()` after SIGKILL has no timeout of its own: its signature can't fail, and a SIGKILL can't be refused short of an uninterruptible sleep.
- Backup chooses the parent with `PlanTags::parent`: explicit `ParentOptions.parents`, or rustic's own match when it returns `None`. Extra tags are `UserTag`s, which never start with the reserved `ladderback-` prefix in any case, so they can't make a snapshot look like another plan's (I6); the worker refuses such a tag in a spec too. Prune always runs with `instant_delete = false` and `early_delete_index = false`, and `keep_delete` is a `KeepDelete`, never under rustic's 23 h default; the worker refuses a shorter one too. Its summary counts `packs_marked = unused + repack`, `packs_deleted = packs_to_delete.remove` and `packs_recovered = packs_to_delete.recover`. Check sends each finding as a warning of its level (`check-warning` for rustic's `Warn`, `check-error` for anything else) in rustic's own words, masked and cut like every warning, the errors first so that the operation's cap on warnings never keeps a tidy-up in place of an error, then counts the findings by level; a check that ran to its end succeeds, with warnings when it found anything (§16, decision 51).
- A backup's spec carries its plan's snapshot host (§3.1) and its whole `SourceFilter` as `SourceFilterSpec`. The worker maps the filter's globs and glob files onto rustic's `Excludes` and the rest onto `LocalSourceFilterOptions`, and the host onto `SnapshotOptions::host`; with no host, rustic records the machine's own name. The worker parses the host again as a `Hostname` and refuses one that isn't (`InvalidJobSpec`), before it opens the repository. A spec without `filter`, as an older daemon's would be, is refused the same way; a spec without `host` means no host. The job spec's size cap bounds every pattern and path the filter lists, but rustic reads each glob file whole, so a very large glob file costs the worker's memory, never the daemon's. The worker runs in the daemon's working directory, and rustic reads a glob file from the working directory, so every `glob-files` and `iglob-files` path is a `GlobFile`, an absolute path: the configuration refuses a relative one at its key when it loads (`Value(GlobFile)`, §6.1), and an import refuses it as unsupported (§6.2). The worker doesn't check the paths again.
- The `Redactor` masks each secret raw, fully percent-encoded with either hex case, and as the url crate encodes a userinfo (rustic quotes URLs that way); a secret a URL parser splits (`@`, `#`, `?`, `/`, `:`) is also masked piece by piece from 8 bytes, and as it is printed across the host, path and query. A password in the repository URL is masked as written and decoded, and also when a raw `/` in it ends the authority early.
- **Worker environment.** A worker is started with `env_clear()` and only the variables of an allow-list from the daemon's environment (module `engine::environment`): `PATH`, `HOME`, `USER`, `LOGNAME`, `TMPDIR`, `TZ`, `LANG`, `LC_ALL`, `SSH_AUTH_SOCK`, `XDG_CONFIG_HOME`, `XDG_CACHE_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME`, `SSL_CERT_FILE`, `SSL_CERT_DIR`, `RCLONE_CONFIG` and the proxy variables `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY`, each also in lowercase. Names are matched exactly. Everything else, such as `AWS_*`, `AZURE_*`, `GOOGLE_*`, `RUSTIC_*`, `RCLONE_CONFIG_*` and the variable a secret reference was read from, is not passed; a repository that needs a credential gets it through `${…}` in its options (§10.2). A proxy URL with credentials embedded passes as it is, so those credentials stay in the worker's environment (a residual risk the user takes by writing them there; no secret source is added for them), but they are masked wherever the worker's output shows them: the daemon adds the password and the whole userinfo of each of `HTTP_PROXY`, `HTTPS_PROXY` and `ALL_PROXY` (either case, with or without the scheme; `NO_PROXY` lists hosts, not a URL) to the job's `Redactor`. The base is the daemon's own environment, read at each job, unless `WorkerEngine::with_environment` replaces it; tests and a composition root that has read its environment already use that.
- **Masking by the daemon.** The programs a worker starts (rclone, ssh) write to its stderr without going through its `Redactor`, so the daemon builds a `Redactor` from the job's repository and `repo_hot`, password, the three option sets and secrets, and the proxy credentials above, and masks each stderr line before logging it. A line cut at the cap is masked as a cut text (§10.2, "Where masking runs"), and so is a last line the stream ended without its newline, which a kill can leave partway through a write; both are logged ending in `…`. It masks every text a worker's events carry as well: failure details, warnings, progress text (which then only names a step, and goes no further: decision 82) and log lines, and the failure it reports for a line it can't read. The worker masks its own, but it rejects a job spec before it has the job's secrets, and a parse error can quote the value it choked on, and it knows nothing of the proxy credentials. The worker cuts a text after masking it and marks the cut with `…`, so the daemon masks a text that ends in the mark as a cut text too. A fake job has no secrets of its own and masks only the proxy credentials.
- OpenDAL's local file service is the repository string `opendal:fs` with the option `root`.
- A worker leads a process group of its own. A stop sends SIGTERM to the worker alone, so a backup winding down (item 1) keeps the programs it started, then SIGKILL to the group after the grace period; a kill is the group's. A worker that exits by itself, at its deadline (75), on a broken event stream (74), on a SIGTERM (143) or by crashing, gets the group a SIGKILL as well, so the `rclone` of an rclone backend, which `process::exit` doesn't stop, ends with the worker. On Linux the daemon sees the exit with `waitid(WNOWAIT)` and signals the group while the worker is an unreaped zombie, which still holds its process id. nix has no `waitid` on macOS, so there the worker is reaped first and the group is signaled by the id it had. POSIX keeps a process id from being reused while a process group of that id has a live member, so the window left is a group with no live member, whose id a new process takes and makes itself leader of between the reaping and the signal. The worker keeps the event pipe on a close-on-exec descriptor of its own and points descriptor 1 at `/dev/null`, so no program it starts inherits the pipe or can write into the stream. Once the worker has exited, the daemon reads what is left in the pipe for one more second at most, so a process the worker left behind that holds the pipe open can't keep the events from ending. On Linux the worker asks for SIGHUP when its parent dies (`PR_SET_PDEATHSIG`) and handles it as a SIGTERM once its parent is no longer the process that started it. The kernel sends that signal when the parent *thread* ends too, and the daemon starts workers on tokio's blocking pool, whose threads end after 10 s without work while the daemon lives on: a SIGTERM there stopped a backup that outlived its thread, which failed with 143 (#448). Elsewhere a worker whose daemon died ends at its next event, when the pipe is broken.
- A progress or log callback that finds the event stream unwritable (the daemon is gone) ends the worker at once with code 74, and so does the job's own write failing. A panic is written to stderr with the job's secrets redacted. The worker's stderr is a pipe the daemon reads on a task of its own, never the terminal: a worker in a process group of its own is a background job to a terminal with `stty tostop`, and a write to the terminal would suspend it. Each line, cut at the message cap, goes to the daemon's log as a warning (target `ladderback::worker`), without holding up the events, and the reading ends with the worker like the events' does.
- Integration tests run the worker through `engine-worker`, this crate's own binary, which does what `ladderback worker` does.
- Every child the daemon starts, a worker, a hook, a password command or the `rclone` that serves an `rclone:` repository it opens to evaluate retention, starts through the spawn gate (`spawn_gate::hold`, decision 58): one start at a time in the process, so none inherits another's pipes where the standard library makes a pipe in two steps (macOS). The gate is held for the start only, not while the child runs, nor while `rclone` comes up: the engine starts that server itself, as rustic's backend does, and waits for its address outside the gate. That wait, and the one for `rclone version`'s answer, end 2 minutes after the open began, well inside the use case's read timeout: an `rclone` that hasn't answered by then is killed and reaped, and the open fails (#326). Async code waits for the gate on tokio's blocking pool (`spawn_gate::hold_blocking`), so a start whose `exec` stalls never holds up the runtime's threads.

### 4.2 Daemon (agent)

- **axum 0.8** HTTP server. It serves the embedded UI, `/api/v1/*` (JSON) and `/api/v1/events` (WebSocket for live updates). It binds to `127.0.0.1:9898` by default. Request checks, body limits and the security response headers (§10.1) apply whether or not auth is enabled: a request is checked first, then its body is read up to the limit of its route class (128 KiB for `/api/v1`, none for the UI) before a route runs, and every response carries the headers. It listens through `http_adapter::GatedListener`. Where the platform makes a socket and accepts a connection in two steps (macOS), that listener makes the listening socket and accepts each connection while it holds the spawn gate (decision 66), so a child started meanwhile never inherits them; Linux accepts as tokio does. An accept takes the gate on the runtime's thread when it is free at once, and otherwise waits for it, and accepts, on tokio's blocking pool. A failed accept is handled as `axum::serve` handles its own: a connection its client gave up on is passed over, and any other failure is logged and tried again a second later.
- **Scheduler** (§5). It turns plans into jobs and respects the agent's concurrency limit and each plan's overlap policy (decision 75). `app::schedule::Scheduler` is the loop: `src/main.rs` spawns the composition root's `Background` task (`src/composition.rs`) once the daemon listens, which runs the queued backups recovery handed back and then the loop, and aborts it once serving has ended, after axum's graceful shutdown has let the open requests finish. It starts a plan's run through the `PlanRuns` trait, which the composition root's plan runner implements: not a port, but the use cases the root wires, so a scheduled run is a manual run's use case with another trigger. Every backup, scheduled, started by hand or held from before the start, takes its place in one `app::queue::RunQueue`, and runs once its turn comes.
- **Job runner.** It spawns workers, consumes events, writes the op log (queued, running, finished; a write the store refuses never changes how the operation ends, §9) and broadcasts to UI clients: a job's start, progress and warnings as the worker reports them, and how an operation ended once the run's last write to the log is done (§4.4). If a hub is configured, it also writes events to the sync outbox.
- **Store.** SQLite via `sqlx`, in WAL mode (§9).
- **Logging.** `serve` installs `env_logger` first, writing one plain line per record to stderr, with millisecond timestamps and colour as §4.5 decides it: none with `--plain`, otherwise by what `anstream` reads of `NO_COLOR`, `CLICOLOR_FORCE` and `CLICOLOR`, and then of whether stderr is a terminal. The default level is `info`, because env_logger's own would hide the worker's warnings (§4.1); `RUST_LOG` directives layer on top of that default, and an unset, empty or blank value means the default. It logs `ladderback <build> starting` before it binds, the build as `--version` names it (`0.3.0`, or `0.3.0+3f937cf` between releases; decision 90). The lines the daemon says itself (`listening on`, the refusals that stop it, and the warning that sign-in is off on the network, which no `RUST_LOG` setting may hide: §10.1) are not log records: they are written through `output::to_stderr` (§4.5), so a log that nobody reads stops the daemon with 141 at the first of them, before it serves, whereas once it serves the logger drops what it cannot write and the backups go on. `ladderback worker` installs no logger.
- **Config** (§6.1). `config.toml` in the platform config dir, `LADDERBACK_CONFIG_DIR` when set (a non-empty value; tests and a second daemon use it). The platform folders: macOS `~/Library/Application Support/ladderback` for both config and data, `~/Library/Caches/ladderback` for the cache; Linux `$XDG_CONFIG_HOME|$HOME/.config/ladderback`, `$XDG_DATA_HOME|$HOME/.local/share/ladderback` and `$XDG_CACHE_HOME|$HOME/.cache/ladderback` (a relative `XDG_CACHE_HOME` is ignored, as the XDG specification says); `LADDERBACK_DATA_DIR` overrides the data dir, which holds `ladderback.db` and the agent ID, and `LADDERBACK_CACHE_DIR` the cache dir, which holds the workers' cache slots and nothing that is needed. No home directory and no override is a typed exit for the config and data dirs, not a guess; for the cache dir it only means workers without a cache (§16, decision 59). A service with no home directory sets `LADDERBACK_CACHE_DIR` (under systemd, to its `CacheDirectory=`). `serve` reads the config before it binds: a file this build cannot read — unreadable, too large, missing or newer schema, invalid — is a typed startup exit (the catalog's `cli-config-*` messages) that names the file and the version it found; it never starts on a silent empty configuration, and never prints "listening on" first. An empty configuration is fine: an agent with nothing to do still serves.
- **Start-up order.** `serve` creates the data folder and takes its lock (`<data>/ladderback.lock`, §9) before it reads anything, so a second process on the folder is refused before it touches the configuration. Then it reads the configuration, opens the operation log, ends the operations that log still shows as running and reads the queued ones (`RecoverOperations`, §9), and only then builds the engine and the router's state, binds the listener and prints `listening on`. Then it runs the queued backups again and starts the scheduler (§5, decision 73). A start that can't lock the folder (`cli-data-dir-in-use`, or `cli-cannot-lock-data-dir` when the file system has no locks) or can't end those operations (`cli-cannot-recover-operations`) is a typed exit like the configuration's: it prints no `listening on` and serves nothing. A recovery that ended operations logs one warning with their count.
- **Shut-down order.** On Ctrl-C or SIGTERM `serve` stops serving (axum's graceful shutdown) and stops the background task, so the scheduler starts no run and the persistent queue hands on no more (decision 73); then it closes the operation log (`SqliteStore::close`), which waits for the log's calls in flight: a write a running operation began commits or fails as it would have rather than being cut off, and no connection, and so no `-wal` or `-shm` file, outlives the daemon. It waits 20 s at most (`LOG_CLOSE_BOUND`, the `SAVE_BOUND` a run gives one write of its own, past the store's own bound on a call of about 15 s): a busy store still finishes, and one that hasn't by then is stalled, so the daemon logs a warning and stops without it rather than hold up the service manager, which would kill it anyway. A write an operation makes after the close is refused. At the next start, an operation the log still shows as running ends `daemon-stopped`, as after a crash, and one it still shows as queued is the persistent queue's again (§9, decision 73). Only then does it drop the runtime, and with it the jobs still running, and last it lets go of the data folder's lock (§9), so no other daemon recovers the log while this one could still be writing it. A start refused once the log is open (`cli-cannot-recover-operations`, an agent ID it can't read or its own path it can't find) closes the log the same way before it exits. A daemon told to stop exits with status 0.
- **Operations API.** `POST /api/v1/operations` with `{"plan": …}` starts a backup of a named plan and answers `202` with the operation's ID, after the operation is in the log as queued and its cancel switch is parked, so a cancel sent at once is accepted, and one that fires before the engine is up ends the operation cancelled once its before-hooks have run; refusals are typed (`plan-unknown`, `invalid-body`, `config-unavailable`, and the secret and template codes of the Repositories API, 422, with the same arguments and a `detail` masked of every secret of the repository, I4, when the plan's repository has a secret that can't be resolved; nothing is queued then, #309). E2 grows it into the operations page: `GET /api/v1/operations?after=<cursor>&limit=<n>&plan=<id>` answers the keyset history page, newest first, running operations included — the page's initial state over REST, which a client that then subscribes closes the gap a late subscriber has (§4.4); `GET /api/v1/operations/{id}` answers one operation's detail with its warnings; an operation that failed carries `failure-code`, and beside it `failure`, `{code, args?, detail?}` as a refusal's error is shaped: the arguments its message takes, by name, and the engine's own words, which the engine masked of every secret of the job (I4, #474); a backup the schedule started that was refused for a setting of its repository (scheduling-and-config.md §5) carries its refusal as a request to start it is refused with, what a platform or a command said as `detail`, masked of the repository's secrets. `failure` is a field added to the published `/api/v1` shape (operations.md §12.1), so `failure-code` stays as it was; `POST /api/v1/operations/{id}/cancel` takes the empty JSON body `{}` (the JSON-body rule applies to every mutating method) and cancels politely: the worker stops, the finally-hooks run, the operation ends `cancelled`. Cancel reaches an operation whose cancel switch is parked: a running one, and a queued one this daemon started or the persistent queue has handed on, which ends `cancelled` without reaching the engine. A queued operation from before a restart that the queue hasn't handed on yet (it is still on its way, or the configuration couldn't be read, decision 73) has no switch, and is `operation-not-running` (409) like a finished one; an unknown ID is `operation-unknown` (404), a cursor that isn't an operation ID `invalid-cursor` (400), and `limit` is clamped, never refused. Operation IDs are UUIDv7, which is what the log orders by. A second backup of the same plan runs beside the first; I7's slot rule is maintenance-only. The agent, repository and plan hooks (§6.1) wrap every API-started run, read from the configuration as it stands when the run starts.
- **Plans API.** `GET /api/v1/plans` answers `{"plans": […]}`, one row per configured plan in the order the configuration writes them: `id`, `repository` (its alias), `scheduled` (whether it has a schedule; one without runs only when it is started) and `next-run`, the scheduler's planned run as RFC 3339 in UTC, or `null` for a plan without a schedule and for a scheduled one the scheduler has planned no run for (it hasn't yet, or the schedule has no run left), and `warnings`, left out when there is none: one `glob-never-matches` per glob of the plan that can never match (scheduling-and-config.md §6.1, #510), which the start page shows in a Notes column that it adds only when a plan has one. A planned run that can't be read is no reason to hide the plans: they are listed without it, and the daemon's log names the store's code. A configuration the daemon can't use is refused with its `config-*` code (503), as the bullet on such a configuration below says. The start page lists them, with each next run in the reader's own time zone; the operations page offers a start button for each. Without plans, the start page says to connect a repository first, since a plan backs up to one by name, and links to the Repositories page; it always links to where a plan's format is described, §6.1 at the tag of the build's release on GitHub, so a build from `main` between releases links to the previous release's text (`routes::PLAN_FORMAT_URL`, #477).
- **Repositories API.** `GET /api/v1/repositories` answers `{"repositories": […]}`, one row per configured repository in alias order: `alias`, `maintained-here` (whether this agent maintains it, §7.3: `true` only for `maintenance = "local"`; a row without it reads as `false`, so a page offers no maintenance it can't run), `create-offered` (whether the row offers to create the repository, decision 53: `true` while its entry records no `repository-id`, the newest operation of a plan that backs up to it failed `repository-not-found` and none of them ever succeeded, so never while nothing is on record; left out when `false`, and `false` for every row when the operation log can't be read, which the daemon logs at WARN), `repository` and `repo-hot` (where it is, with any password in a URL masked by the domain's `Redactor`), and `password`, where the password comes from (`{"source": "inline"}`, or `file` with `path`, `keyring` with `entry`, `env` with `name`, `command` with `program`), never its value (I4); and `warnings`, left out when empty: one `{code, args}` per secret written as text in the config (`config-inline-secret`, with `field` naming the setting, such as `password` or `options.secret_access_key`, and `location-secret` for a password in a location, with `field` `repository` or `repo-hot` and `kind` `rclone` for an rclone location, whose credential belongs in rclone's own configuration file, or `url` for any other; locations first, decision 37), which the page writes as a line of text in the password cell. Three routes take `settings` (`repository`, `repo-hot`, `password`, and the three option sets, as in `config.toml`; any other key is `invalid-body`): `POST /api/v1/repositories/_test` opens the repository, saves nothing and answers `200 {id}`; `POST /api/v1/repositories` with `{alias, settings, maintain-here?}` tests, then saves with the ID it read (`repository-id`, §7.3), with `maintenance = "local"` when `maintain-here` is `true` and with no `maintenance` otherwise (absent is `false`), and answers `201 {id}`; `POST /api/v1/repositories/_init` with `{alias?, settings}` creates a repository where none exists and answers `201 {id, saved}`, saving it, with its ID and with `maintenance = "local"`, when it has an alias (decision 48). `POST /api/v1/repositories/{alias}/init`, with any JSON body (the page sends `{}`), creates the repository the configuration already holds under `alias`, as an imported profile leaves one, where its entry says and with the password its entry names, and answers `201 {id}`; it records only the new repository's ID in the entry (`repository-id`), and only while the entry still names the location it was created at, and leaves the rest of it, `maintenance` included, as it was (decision 53); an alias the configuration doesn't hold, or that is no alias, is `repository-unknown` (404, with the `alias`), an entry that already records a `repository-id` is `repository-exists` (409), and any other whose row the list wouldn't mark `create-offered`, nothing on record included, is `create-not-offered` (409, no arguments), all before anything runs. Then, since the log doesn't say where the failure behind the offer happened, Create first asks the engine to open the repository where the entry says now, and initialises only when that fails `repository-not-found`: a repository that opens is `repository-exists`, and any other failure `create-not-offered` (decision 53 §7). The two underscore routes cannot collide with `/repositories/{alias}/…`, since an alias is a slug. A `password` is `inline` with `value`, `file` with an absolute `path`, `keyring` with `entry` or `env` with `name`; a `command` source is `invalid-body`, because it would be the first route that runs a program, and that belongs behind authentication (§10.1). Refusals are typed and carry the engine's own words as an optional `detail`: `invalid-body` (400; so are settings over their caps, a location or an option value of more than 64 KiB as written or an option set of more than 64 options, scheduling-and-config §6.1, #236; nothing runs), `repository-alias-invalid` (422), `repository-alias-taken` (409), `repository-already-configured` (409, with `alias`, the one the configuration already has for the repository at that location or with that ID: a repository has one alias, §7.3; a taken alias is refused first), `repository-exists` (409, with the redacted location), `repository-not-found` (404, no arguments: the job found an empty folder on this machine, local or OpenDAL `fs`, where the repository should be, decision 53), `credentials-refused` (503, no arguments: a REST server refused the repository's credentials with 401 or 403, decision 85), `repository-path-relative` (422, with the setting, `field`, that names a path on this machine by a relative one, a password file included: scheduling-and-config §6.1; nothing runs; a value both over its cap and relative is refused for its length, as `invalid-body`), the secret and template codes (422): `secret-missing`, `secret-unreadable`, `secret-keyring-unavailable` (a keyring source on Linux with no Secret Service to ask: no session bus, no daemon, or a locked or missing collection, §10.2), `secret-not-text`, `secret-too-large`, `secret-command-failed`, `secret-command-output-open`, `secret-command-timed-out`, `secret-in-process-arguments`, `secret-expansion-too-long`, `secrets-too-large-to-mask` (the secrets a job masks come to more than 256 KiB, with `limit`, §10.2; `field` is the setting where they passed it, the proxy variable such as `HTTPS_PROXY` when the engine counted the daemon's proxy credentials, and is left out when the job's own secrets did), `template-invalid` and `location-too-many-credentials` (an rclone location with more than 16 credentials, §10.2), each with the setting (`field`) and, for a source, where it is read from (`source`), and for the platform's or a command's words a `detail` with every secret of the repository masked (I4); the snapshot listing answers with the same codes and logs the code and that detail, `password-not-accepted` (503, no `detail`: the password opens none of the repository's keys), `credentials-refused` (503, the server refused the login, also when Create would make the repository there), `operation-failed` (422, `detail` is what rustic said, such as no repository at a REST, rclone or remote OpenDAL location), `engine-unavailable` (503), `repository-timed-out` (503), `repository-replaced` (503, the snapshot listing only: the location holds another repository than the ID the configuration recorded) and the `config-*` codes (503). Connecting tests and saves, and Create looks, creates and records the ID, under one lock, so two connections made at the same moment both survive and two Creates of one entry create it once; the lock is the composition root's, and a later writer of the configuration must take it too. Each of the three jobs has a deadline of 2 minutes (`REPOSITORY_JOB_BUDGET` in `domain`, a constant, not a setting), counted from the request's start of the job, the engine's start included, and Create's look and its initialisation are a job each, so it holds the lock for at most two deadlines: the use case races the job against a timer on the `Clock` (wall-clock, like every deadline here, so a machine that slept through the time finds it passed on waking) and checks it on every event, so a worker that keeps talking can't hold it off; the events already waiting behind the one that finds the time up are read first, for the result may be one of them. When it passes, the job is dropped, which kills the worker and its process group at once, and the request is refused with `repository-timed-out` and saves nothing; the lock is released as the request returns, either way. A result that arrives as the time runs out stands, since a repository it created is already there; a creation that was killed may have left part of a repository, and creating again says `repository-exists` only if its config was already written. The worker's own start timeout (§4.1) is separate and shorter, and the worker's watchdog (§7.3) is for backups only: neither covers a backend that takes the job and then never answers.
- **Repository locations (decision 80).** A row of a repository reached at several locations carries `locations`, every location in the order a job tries them, the first first, and leaves it out for a repository of one location, which `repository` names: each is `{position, repository, repo-hot?, options?, when?}`, with `position` from 1, the addresses masked as `repository` is, and `options` as `{set, name, reference?}` per option (`set` is `options`, `options-hot` or `options-cold`; `reference` is the value only when it is references alone, such as `${LAN_KEY}`, which say where a secret is and never hold it; a value written in the configuration is never shown, as it may be the secret). Its `warnings` add one `location-plain-http-credentials` per location that sends its credentials where an impostor could read them, with `position`, `cause` (`plain-http`, `unchecked-certificate`, `plain-endpoint`, `plain-ftp`) and `rule` (`network` when the location has a rule, which can't tell the network it is meant for from one made to look like it, else `none`), never the address or a credential (security.md §10.6), and `locations` (`one` or `several`), for a repository of one location too; `location-secret` and `config-inline-secret` carry an optional `position` for a location after the first. `when` is a location's rule, its alternatives in the order written, each `{network, only?, except?}` (`network` is `wired` or `wifi`; `only` and `except`, the Wi-Fi networks by name as the configuration writes them, are left out when empty), left out for a location with no rule. The row's `warnings` also carry the notes about the rules, for any entry with one, a repository of one location included: `location-every-ruled` when every location has a rule, `location-last-ruled-no-retry` with `plan` for each scheduled plan backing up to it that doesn't retry while its last location has a rule, and `location-rule-name-unreadable` with `position` for a rule that names Wi-Fi networks while the last read of the name failed (decision 80, point 10). The page shows each alternative in words under its location ("May be tried on a wired network."), then where the location is skipped, a VPN that carries all traffic included, and the notes as the row's other warnings are shown; a Test that skipped a location for its rule says so. `POST /api/v1/repositories/{alias}/test`, with any JSON body (the page sends `{}`), probes every location of the saved entry in order, past the one a job would use, each in a worker of its own with only its own secrets, and answers `200 {locations: [{position, address, outcome, source?}]}`: `outcome` is a location outcome code (`used` for one that answers and holds the repository, `silent`, `refused`, `not-a-repository`, `other-repository`, `password-not-accepted`, `secret-unavailable`, or the code of a setting that can't be used, such as `template-invalid`), and `source` names where a secret was looked for (`env LAN_KEY`) or the setting that can't be used, never a value. It records nothing: no operation, no repository ID. An entry of one location is tested too, and while it records no repository ID, whatever repository it holds counts as its own. An alias the configuration doesn't hold is `repository-unknown` (404, with the `alias`), a body that is not JSON `invalid-body` (400) before anything runs, a repository password that can't be read the secret codes (422), and a configuration the daemon can't use the `config-*` codes (503).
- **Maintenance API.** `GET /api/v1/repositories/{alias}/groups` lists the repository's snapshots by owner, read live through the engine like a snapshot listing (no slot, nothing stored): `plans` (every plan of this agent on the repository, in the configuration's order, with `count` and the newest `snapshots`), `orphaned` (tagged history no plan of this agent owns, with the plans it could be adopted into) and `unmanaged` (untagged history by host, label and paths, with the plans whose host, label and sources equal the group's). A group lists at most 500 snapshots (`MAX_GROUP_SNAPSHOTS`) and `count` is the real total; no list is built past its cap. `POST /api/v1/repositories/{alias}/maintenance/preview` takes the body of a start (`kind`, and for `adopt` the plan `into` and the group `from`) and answers `200` with what the run would do: a `forget` says per plan which snapshots its retention lets go (`total`, `remove` and at most 50 `listed`, `MAX_PREVIEW_SNAPSHOTS`) and what it leaves alone (I6), an `adopt` the snapshots it would rewrite, a `prune` the engine's dry run (`packs-marked`, `packs-deleted`, `packs-recovered`, `bytes-deleted`, and `keep-delete-hours`, I2), a `check` whether it reads data. A prune's dry run opens the repository as the prune does: an identify first, so the plan names the repository ID and reads through the repository's cache. The groups and the preview of a forget, an adoption or a prune carry `warnings`, left out when empty: `maintenance-other-hosts` (with `count` and `hosts`, the first five by name) when a repository this agent maintains holds snapshots from other hosts (§7.3); a prune's preview lists the repository's snapshots for it. A forget's and an adoption's preview names a `selection` (16 lower-case hex digits: a fingerprint of the exact set of snapshot IDs), and `POST /api/v1/repositories/{alias}/maintenance` takes it: the run is refused with `maintenance-selection-changed` (409) when what it would act on is no longer that set, before the slot is taken and before anything is removed, so what a person reviewed is what a run acts on (I6). Without a `selection` a start selects as it finds the repository. A `selection` on a prune, a check or a preview, a text that is not a selection, and a key the body does not know are `invalid-body` (400). Only a repository this agent maintains (`maintenance = "local"`, §7.3) is maintained through these routes: of any other, a preview and a start of every kind, adoption included, are refused with `maintenance-not-owner` (409, with the `alias`) before the engine is reached and before anything is logged, while its groups are still listed (I1). Refusals are typed: `repository-unknown`, `plan-unknown`, `maintenance-kind-unknown`, and `repository-not-found` when a read found an empty folder on this machine (local or OpenDAL `fs`) where the repository should be (404, decision 53), and `credentials-refused` when a REST server refused the repository's credentials (503, decision 85); `maintenance-not-owner`, `maintenance-busy` (start only), `maintenance-selection-changed` (409); `retention-keeps-nothing`, `adoption-no-match`, `adoption-ambiguous`, `operation-failed` (422, the last with the engine's own words as `detail`) and the secret and template codes of the Repositories API (422: the same thirteen, with the same arguments and a `detail` masked of every secret of the repository, I4); `repository-read-timed-out` (504: a read, each plan's retention read of a forget included, waits at most `READ_TIMEOUT`, then the worker is stopped); the `engine-*` and `config-*` codes, `protocol-violated`, `deadline-passed` and `repository-replaced` (503, the last when the location holds another repository than the ID the configuration recorded, §7.3); and `operation-failed` as 503 too when the operation log fails (with its own words as `detail`), and, with no `detail`, when a hook failed, the repository already exists or a plan's retention policy is not one the engine accepts. A preview takes no maintenance slot and writes nothing to the operation log. A snapshot the wire cannot carry is left out of its list and still counted; the groups and previews do not say that a snapshot's paths or tags were cut (the snapshot listing does).
- **A configuration the daemon can't use.** Every route that reads `config.toml` reads it on each request, and a file that can't be read or used is refused as a save of it is (#347; the mapping is scheduling-and-config.md §6.1): `GET /api/v1/plans`, `GET /api/v1/repositories`, `POST /api/v1/operations`, `GET /api/v1/repositories/{alias}/snapshots`, `…/groups`, `…/maintenance/preview` and `…/maintenance` answer 503 with the same `config-*` code and arguments, so a hand edit with a mistake in it is `config-invalid` with the `file`, the `line` when the reader knows it, and a `detail` that starts with the setting (`repositories.demo.colour`) and never holds a value of the file (I4); a file that can't be read is `config-unavailable` with the `file` and the system's words. A snapshot listing the engine can't start is still `engine-unavailable`, by its code alone. The Repositories page says it in the list's place, the Operations page where the plans' buttons would be (and a refused start or cancel above them), and the Snapshots page where the repositories to pick from would be, each in a `role="alert"` paragraph with the daemon's words marked as English (§8.4).
- **Profile commands** (§6.2). `ladderback import-profile <file.toml> [--repo-name <alias>] [--json]` reads a rustic profile and adds its repository and plans to `config.toml` in one save, and prints what it added; `ladderback export-profile --plan <id>` prints one plan as a profile the stock `rustic` reads. They run in the CLI process, not in the daemon, through the `ProfileReader` and `ProfileWriter` ports (`adapters/interop`), the config store and, for the agent ID the export tags, the data folder. Neither opens a repository, runs a hook or resolves a secret. Notices are warnings on standard error, in the catalog's words; the profile of an export is the only thing on standard output besides the import's summary. A refusal is a typed error on standard error, exits with 1, and changes nothing: an import writes no file, an export prints no profile. The commands read the process's environment in one place: `RUSTIC_*` (the import's gap-fill, §6.2), and `HOME`/`XDG_CONFIG_HOME` for rustic's profile folder (`platform::rustic_config_dir`). `import-profile` takes `--json` (§4.5): one document on one line of standard output instead of those sentences, and nothing on standard error. The document is what the import added, with its notices as codes and arguments, or the code of its refusal: the codes the REST API has (a name that is no alias is `repository-alias-invalid`), and two made for what stops an import before it starts, `config-folder-unknown` and `runtime-unavailable`. The profile an export prints is TOML, so it has no `--json`.
- **What an operation's summary says (#192, decision 52).** Each summary in the operations history carries, when the log has it, `repository`: the alias of the repository a maintenance run ran on, as it was when the run started (absent for a backup and for a row an earlier build logged). A backup's `result` carries `files` (new, changed and unmodified, summed without overflowing), `bytes` (the data it added, as before), `duration-ms`, and the optional `snapshot` (64 hex digits) and `bytes-processed` (the source it went through). A summary of a repository reached at several locations carries `locations` (decision 80): every location as the run's choice saw it, in order, as `{position, address, outcome, source?}` like a Test's answer, with `not-tried` for a location after the one used; the one whose `outcome` is `used` is the location the run used. It is left out for a repository of one location and for an operation that opens none. Every new field is optional, so a client of the earlier API reads what it read before.
- **Secrets** (§10.2).
- **Hub client** (§7). It keeps an outbound WebSocket open, with reconnect, backoff and outbox replay.

### 4.3 Hub

Everything an agent has, plus:

- **Agent registry**: agent ID, identity public key, hostname (unique), version, last seen, online status, clock offset.
- **Aggregated op log.** It receives operation records and summaries from agents. Raw logs stay on the agent and are fetched on demand.
- **Plan registry.** Agents publish their plans (minus secrets), so the hub knows the retention policy for each `ladderback-plan` tag.
- **Repo ownership registry.** It maps each rustic repository ID to its single maintenance owner (I1, §7.3).
- **Maintenance runner** for **hub-managed repos** (§7.3): forget, prune and check, serialized per repo by `OperationStore::try_start` (I7).
- **Downloads.** For hub-managed repos, the hub opens the repository with its own secret and streams `dump` output to the browser. No file contents cross the sync protocol.
- **Notifications** (§11).
- **Remote control** (milestone 5): "run now", cancel, and restore into a new folder on agents that allow it (§10.4). Plans are **view-only from the hub** in v1. Editing them from the hub is a post-v1 feature, opt-in per agent (§16, decision 2).

### 4.4 Web UI (Leptos CSR)

Every page follows §4.5. Pages:

1. **Dashboard.** A card per machine: online status, last backup per plan (time, result, size added), next run, overdue plans and any running operation with live progress. A list of recent failures and warnings.
2. **Machine detail.** Plans, history timeline, logs and an agent settings summary.
3. **Plans.** Create and edit sources, excludes (globs, iglobs, git-ignore, exclude-if-present), tags and label, schedule, retry policy, retention, hooks and repository. Also "Import rustic profile…" and "Export as rustic profile".
4. **Repositories.** Add or connect (local, SFTP, REST, S3, B2, rclone…), test the connection, init, stats (`infos_files`/`infos_index`), and request a maintenance owner and set the maintenance schedule. Shows the repository ID, the granted owner and any rejected claim. Testing opens the repository and reports its ID; a write-permission check is **not yet built** (it belongs with the maintenance-owner work).
5. **Snapshots.** Pick a repository, and its history is grouped by owner: a section for each plan of this agent (a table of its snapshots, newest first: the newest are listed and the rest counted; each time is the one the clock that took it read, with that clock's offset after it when the viewer's was at another then, §16 decision 56), then **Orphaned history** (snapshots tagged for an agent or a plan this configuration does not have) and **Unmanaged history** (snapshots no agent tagged). A group that a plan of this agent could take over has an **Adopt** button (§7.3); a group that none could take over says why: an orphaned group lacks the tag of an agent or a plan, or no plan of this agent could take it, and an unmanaged group has no plan that backs up the same host, label and paths. A repository no plan backs up to that holds nothing says that too. Above the history sit **Forget snapshots**, **Prune unused data** and **Check the repository**. Each of them, and each adoption, is first *reviewed* in a dialog that says what the run would do and names the snapshots it touches, and nothing changes until the review is confirmed. A repository this agent maintains that holds snapshots from other hosts (§3.1) says so before those buttons and in the review of a forget, an adoption or a prune, since another machine may maintain it too (§7.3). Filtering by host, label, tag, plan or path, a snapshot's detail with a tree browser (`ls`), and the two actions below are **not yet built**.
   - **Download** (**not yet built**) a file or directory (tar/zip, built from `ls` + `dump`). On the hub this uses the hub's own repo access and only works for hub-managed repos.
   - **Restore** (**not yet built**) follows §10.4: by default into a **new folder** (`~/ladderback-restore/<host>-<snapshot-short-id>-<timestamp>/`). Restoring over the original location is offered only in the agent's own UI, with its own confirmation.
6. **Operations.** A searchable history with full logs, warnings and a cancel button.
7. **Settings.** Auth, hub pairing, notifications, and the allowlist of folders a dry run may read (§16, decision 89).
8. **Pending changes.** Proposals waiting for a person, with a count in the navigation that is part of the link's accessible name and reaches screen readers through the announcer (A2, A3): the summary Ladderback writes from the changes, the exact `config.toml` diff, the forget preview, any maintenance claim and each command with its own tick; approve with step-up, or reject with a reason per change (§16, decision 89).

Live updates come from one WebSocket per tab carrying `UiEvent` (operation started/progress/finished, agent online/offline). The page fetches initial state over REST. The daemon forwards an operation's warning events to subscribers unchanged, and its progress events as `LiveProgress` shows them (below): coalescing happens once, in the worker (§4.1), and the daemon never re-coalesces. Progress bars are stateful per key on the way out (`app::progress::LiveProgress`): a page is told of the bar the engine began last that is still open, with its **step** (§3.1), as `operation-progress` with `step`, `current`, `total` and `unit`, what the bar counts: `bytes`, or `count` for a counter or a spinner, and `count` when a daemon older than the field leaves it out (§16, decision 83) (`Begin` publishes 0, `Advance` adds, `Length` sets the total, a title names the step; a change to an older open bar, or a finished bar, publishes nothing), so a page sees current-of-total numbers of one step, not deltas. The engine adapter maps rustic's text for a bar to the step; the text never leaves it, and a text it doesn't know is no step (§16, decision 82). How an operation started and how it ended are not the worker's to announce but the run's that records them (decisions 41, 68). It publishes one `operation-started` once the log has the write that says the operation is running, with the log's start time, so a page that reads the history on hearing it finds the run there; a maintenance run, whose `start` already wrote it running, publishes it once as it begins its jobs, however many it takes. It publishes one `operation-succeeded` or `operation-failed` after its last write to the operation log, from the operation as it ended and after its ending hooks have run, so a page that reads the history on hearing it finds the end there. A write the log refused, or gave up on after `SAVE_BOUND` (§9), does not hold either announcement back: the history then shows the operation as the log last had it, and the run's `Finished::recording_errors` holds the write. A cancelled operation announces no end, and one cancelled before the log had it running announces no start either; a run of several engine jobs announces once. A job that is no operation (the repository's ID, a snapshot list, the groups, a preview, initialising a repository) publishes nothing at all, no start, end, progress or warning (#308): the history has no row for it, and a run that reads first keeps none of what its read said. The events WebSocket answers a client's ping with a pong, so a live page survives an idle network.

**Settled in the live-pages build** (`crates/web/src/backend.rs`, `ws.rs`, `routes.rs`):

- **State model.** Each live page holds its state in one `RwSignal`. The operations page's is `OperationsState`: the history rows (newest first) plus the live progress of a run still going. The initial REST fetch builds it; every `UiEvent` is applied to it by a pure function (`apply`) in the host-tested module, so a missed event cannot be represented wrongly; an event about an operation the state doesn't hold is ignored — the reconnect's re-fetch brings the whole story, never a half-invented row. Nor does an event take a row back, whatever order it and a read of the history arrive in: a start moves only a queued row, and progress and warnings reach only a row that has not ended. A run that warned on its way to the end becomes `succeeded-with-warnings`, not a plain success. A `failed` event keeps its typed code for rendering through the catalog.
- **Reconnect and merging.** The socket dropping is a failure like any other: after `reconnect_backoff(attempt)` (doubling from 1 s, capped at 30 s) the loop re-fetches the whole history and resumes the stream; a fetch that fails leaves the page in `Phase::Unreachable` and the loop keeps trying, so a daemon that comes back is a page that heals. Each stream that opens, the first and every reconnect's, reads the history once more (decision 68): the page hears nothing told before its stream opened, such as the start of a run its first read had queued (#305). The first read does not wait for the stream, and events heard while the later one is out are applied as they come. The re-fetched page is `merge`d: the store's page is the truth for what it holds, but a status an event advanced is never regressed (the store can answer with what it held before news the stream has told since, and an end event can beat it when the log lost its final write), and a live row the page doesn't hold yet stays, newest — dropping it would unshow a run the reader is watching. At the stage the page's row already has, a run still going keeps its status, start and progress as the events left them and gains the warning codes the store has and the row lacks: mid-run, that is a before-hook's warning (#328) or a secret file other users can read that the run's start met (#386), which no event tells and the run's start write puts in the store; a run's other warnings reach the store only with its end. A row the read moves on, from queued to running or from running to ended, takes the store's row and keeps each warning code the page heard that the store lacks. A row names each code once, as the history does (#508), so a code is added only when the row lacks it: the store's first, in the order the first warning of each was recorded, and those only the events told after them. A run that ended takes the store's end whole, which has every warning (so `succeeded-with-warnings` where the end event left `succeeded`) and the result an end event doesn't carry; the status's change is no second end, so nothing more is announced.
- **Settle-poll.** A start announces "Backup started." at once, then polls the history until the operation ends (120 s, every 250 ms), merging each page: the first `UiEvent` may lose the race with the announcement, and a cancelled run emits no `UiEvent` at all. A cancel does the same, without an announcement of its own. A poll that runs out of its budget without an end says so politely ("Still waiting for Ladderback to say how the run ended."), so a reader is never left watching a row that quietly stopped moving; the connection's own loop keeps the page healing behind it.
- **Leaving the page (#300).** The connection, its reconnects and re-reads, and every settle-poll last as long as the reader's visit to the page and no longer: the page begins a `visit::Visit` as it is built and ends it as it goes (Leptos's `on_cleanup`), and each of those tasks runs through `Visit::during`, which ends it at its next await, whether it is waiting on the stream, on a read, or out a back-off or a poll's pause. The task is dropped there, and the events stream it holds closes with it; a task the end finds ready to go on goes no further, so nothing is applied to a page that is gone, and a settle-poll that ends this way says nothing. Coming back builds the page again, with one stream of its own. A pause is the page's too, and ends with it (§4.5, "Live updates").
- **Announcements.** The end of a run (finished, cancelled, failed — failed assertively) is announced from a status-transition effect over the state, not from the code path that happened to see it, so the events stream and the settle-poll both arrive at exactly one announcement. It names the kind of run that ended ("Check finished.", "Backup finished."), so a check's end is never told as a backup's.
- **Rows (#192).** The first column is Operation, and each of its cells is its row's header (`<th scope="row">`): a backup is named by its plan, a maintenance run by what ran and the alias of its repository ("Check of demo"), or by what ran alone when the log kept no alias. The Result column, before Actions, lists what a succeeded run produced (a backup's short snapshot ID, its files, the source it went through, what it added and how long it took; a check's findings; the count a forget, a prune or an adoption reached) and, for a failed run, says first why it failed: its `failure` in the catalog's words, the engine's own marked as English (`lang="en"`, WCAG 3.1.2), as the alert of a refusal says them (#474). It is empty for any other row. One item alone, such as a failed run's reason with nothing after it, is said as a sentence, and two or more as a list, one an item (`Said` in `operations.rs`): a list of one is heard as a list and draws a marker that sets nothing apart (#430). A placeable in an item (a path, an address, a snapshot's ID: `runs` in `repositories.rs` finds each between the catalog's isolation marks) is a `.placeable`, an inline block that moves to the next line whole rather than breaking where a line runs out ("home-" / "laptop.password"), and breaks inside only when it is wider than the cell, then first after a separator (`address_parts`, a `<wbr>` after each part). The table takes its name from the page's heading (`aria-labelledby` the `<h1>`, whose `id` is `page-heading` on every page), not from a caption that said "Operations" again under the heading (#431). A run whose choice used one of several locations says so after that, whatever became of the run, a failed one included: "Used location 2 of 2: rest:https://backup.example.net/laptop", the address as the run recorded it with credentials masked (decision 80; the earlier locations and their outcomes are in the summary's `locations`, which no page shows until an operation detail view exists). Each Cancel button names the run it stops. A backup the schedule started that was refused before it ran (§5) is a failed row like any other: its Started cell is the moment it was refused, the time it was queued, as it never started, and its Result says why as the refusal of a run by hand does: the refusal's code, its arguments, and what a platform or a command said as the detail, masked of the repository's secrets (I4).
- **Re-read on an end.** An end event carries no result, and the run tells of its end only after its last write to the log, so the page reads the history again when an end arrives (`backend::asks_for_a_reread`) and merges it, and the row's Result shows without a reload; a run started elsewhere, which the page did not hold, comes in with it. One re-read is out at a time (`backend::Rereads`), across the stream's reconnects too, and the read a stream's opening asks for is one of them: ends and openings that arrive while one is out are owed one more after it, and only one, so no run of reconnects has more than two reads waiting. A re-read that gets no history (a refusal, no answer, or none within `backend::REREAD_PATIENCE`, 10 s, after which its fetch is aborted) is tried again after 1, 2 and 4 s, and then left to the next end or the next reconnect's re-fetch. Its `@ui` journeys play the daemon, so an end reaches the page after the page is listening, one holds a re-read's answer back while the stream drops and another run ends, and one holds the stream's opening back while a run starts.
- **Sort.** The history arrives newest first; that is the default. The sort button cycles newest → oldest → newest, and each press is announced politely. A first press announces *newest first*, because the page's default is the daemon's order, not the button's. The Started cell carries the raw RFC 3339 instant in its `title`, so the order is testable without the locale's text; the visible text is `DATETIME($when)` through the catalog (`ui-instant`).
- **Starting a plan.** The page has a start button for each plan, named with its plan ("Start backup of demo-home", one message with the plan as its argument), as a row's Cancel is ("Cancel demo-home"). A row's Cancel shows "Cancel" alone (`ui-cancel`), the word its name begins with (2.5.3), so it takes one line in the 8rem Actions column at 1280 px (#430). A reader tabbing through the plans hears which one each button runs (2.4.6, 4.1.2), and the visible label is the name (2.5.3). The buttons are one row of actions (`.actions`, drawn only when there is a plan), so each stands apart from the next by the row's gap rather than touching it, and on a small screen with larger text they wrap one under the other (#284).
- **Stable table and rows (#124).** The table is built once, and its rows follow the state in place, so an update to a row never replaces a control a reader has focused (2.4.3). What the page shows (loading, unreachable, empty or the table) and the ids of the rows in the order the sort gives are memos: only a change of those rebuilds the table, and a progress report, a start or an end changes neither. A row is keyed by its operation's id and reads each fact it shows through a memo of its own (status, started instant, progress), so an update reaches only the cells it is about; the Cancel button and the progress bar are present or absent by a memo of a boolean, and an ended run loses its button because it is no longer a control. The sort order and the header's `aria-sort` follow the sort signal, so a press is answered by the table itself and not by the next update. `StatusBadge` and `Progress` take signals for this. The decisions (`shown`, `ordered`, `progress::percent`, `badge_of`, `OperationsState::row`) are pure and host-tested. **Known limit:** a row that changes place (runs joining the history, a sorted view where a run's order changes) is moved in the table, not built again, and keeps its state; a move may still cost a control in that row its focus, and no journey covers a move.
- **Stable columns (#194).** The table's columns have fixed widths (`table.operations` in `style.css`, `table-layout: fixed`), so a run that starts, shows its progress and ends changes what its row says, not where the columns are. An automatic table resized every column whenever one cell's content did, and the table jumped as a run started and ended. Where the table has at least 48rem (a container query on `.table-frame`, the `<div>` around it: a query on the table itself left its columns as they were), each column but Result is as wide as what it holds needs, in rem so it grows with the text (Operation, Status and Actions 8rem, Started 11rem), and Result takes the rest: 368 px of 928 at 1280 px, where shares gave it 18 % beside an empty Actions column and a finished backup's facts broke inside ("Snapshot" / "ba5cc73e", #430). Below that, as at 320 px or with 200 % text on a laptop (the query's rem is the reader's text size), the columns keep fixed shares: Operation 20 %, Status 19 %, Started 22 %, Result 18 %, Actions 21 %. The progress bar fills its cell, up to 16rem, rather than setting the cell's width, so a running row neither widens Status nor makes the page scroll sideways at 320 px. The sort button follows the Started header's text in a `.sort-header` that wraps: a gap apart on one line when the column has room, below the text when it hasn't, never touching or over it (the gallery's `SortableTable` lays its header out the same way). A word breaks inside only when it is wider than its column, as on a small screen or with 200 % text. A fixed column can't grow to hold its content, so what doesn't fit would run over the next column: the space around the text in this table (a cell's padding and a badge's, `min(0.5rem, 1.25vw)`, and a button's, `min(0.375rem, 1.25vw)`, the browser's own 6 px on a wide screen) follows the screen's width rather than the text's size, and a Result list's markers sit inside its items (`list-style-position: inside`, no indent), so at 320 px with 200 % text every column still holds one letter of the largest text and nothing leaves its cell. Not every word fits whole at 320 px: the headers and a row's longest words need about 350 px beside one another, and the table has 248 px of text room, so the shares favour the operation's name, the sort button and the Cancel button's label.
- **Unreachable and loading.** `Phase::Unreachable` replaces the page's `<h1>` with "Cannot reach Ladderback" (the page is already open in the browser the daemon served, so this is a state of the page, not a navigation). `Phase::Loading` shows "Loading…" until the first answer arrives; the `@ui` loading scenario covers it by delaying every `/api/v1/` answer (the world's `answerDelayMs`, set by a Given that names the seconds), and that scenario is the phase-2 guard-class addition §13 asks for.
- **Journey fixtures.** The `@ui` Givens write a config.toml with one demo plan (two, backing up the same source, where a journey tells plans apart) and a scratch copy of the `demo-repo` fixture repository into the daemon's config dir. Each source file's content is unique to its number, so the repository cannot collapse the backup into one deduplicated chunk and end before the journey can watch it: `small` (10 000 × 2 KiB, about two seconds) ends a run after its Running row has been there to read; `big` (50 000 × 2 KiB, about ten) outlives a cancel or a mid-run reload. Demo data appears only where the daemon isn't the source (loading, empty states); no operation row is ever hardcoded.
- **Scripted daemon.** A journey that must watch a control while updates arrive plays the daemon itself (`ui-tests/support/scripted-daemon.ts`): the history, the plans and the events stream answer as the steps say, so each update reaches the page when a step sends it and the result does not depend on how fast a real backup reports. It counts the events streams the page has open and has opened, and its reads of the history, so a journey can tell that a page the reader left stops listening. Only the daemon's answers are played: the page is the real one, and a request the script doesn't answer (a start or a cancel, unless a step has the script queue the backup or accept the cancel itself) goes on to the run's daemon.

**Settled in the repositories-page build** (`crates/web/src/repositories.rs` for the decisions, `routes.rs`, `components.rs` and `main.rs` for the glue):

- **Navigation.** The header carries a `<nav aria-label>` with a link to each page (Operations, Snapshots, Repositories), the current one marked `aria-current="page"` and bold. The router wraps the header and `<main>`, so a link is a route change like any other: the title changes and focus moves to the new `<h1>`. A page's stops therefore begin with the skip link and three links, and an `@ui` scenario that counts Tabs counts them.
- **Version (#502, #516).** After the navigation, at the header's right, the running build in muted text ("Version 0.3.0", or "Version 0.3.0+3f937cf" between releases; `ui-version`, the build a placeable): the build the daemon tells the page in its session answer (`GET /api/v1/session`, and a sign-in's answer), shown as `BuildDto::display` says (decision 90). It is plain text, not a tab stop, and wraps under the navigation on a narrow screen. It is shown only with the navigation (signed in, sign-in off, or a session the page couldn't read), never on the sign-in page, which shows only what signing in needs, and only once the daemon has told it: a page whose session read failed shows no version rather than a guess. The daemon tells the build only to a page that may see the pages (sign-in off, or a live session), so a page yet to sign in learns neither the commit nor whether the build had changes; the version alone is no secret (the UI's public wasm carries it, as `PLAN_FORMAT_URL` does). The header names the build the daemon runs, as it last told the page: after an update and a restart, a tab left open keeps the old page's code until it is reloaded, while its header may name the new build once the daemon tells it again (a sign-in, or a session read). Telling such a page to reload is #531.
- **The page.** The list is a real table (`Name` as the row header, `Location` with the hot half on its own line, `Password`, `Actions`), named by the page's heading as the Operations table is (#431), then the form. The list is loading ("Loading…"), empty ("No repositories yet.") or the table; a daemon that cannot be reached says so in the heading, like the other live pages, and a later answer to a request heals the page. A row says where the password comes from ("Kept in the configuration file", "Read from the file …") and never shows one. The `Location` cell of a repository reached at several locations is a list named "Locations of nas" (decision 80), one item per location in the order a job tries them: "Location 1, tried first", "Location 2" and so on, its address masked, and each option by name, with its value only when it is references alone ("The option key in options comes from ${LAN_KEY}.", else "… is written in the configuration file and not shown."). Such a row has a button in `Actions` that shows **Test** and is named **Test the locations of nas** (`aria-label`; the name begins with the visible text, WCAG 2.5.3), so it takes one line beside the addresses (#482); it posts `POST /api/v1/repositories/{alias}/test` with `{}` and writes each location's outcome under it in the list ("Answers and holds the repository.", "Did not answer.", "Answers, but holds another repository. Check its address.", with where a secret was looked for when one could not be read). While it runs the button says so politely and ignores a second press without being disabled, so focus stays on it; the answer is announced politely ("Tested nas: 1 of its 2 locations answers and holds the repository."), and a refusal is the row's alert, as Create's is. A row of one location has no such button: the form's **Test the repository** tests a location before it is saved, and the route serves one-location entries for other clients.
- **Creating from a row.** A row the daemon marks `create-offered` (decision 53: its entry records no repository ID, its newest operation found no repository there, and none of them ever succeeded; a row with nothing on record yet is not marked, so an imported profile's repository is offered once its first backup finds its folder empty) has a button in `Actions` named after its row (**Create demo**) that posts `POST /api/v1/repositories/{alias}/init`: the repository is created where its entry says, once the engine finds a folder there that holds nothing of a repository (decision 53 §7), with the password reference the entry already names, so an imported profile's repository needs nothing typed; the entry records the new repository's ID, and the rest of it, `maintenance` included, is left as it was. A created repository is said below the list, and the list is read again: the row offers Create no more, since its entry records the ID, so its button goes. Focus moves to the short confirmation, "Created demo." (a `<p tabindex="-1">`), where a screen reader reads it, so the announcer stays silent, as on a route change; the ID follows in a sentence of its own ("Its ID is …"), outside the focused element, so a screen reader doesn't spell out 64 hex digits unasked. The confirmation stays until a row's Create or one of the form's buttons is pressed again. A refusal is a `<p role="alert">` in the row ("There is already a repository at the location of demo, so nothing was created.", or the daemon's sentence for any other); the list isn't read again, so the row and its button stay and focus stays on the button. A second press is ignored from the first until the answer is a refusal, or, once the repository is created, until the list is read again and the button goes with its row; a second Create from a page that wasn't read again is refused as a repository already there.
- **Wrapping in the table.** The body lets any word break anywhere (`overflow-wrap: anywhere`), so a long path never widens a page past a small screen, but an automatic table then counts a short name's narrowest as one letter, and beside the long paths it squeezed the names, the `Name` header and the Create button to a letter or two a line ("de/m/o"). Only in the Repositories table (`table.repositories`, these rules scoped to it) the location and the password's source have widths of their own (`td.location`, `td.password`, #482), so the columns beside them get their whole width when the screen has room. With at least 26rem of room (a container query on `.table-frame`, the `<div>` around the table), the Location column is as wide as its widest address needs (an `.address` box is `max-content` wide), up to the room that leaves the other columns 30rem and never less than 6rem, and Password, which has the most to say, takes what the others leave. Location is exactly as wide as its widest address, up to that cap (`td.location` is `inline-size: 0`, so only the address boxes size it): a Test's results, an option or a rule line under an address never widen it, so the columns don't move when results arrive, and each address box fills its line (`min-inline-size: 100%`), so a part narrower than the column stays whole. Above 26rem a column header keeps its words whole (`overflow-wrap: normal`): Actions, as narrow as its Test button, broke "Actio" / "ns". Fixed shares missed both ways: at 35 % each the address broke at 1280 px beside a Password column with room to spare, and at 55 % and 20 % Location was half empty while a password warning took fifteen lines and the password file's path broke inside a word. Below 26rem, as at 320 px, Location takes 55 % and Password 20 %, which keeps each part of an address whole. Everywhere, a row's name and a button's label keep a floor of `min(12ch, 35vw - 2rem)`: a short one is never squeezed, and a long one breaks at a space or a hyphen first and inside a word only past the floor, so even a 64-letter name with no hyphen fits 320 px (1.4.10). The floor is at most 35 % of the screen's width less 2rem, so it gives way as the text grows: at 320 px and 200 % text the four columns' padding alone takes 128 of the 256 px the table has, so no `ch` floor can hold there (a plain `10ch` overflowed the screen by 144 px), and the table still fits. The cells' padding follows the screen's width, `min(0.5rem, 1.25vw)`, as in the Operations table, and a list in a cell has a 1.25rem indent rather than the browser's 40 px, so at 320 px the address has room for each of its parts. An address breaks only after a separator (`address_parts`: a `<wbr>` after a slash, a dot, an at sign or a colon that a letter follows) and inside a part only when that part is longer than a line, as at 320 px with 200 % text. A path in the Password column, such as the file a password is read from, and any placeable in a location's hot half, options and Test results, is a `.placeable` (`runs_view`), kept whole as in the Operations table's Result. The row's Test button shows one word whole (`.whole-words`, `overflow-wrap: normal`, no floor), so it takes one line beside the addresses. The other tables keep the body's rule.
- **The form.** `Name`, `Location`, `Hot storage (optional)` and `Password` (`type="password"`), then the **Maintain this repository from this agent** checkbox (`Checkbox`, off by default), then three buttons. **Test the repository** is the form's submit, so Enter in a field tests; **Connect the repository** and **Create the repository** are buttons. Every field has a visible label and a hint wired through `aria-describedby`; `FormField` takes its `id`, its `value` signal and its input `type`. Spaces around a name or a location are not part of it; a password is taken as typed. A repository is connected under a name; creating needs none, and then the repository is not saved. The checkbox decides who maintains a connected repository (decision 48): on, this agent (`maintenance = "local"`); off, nobody from here, for another agent or the hub may already maintain it and only one place may (I1). Its hint says so. A repository created here is maintained here whatever the checkbox says, since nothing else can know it yet. A repository saved before this choice existed has no `maintenance` and is not maintained here until `maintenance = "local"` is added to its configuration; the Snapshots page says how.
- **Errors.** A form missing what its button needs, and any refusal, move focus to an error summary: an `<h2 tabindex="-1">` ("There is 1 problem with the form") over a list of the problems. A problem about a field links to it, the link moves focus itself (the router would take the click and only scroll), and the field shows the same text with `aria-invalid`; a refusal about the repository (it would not open, it exists already) has no field and is plain text. The engine's own words in a sentence are in a `<span lang="en">` (3.1.2), and a repository that would not open is followed by the page's own advice. The summary is not a live region: focus tells the reader.
- **Results.** A test, a connection and a creation say what happened in the page ("The repository opens. Its ID is …") and politely through the announcer, without the ID, a long run of digits a screen reader would spell out. A request that takes the engine a moment says so, and a second press while it runs is ignored.
- **What stays in the fields.** A failure keeps everything typed, the password included, so nothing is typed twice (3.3.7). A test keeps it too, since the next step is to connect. A saved repository, connected or created under a name, clears the form, turns the checkbox off again and reads the list again. The password is never shown after it is typed (I4): the field is a password field, the value lives only in the page's signal, and nothing the page shows or announces is built from it.
- **Where a typed password goes.** The daemon saves it inline in `config.toml`, written 0600, and so it is in the copies of earlier versions of the file that a save keeps in `history/` (ten at most, also 0600, §6.1). The config folder is 0700 when the daemon creates it and is left as it was when it exists. There is no keyring write for a typed password yet, and the hint beside the field says where it goes.
- **Left out, on purpose.** The `command` password source (see the API above); editing a backend's options (the API accepts them, the form does not); a typed engine failure for no repository at a REST, rclone or remote OpenDAL location, which can't be told there from one that is out of reach (decision 53: only an empty local or OpenDAL `fs` folder fails `repository-not-found`); the repository's stats and maintenance schedule, asking for the hub as maintenance owner, changing who maintains a saved repository, and the write-permission check (later milestones).
- **Contrast.** The form error's color on the page background, links on the surface and page backgrounds, and the table's rule are pair-checked by `just test-contrast` along with the badge pairs.

**Settled in the maintenance build** (`crates/web/src/maintenance.rs` and `wording.rs` for the decisions, `snapshots.rs`, `components.rs` and `ws.rs` for the glue):

- **Where it lives.** Every decision is in a host-tested module. `maintenance.rs` holds the requests, the review a preview becomes, the sizes of the lists (`Rows`), what the page shows of a history (`shown`), the panel of a run (`Panel`: what the page asks, shows, says and does next, as a state machine over what happens to it) and the wait for a run (`Watch`, `poll_delay`). `wording.rs` turns each into the catalog's messages: one message for each caption or label, with the names, counts and kinds passed as raw arguments and chosen by the catalog's selects and plurals, never joined or inflected in code. `snapshots.rs` only draws what they decide and sends what they ask; it is left out of mutation testing, and `.cargo/mutants.toml` says exactly what stays in it.
- **The history.** It shows "Loading…" until the first answer. A repository that holds nothing says so ("No snapshots yet."), and a forget of a repository no plan backs up to opens a review that says why it has nothing to do, with a Close button and nothing to confirm. Picking the repository that is already shown reads its history again without building the page anew, so a run on the page stays on it, and the page's heading recovers when a later answer succeeds after one that failed.
- **The review.** An adoption, a forget, a prune and a check each ask the daemon for a preview first. The review is its answer: what the run would do, the snapshots it names, what it leaves alone, what it warns of (the other hosts of §7.3) and the selection that confirming sends back. A warning is part of what the dialog is described by, after the facts, so a screen reader reads it on entry. A refusal of the preview is an alert in the page, in the page's language, with the engine's own words in a `<span lang="en">` (3.1.2). The run is started with the selection the preview named, so what was reviewed is what runs.
- **Every wait is told.** The request of a preview says "Preparing the review…" (polite). Starting a run says "Starting the forget…" in the page and in the dialog; the dialog holds still while it does (see the review dialog under the component build), and the announcer holds its messages while a modal is open, so a polite region inside the dialog says it too. A run that is going says "A forget is running." (polite), and its end says how it ended (a failure assertively) and has the page read the history again. The wait polls the run every 250 ms for twenty reads, every second up to the eightieth, then every five seconds, and gives up after seven failed reads in a row; it then says the page stopped watching, that the run goes on and that the Operations page shows how it ends, never "still waiting" and silence. The end of the last run is cleared once another review is asked for.
- **Focus.** Closing a review returns focus to the control that asked for it; when that control has gone with the run (an adopted group's button goes with the group), focus goes to the maintenance heading. It never falls to `<body>`.
- **Journeys.** The `@ui` scenarios use the keyboard alone. `the daemon's answers to the UI are delayed by N seconds` holds every `/api/v1/` answer, so the waits above are long enough to read and to act within; `the repository has been removed` makes the history's read refuse with the engine's words, and `the config names no plan` leaves a repository no plan backs up to. The count of rows reads the history again before it counts, so a table the page left stale cannot pass. Unmanaged groups and the cancelling of a running maintenance are covered by host tests only. Instants in the new tables go through `routes::instant`, which writes UTC as the Operations page does.
- **Small screens and other languages.** The tables of snapshots have two columns in fixed shares of the width (45 % for the ID), so at 320 px a header and an ID stay whole while there is room and break only where a share is too narrow, as they do at 200 % text. They never scroll, so none takes a tab stop of its own. The journeys pin the page and the review of a forget at 320 × 256 (a table's words whole, nothing scrolls sideways or is clipped, no accessibility violations), at 200 % text with wider spacing, and under `en-XA` and `ar-XB`, where the IDs and instants in the tables, the paths of a list and the engine's own words (`lang="en"`) are data and stay as they are; the check that every visible text is transformed exempts nothing on the pages that show no data.

### 4.5 Accessibility

Accessibility is designed in from the first screen, not audited in at the end. The target is WCAG 2.2 AA (A1–A6, §0).

**Supported assistive technologies** follow the supported platforms:

- Orca with Firefox on Linux;
- VoiceOver with Safari on macOS;
- keyboard-only use in any current browser. Safari reaches links and buttons with Tab only when "Press Tab to highlight each item" is on, or with Option+Tab; the manual pass uses that setting.

**Structure.**

- **Native HTML first:** `<button>`, `<a>`, `<table>` with `<th scope>`, `<dialog>` opened with `showModal()`, `<details>`, `<time datetime>`. ARIA only where no native element exists, and then following the WAI-ARIA Authoring Practices pattern for that widget. The progress bar is the one exception: a `role="progressbar"`, because a native `<progress>` draws the value it exposes, which is throttled, and can hold neither the step nor the text the bar shows (§16, decision 83).
- **Page skeleton:** landmarks (`header`, `nav`, `main`), exactly one `<h1>`, descriptive headings and labels with no skipped levels (2.4.6), and a "Skip to content" link. Text in another language, such as rustic's verbatim English messages, carries its own `lang` (3.1.2).
- **Route changes** (path navigation): the router updates `document.title` (page, then machine, then "Ladderback") and moves focus to the new page's `<h1>` (`tabindex="-1"`). Screen readers read the focused heading, so the announcer stays silent. Changing filters, sorting or pages updates the URL query without moving focus.
- **Pointer targets:** at least 24 × 24 CSS px (2.5.8). Nothing needs dragging (2.5.7) or works only on hover.
- **Tooltips and popovers** can be dismissed with Escape, stay open while hovered, and stay until dismissed (1.4.13). The `title` attribute never carries information on its own.
- **Sessions** end after **12 hours unused** and after **30 days** however much they are used (§10.1). Only what the reader does counts as use: what the page reads on its own, and its events stream, never keep a session alive. **Two minutes before** a session would end unused, the page warns in a dialog that takes focus on its one button, "Stay signed in", which keeps the session; Escape keeps it too, and closing it returns focus to where it was (2.2.1 Timing Adjustable; two minutes leaves a screen reader or a switch user ample time over the 20 seconds 2.2.1 asks for). The 30-day end is not warned of: 2.2.1's 20-hour exception covers it, and the warning is skipped when the lifetime ends the session first. Expiry never discards unsaved form input: a "Sign in again" dialog opens over the page, which stays as it was, and the request the daemon refused is sent again once signed in. The sign-in form is one "Admin password" field with `autocomplete="current-password"` (paste and password managers work, A5, A6) and the form's error summary; while signed in, the navigation ends with "Sign out".

**The shared component set** in `web` is the only place widgets are built. Each component has an accessibility contract and tests for it:

| Component | Contract |
|---|---|
| Dialog (confirmations, step-up confirmation) | Native modal `<dialog>`. Focus moves in, the background is inert, Escape cancels, and focus returns to the control that opened it. A destructive button is never the default. Errors inside the dialog, such as a wrong password, use a `role="alert"` inside it |
| Review dialog (a run reviewed before it starts) | The Dialog contract, and more. It is named by its title and described by what the run would do, so a screen reader reads both on entry. Focus starts on its first button, **Cancel** (**Close** when the run would do nothing), so a stray Enter backs out and never confirms; the confirm button is named for what it commits to ("Forget 2 snapshots"). While the run is being started its buttons say they are unavailable (`aria-disabled`, still reachable by Tab so focus never falls), Escape does not dismiss it, and a polite live region inside it says "Starting the forget…", because the announcer holds its messages while a modal is open |
| Data table (snapshots, operations, history) | A real `<table>`. Sortable headers are buttons with `aria-sort`. Row actions are named with their row ("Restore snapshot 3f2a…"). The new page and row count are announced |
| Tree (snapshot browser, M3) | WAI-ARIA tree pattern: one tab stop with roving `tabindex`; arrow keys (Left and Right swap in right-to-left layouts), Home and End, type-ahead; `aria-expanded`, `aria-level`, `aria-setsize` and `aria-posinset` for lazily loaded children; `aria-busy` while a folder loads. Download and Restore for the selected node sit in a details pane next to the tree, reached with Tab. If M3's VoiceOver pass shows the tree is unusable there, the fallback is a nested list of disclosures |
| Status badge | An icon with a distinct shape per state, visible text, and color. Never color alone (A2) |
| Progress | A focusable `role="progressbar"` (`tabindex="0"`) named for what it measures and for its run, as its row and its Cancel button are, so two running backups' bars are told apart (WCAG 2.4.6): "Backup progress of home" by its plan (`ui-plan-progress`), "Check progress of demo" by what runs and its repository's alias (`ui-operation-progress-of`), and "Check progress" alone for a run the log names neither for (`ui-operation-progress`; "Operation progress" for a kind the page doesn't know), which holds everything it draws, so its focus ring surrounds what a sighted reader sees and a screen reader hears its value text alone. The fill and the visible text follow every report, and the fill moves smoothly. The value it tells, `aria-valuenow` and `aria-valuetext` (`ui-progress-value`: the step, the percentage, the amounts as sizes when the bar counts bytes, and the time left, as in "Backing up… 42%, 3.1 GiB of 7.4 GiB, about 6 minutes left"), changes at once for the first report, a new step, a total learnt or lost and the total reached, and otherwise at most every 30 s, the latest report told when the 30 s are over: screen readers speak value changes themselves, so the exposed value is throttled. The time left is measured from the first report of the step and total, and told once that measure has run 30 s and done 1 % of the total. A total not known yet (a backup before rustic has walked its whole source) or of zero is indeterminate: no `aria-valuenow` and no track, and in place of the percentage the text says the operation is working, never 0 % (#422). On the Operations page that text is the step the run is in (`ui-step-<code>`), or `ui-progress-working` for none; while the bar shows a percentage, the step's message stands above it. A bar that goes while it holds focus, as it does when its run ends, hands focus to the element its `then_focus` names, on the Operations page its row's header (`tabindex="-1"`: a script's target, no tab stop), so focus never falls to the page (WCAG 2.4.3) (§16, decisions 82, 83) |
| Form field | Visible `<label>`; hint and error linked with `aria-describedby`; `aria-invalid` on error; `autocomplete` tokens where a field has a known purpose (1.3.5), and `off` where its caller names none. On a failed submit, focus moves to an error summary (a heading with `tabindex="-1"`) that names each problem and links to its field. Errors say what is wrong and how to fix it (3.3.1, 3.3.3). Validation never interrupts typing |
| Tabs, menus, disclosures | Their WAI-ARIA patterns, or native `<details>` where it suffices |
| Toast | Spoken through the announcer and never steals focus. Never the only place a failure appears: failures also stay on the page |
| Pause control (a page that follows the daemon live) | A toggle `<button aria-pressed>` whose name stays the same pressed or not. While it is pressed, the page holds still and a banner beside it, not a live region, describes it (`aria-describedby`) and counts the changes waiting. Focus never moves. Pressing it again shows every change at once, and the announcer says once what changed |

**Live updates (A3).** `UiEvent`s update the page visually, but only the **announcer** talks to screen readers.

- **Two regions:** a polite `role="status"` and an assertive `role="alert"`. Both sit in the static `index.html`, outside the Leptos mount point, empty and never `display: none`, so they exist before anything is written to them.
- **Polite:** an operation finished, an agent came back. **Assertive:** only a failure that needs the user now, such as a failed restore.
- **Writing:** each message clears the region and sets the text on the next tick, so a repeated message is announced again.
- **Bursts are merged:** the same message within 2 s is said once, and ten agents changing at once become one summary ("3 backups finished, 1 failed").
- **Modal dialogs** make the rest of the page inert, including the regions. While one is open, announcements queue and are spoken when it closes.
- **Progress** is never written to a region. The start and the finish are announced.
- **Focus survives an update (2.4.3).** An update to a row changes text, values and the presence of what it is about; it never rebuilds a control the reader may be on. A control goes only when it stops being one, as a Cancel button does when its run ends. A row's Cancel button or progress bar that goes while it holds focus, its row staying, hands focus to the row's header, which names the run (`components::hand_focus_when_gone`; #438, and for the bar the Progress row above), and the run's end is announced as any other. A row that leaves the page, or a table built again (a change of what the page shows), takes the header with it, and focus then falls to the page.
- **Pause:** the Operations page, the one page that follows the daemon live, has a "Pause live updates" control (2.2.2). While paused, the page stops changing and a banner counts pending changes; the announcer holds what happens by itself and still answers what the reader does. Resuming shows every change at once and says once how many runs ended (decision 65).

**Settled in the first build** (`crates/web/src/announcer.rs` for the timing, `live.rs` for the regions):

- **Where it lives:** the timing is pure logic over an injected clock in a module of the `web` binary, so `cargo nextest run -p web` runs its tests on the host; the glue that writes the regions and owns the one timer is `live.rs`. The regions in `index.html` carry `role`, `aria-live` and `aria-atomic="true"`, are visually hidden with a class and never `display: none`, and the app mounts into `#app` beside them.
- **Merge window:** 2 s, from the first polite message, not the last, so a steady trickle cannot postpone the write for ever. The messages in it are joined with a space in arrival order (catalog messages are whole sentences) and a text already in the batch is said once. A page that wants a summary ("3 backups finished, 1 failed") builds it and sends it as one message; the announcer only merges. At most 16 messages are held for one write, so a modal left open cannot grow the queue without bound.
- **Write, clear, then set:** the region is cleared when the window closes and set 50 ms later. A message for a region that is still waiting to be set joins that set. Blank text and progress updates are ignored.
- **Modal dialogs:** opens are counted, so nested modals hold messages until the last one closes. Closing flushes everything held at once, without a new 2 s window, assertive first. A close with no modal open is ignored. A polite message sent inside an open window and held by a modal joins the same batch. A write already waiting for its tick when a modal opens is made after it closes. A page that unmounts a dialog while it is open (a route change) must tell the announcer it closed, because a removed `<dialog>` raises no `close` event.
- **Assertive messages wait for a modal too:** the design's "announcements queue" covers them, and it is the behaviour that works. A modal makes the rest of the page inert, and VoiceOver and JAWS say nothing for a live region in inert content (w3c/aria#1854), so an assertive message let through would be lost, and it is the urgent one. They skip the merge window; two for the same region that arrive within the 50 ms before the first is set, or while a modal is open, are joined into one set. The same limit of 16 holds per region. A failure that happens inside a dialog belongs in a `role="alert"` inside that dialog (the Dialog contract above), which needs no announcer. Moving the regions into the open dialog instead was left out: it needs a design change, and the real Dialog component is the place to revisit it.
- **Route changes:** `document.title` follows the path. An unknown path is the not-found page, with its own `<h1>`, and so is `/_gallery` in a build without the gallery. Each page's `<h1>` takes focus when it is shown after a navigation. The page load itself leaves focus at the top, where the skip link is.
- **The skip link handles its own activation:** its click handler moves focus to `<main>` and stops the click. Left alone, the router takes the click on `#main` and only scrolls to it, so focus stays where it was. The router ignores a click that something else has already stopped, so it needs no option, and the address and the history stay as they were (a `rel="external"` on the link, tried first, worked too, but called an in-page link external and left a `/#main` entry that Back had to step over).
- **The gallery** is the `gallery` feature of `web`: off by default and off in a release build, which `just architecture` checks. `just web-test` builds the UI with it, and `just test-ui` runs the scenarios against that build.

**Settled in the component build** (`crates/web/src/components.rs`, exercised by the gallery):

- **The first six components** are `ModalDialog` (native `<dialog>` + `showModal()`, focus wrapped from the last tab stop to the first and Shift-Tab from the first to the last by a keydown handler on the dialog, Escape and the Close button both closing, focus returning to the invoker, and opens counted by the announcer), `SortableTable` (a real `<table>` with a `<caption>`, `scope`d headers and a sort button whose result is announced politely), `FormField` (a `<label>`, a hint and an error wired through `aria-describedby`, `aria-invalid` on error), `StatusBadge` (visible text on a colored pill, never color alone), `Progress` (a focusable `role="progressbar"` with `aria-valuenow`/`aria-valuemin`/`aria-valuemax` and an `aria-valuetext` that says the step, the percentage, the amounts and the time left, told at most every 30 s while the step stays the same, never written to a live region; a reading without a total, or of zero, leaves out `aria-valuenow` and the track, and its value text and visible text are the step, or `ui-progress-working`, never 0 %; a count past its total is 100 %, never more) and `Toast` (rendered through the announcer, polite; it disappears without an announcement). Tabs, menus, disclosures and the tree stay for later milestones. Every gallery demo shows its loading, empty, error and success states where they apply, and the demo strings come from `ui.ftl`.
- **The review dialog** is `ReviewDialog` (`components.rs`), a seventh component on the same native `<dialog>`, with the same wrap of Tab from its last stop to its first and of Shift-Tab from its first to its last, and with opens counted by the announcer. It takes `working` (while the page starts the run: Confirm and the dismiss button carry `aria-disabled` and ignore clicks, Escape's `cancel` is prevented, and a paragraph with `aria-live="polite"` says what is going on) and `fallback` (where focus goes when the control that opened the dialog is gone). The paragraph is not `role="status"`, because the page keeps exactly one `status` region, the announcer's. Chromium may close the dialog on a second Escape in spite of the prevented `cancel`; the page keeps its own visible "Starting the forget…" line, so that is not silent.
- **The checkbox** is `Checkbox` (`components.rs`), an eighth component: a native `<input type="checkbox">` with its visible `<label>` beside it, which is also its click target, and an optional hint wired through `aria-describedby`. It takes its `id`, `label`, `description` and a `checked` signal the page reads and resets; Space turns it on and off, and the browser tells a screen reader its state, so nothing announces it. It is deliberately minimal: one size (the box never under 24px, the smallest target 2.5.8 allows), no color of its own (its meaning is in its words, 1.4.1), off and on only. A disabled, indeterminate, error or group state waits for a page that needs one. The gallery shows it off with a hint and on without one.
- **Form controls take the page's font.** A browser draws the text of a button, a field, a select and a text area in a font of its own, fixed in size (13.33 px in Chromium), whatever the page's text size: at 200 % text every button's label stayed at that size while the text around it doubled (1.4.4). `style.css` sets `font: inherit` on all four once, in its base rules, so a control's text has the size and face of the text around it, and what a control sizes in `em`, such as the checkbox's box, grows with it. `features/ui/components.feature` pins it at 200 % text on the gallery's buttons, and the gallery at 320 × 256 with that text: nothing scrolls sideways, nothing is clipped, no accessibility violations.
- **Badge tokens:** `style.css` carries `--badge-{loading,empty,error,success}-{fg,bg}` for both color schemes, each pill its text token on its background token. The weakest pair is error at 9.9:1; every pair clears 4.5:1 in both schemes.
- **Tailwind v4** rides trunk's pipeline: a `pre_build` hook in `crates/web/Trunk.toml` runs `@tailwindcss/cli` (pinned exactly at 4.1.0 — newer 4.1.x resolve an optional `oxide-wasm32-wasi` tarball this npm policy refuses) over `tailwind.css`, whose `@theme inline` maps the tokens of `style.css` as Tailwind colors, theme and utilities only, no preflight, so `style.css` stays the base stylesheet and the tokens stay the single source of truth. Its output `tw-out.css` is rebuilt on every build and not tracked (the root `.gitignore` names it), and `index.html` links both. Building the web UI needs Node.js and `npm`: before Tailwind runs, the hook's `scripts/web-packages.sh` stops the build with an error when `npm` is missing, and runs `npm ci` whenever `package-lock.json` differs from the copy the last successful install left in `node_modules`, so a pull that changes the lockfile also changes the installed packages; with the lockfile unchanged it needs no network. `crates/web/tests/trunk_hook.rs` runs the hook against a fake `npm`.
- **The contrast gate** (A4) is `just test-contrast`: `scripts/check-contrast.ts` reads the token pairs named in it from `style.css` — text and muted text on surface (4.5:1), the focus ring on surface (3:1), the eight badge pairs (4.5:1), and the pairs the repositories page adds: text, links and the form error on the page background and links on the surface (4.5:1), and the table rule on the page background (3:1), in both light and dark — and fails any pair under WCAG 2.2 AA. It needs only Node; `just verify` runs it, and CI runs it in the `Check` job.

**Settled in the pause build** (`crates/web/src/pause.rs` and `announcer.rs` for the decisions, `components.rs`, `live.rs` and `routes.rs` for the glue; decision 65):

- **The stream goes on; the page shows a copy.** `Pausable` holds the copy of the Operations page's state and connection phase taken at the press; every view of the page (the heading, which rows show and in what order, each row's cells) reads through it, so while paused no update reaches them. `ws::watch`, its reconnects, the settle-poll and the end announcements read the live state. The resume drops the copy, and the page shows the live state at once: nothing replayed, nothing lost, no row twice. A sort while paused orders the copy.
- **The banner** counts each row that will look different on the resume, one however many events changed it, plus one when the connection's phase changed (`OperationsState::changes_since`). It reads "Live updates are paused. 2 changes are waiting." and is a paragraph the button's `aria-describedby` points at, present only while paused. Its edge has the table rule's color (`--muted`), not the focus ring's, so beside the focused button it never reads as a second focus ring.
- **Two kinds of message.** `live::say` sends a `Kind::Event`, which waits while paused; `live::reply` sends a `Kind::Reply`, the page's answer to the reader's own press (a sort, a start, "Still waiting…" after a start or a cancel, a form's result, a toast), which is said as usual. The end of a run the reader cancelled is the answer to that press: the row's Cancel button marks the run, and its end is a reply, said while paused and not counted. The Snapshots page's maintenance panel still sends all it says as events: it has no pause, and it mixes answers with ends.
- **The announcer's pause and resume.** `pause` writes "Live updates are paused." at once, joined after anything still in its merge window, with no new window. `resume` writes the page's summary first, then the events that waited, then any reply still in its window, one write per region at once, assertive first, each region's queue deduplicated and bounded at 16. A pause sentence not yet written (a resume within its 50 ms, or behind a modal) is dropped, never said after the resume; joined after a write still to come, it alone leaves that write. Behind an open modal they wait for it to close, as every message does. A resume while not paused writes nothing.
- **The resume's sentence.** While paused, the page counts the runs whose status it sees go from queued or running to an end, and the failures among them (`Ends`), in place of announcing each (a run the reader cancelled is answered instead); the resume says them in one polite sentence ("… 3 runs ended while they were paused, and one of them failed."), "No run ended while they were paused." when none did.
- **The control** is `PauseUpdates` (`components.rs`), a ninth shared component: the button with its constant name and `aria-pressed`, and the banner. The page passes what pausing and resuming do to its own state; the component tells the announcer. Leaving the page ends the pause (`on_cleanup`), and nothing is stored, so a reload starts unpaused. It sits after the Operations page's opening paragraph, before the plans' Start buttons. The gallery's "Pause control" demo pauses a demo's own updates: "Finish a demo run" says "Backup finished." while it is not paused and counts the run while it is.

**Time, numbers and charts.**

- Relative times ("3 h ago") are always paired with the absolute time, both in `<time datetime>` and in the accessible name. Text inside a live region never ticks.
- Sizes and durations come from `l10n` (§8.4). Where an abbreviation reads badly aloud, the visible text is `aria-hidden` and a visually hidden spoken form, from the catalog's `.spoken` attribute, sits next to it. An accessible name always contains the visible label text (2.5.3).
- SVG charts (§8.1) have `role="img"`, a title and a one-sentence summary ("Snapshot size grew from 41 to 44 GiB over 30 days"). A "Show as table" toggle exposes the same numbers as a real table.

**Visual adaptation.**

- Light and dark themes follow `prefers-color-scheme`, with a manual override.
- `prefers-contrast: more` strengthens borders and focus rings, and `forced-colors: active` falls back to system colors without losing state.
- `prefers-reduced-motion` stops every animation and transition: the progress bar's fill then jumps to each value rather than moving to it. Nothing flashes.
- Text resizes to 200 % without loss, and pages reflow at 320 × 256 CSS px (A4).
- Color tokens live in one CSS file, and a test checks every foreground and background pair against A4's ratios. Once the visual `DESIGN.md` exists, `design.md lint` runs the same check on its tokens.

**Safe actions and authentication (A5).**

- Restore, in-place restore, adoption, forget and prune say what will happen before it happens and can be cancelled (3.3.4).
- Step-up confirmation (§10.4) allows paste and password managers (`autocomplete="current-password"`). The "type the snapshot short ID" check used when auth is off accepts paste, and the ID is shown as selectable text with a copy button, so it isn't a transcription test (3.3.8).
- A multi-step flow never asks again for something already entered (3.3.7).

**Beyond the web UI.**

- **Notifications:** every message has a plain-text form (email has a text part). Meaning never depends on color or emoji, and every message says what happened and what to do next.
- **CLI:** color is never the only signal, and `NO_COLOR` is honored. Spinners and redraws are off when output isn't a TTY, or with `--plain`. Every command that reports state has `--json`.
- **CLI output,** as built:
  - *Colour.* `--plain` is a global flag, taken before or after a command's name. It turns off the colour of the daemon's log and of `clap`'s help and usage errors. `clap` colours those while it parses, before the flag has a value, so the raw arguments are scanned for the exact token `--plain`, never after a bare `--`. Without it, `clap` and `env_logger` both ask `anstream`, which reads the environment: a non-empty `NO_COLOR` means none, whatever else is set; a non-empty `CLICOLOR_FORCE` forces colour even into a pipe; `CLICOLOR=0` means none; and otherwise colour needs a terminal. Ladderback's own sentences have none to turn off.
  - *`--json`.* A command that reports state prints one document, as compact JSON on one line of standard output, and nothing on standard error. Its keys are kebab-case and its text is codes and arguments, never a sentence (§8.4), so a script reads the same document in every language. `import-profile` is the only such command: `export-profile` prints a profile, `serve` is the daemon and `worker` speaks the worker protocol, so `clap` refuses `--json` on them with 2. An import that saved the profile prints `{"repository": …, "plans": […], "notices": […]}`, with `notices` always there and each notice `{"code": …, "args"?: …}`. Once the command line is understood, every failure is `{"error": {"code": …, "args"?: …, "detail"?: …}}`, the REST API's typed error (`api::ErrorDto`), except one that cannot be a document: the document itself cannot be written.
  - *Statuses,* the same with and without `--json`: 0 when the command did what it was asked, 1 when it refused or could not start, and 2 when the command line was not understood: by `clap`, in its own words before any command runs, leaving standard output empty, or by `serve`, which refuses an `--allowed-host` that no request could match, in the catalog's words (§10.1). The worker is not a command a person runs, and ends with the statuses of §4.1.
  - *Nobody reads.* A pipe has no reader once the program at its other end has ended (`ladderback import-profile nas.toml | head -1`), and `print!` and `eprint!` panic on it (§13.5). Commands print through `output::to_stdout` and `output::to_stderr`, which return the failure, and the binary denies `clippy::print_stdout` and `clippy::print_stderr` so that a later `println!` cannot bring the panic back. A write that fails because nobody reads ends the command, quietly, with 141: 128 and the number of SIGPIPE, the status a shell shows for a program that a closed pipe killed. That covers the import (its words and its document), the export, `clap`'s help, version and usage errors, and the daemon's startup lines. A write that fails for another reason, a full disk say, is said as `cannot write the result: <reason>` on standard error, and the status is 1; `clap`'s own messages are the exception, which say nothing and keep `clap`'s status, as they did when `clap` printed them itself. A standard output that is not open at all is no failure: the runtime reopens it as `/dev/null`, so the command prints into the void and ends as it would have. The worker is left as it was: its standard output is the protocol stream, and it already ends with 74 when that stream breaks (§4.1).

**Tests** (test first, like everything else; §13):

- **Component structure** (roles, names, ARIA attributes, DOM) runs in the browser under `wasm-bindgen-test`.
- **Component behavior** (keyboard, focus return, Escape, accessibility-tree snapshots with `toMatchAriaSnapshot`) runs in Playwright, which sends real input, against a dev-only component gallery route. Synthetic key events in `wasm-bindgen-test` don't trigger native behavior, so they can't test this.
- **Announcer:** throttling, merging, politeness, queueing during dialogs, and "the same text twice, 5 s apart, is announced twice", all with a fake clock.
- **UI journeys** (`@ui` scenarios, §13.2), from M0:
  - axe-core with tags `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa` and `wcag22aa` on every page, in its loading, empty, error and success states;
  - keyboard-only runs through a helper that offers only key presses and role locators; a lint bans pointer actions in journey code;
  - after every Tab, the focused element must have a visible focus indicator, and `elementFromPoint` at its center must be that element or inside it (2.4.7, 2.4.11);
  - runs at 320 × 256, with a 200 % root font size, with the 1.4.12 text-spacing stylesheet injected (failing on clipped text, as in §8.4), and under emulated dark, `forced-colors`, `prefers-contrast: more` and `prefers-reduced-motion`. The clipped-text check leaves out a box that `clip-path: inset(50%)` hides from sight, as the live regions are: no one sees its text, and the region steps check its words.
- **Other surfaces:** a catalog test that every notification message has a plain-text form; the CLI's `@e2e` scenarios (`features/cli/output.feature`): output has no ANSI codes under `NO_COLOR`, under `--plain` or without a TTY, with controls that show forced colour does colour, so the scenarios that expect none can fail; `--json` is one document on one line, for a success and for every failure; the statuses; and a command whose output nobody reads ends with 141. Unit tests cover what no portable scenario can make happen: a write that fails for a reason other than a closed pipe, and an async runtime that does not start.
- **Manual screen-reader pass** in each milestone with UI: the milestone's journeys in Orca and in VoiceOver, including whether progress bars over-announce. Automated checks catch only part of WCAG, so this pass is part of the milestone's definition of done.

### 4.6 MCP server

`ladderback mcp` lets AI agents and scripts drive Ladderback through the [Model Context Protocol](https://modelcontextprotocol.io): newline-delimited JSON-RPC 2.0 over stdio. Stdout carries only protocol messages; logs go to stderr.

**Protocol.** MCP revision `2025-06-18` or later, negotiated in `initialize`. Older revisions are refused, because results rely on `structuredContent` and `outputSchema`, which arrived in that revision. Implemented:

- **Lifecycle:** `initialize`, then `notifications/initialized`, `ping`, and shutdown on stdin EOF.
- **Tools:** `tools/list` and `tools/call`.
- **Progress and cancellation:** progress notifications, sent only when a request carries `_meta.progressToken`; `notifications/cancelled` for a pending call.
- **Errors:** an unknown tool or malformed arguments is JSON-RPC error `-32602`. A failure inside a tool is a result with `isError: true` and the same `{code, args}` payload the API returns (§8.4), never a sentence.
- **Not localized:** tool `title`s and `description`s are fixed English, like API field names (§8.4).

**Placement.** `adapters/mcp` is an inbound adapter beside `http`, with no rule of its own. Its tools call one `Backend` trait defined inside the adapter, with two implementations:

- **In-process:** receives use-case handles from `src/main.rs`.
- **Connect:** an HTTP and WebSocket client that depends only on `api`, never on `adapters/http` (§3.2).

A parity contract suite runs every tool both implementations offer against both, so the two modes can't drift; the proposal tools are connect mode's alone (below).

| Mode | Command | What it drives |
|---|---|---|
| **Connect** | `ladderback mcp --connect [URL] [--token-file PATH]` | A running agent, through `/api/v1` and its events WebSocket, like any other API client. The URL defaults to `http://127.0.0.1:9898` and must be `https` or loopback before a token is sent. The server starts even when the daemon isn't up yet, and connects on the first call. A request whose reply was lost is never resent: the tool reports that the outcome is unknown |
| **Headless** | `ladderback mcp --headless [--config DIR] [--data DIR]` | An in-process agent session wired by the composition root, as `serve` does but without HTTP or the scheduler. It takes the data-dir lock (§9), so a data dir that `serve` has open is refused by that lock and connect mode is the answer. Operations run only while the session lives: on stdin EOF or SIGTERM it cancels its queued operations and stops its workers (SIGTERM, then SIGKILL), so a later `serve` finds no stale queue |
| **Scratch** | `ladderback mcp --scratch` | A headless session in a new mode-0700 temporary directory (`ladderback-scratch-*`) holding config, data and a local repository, seeded with one plan over procedurally generated files. Deleted on exit; stale scratch directories from crashed sessions are swept at the next start. For demos and for agents testing Ladderback itself |

**Tools.** Each maps onto one use case or read-side query. Results are `structuredContent` built from `api` types, declared by each tool's `outputSchema` and mirrored as JSON text. Every `list_*` tool takes `limit` and a cursor, and results have a size cap, so one call can't flood the client's context.

| Tool | Does |
|---|---|
| `status` | Plans, last result and next run per plan, running operations |
| `list_plans`, `list_repositories` | Plans and repositories, with secrets as references only (§10.5) |
| `list_snapshots` | Snapshots, filtered by host, plan, tag, path or time |
| `list_operations`, `get_operation` | History, one operation's status, summary and warnings |
| `operation_log` | One operation's redacted log, paged |
| `run_plan` | Queues a backup now, under the plan's overlap policy, with `trigger = mcp`; returns the operation ID. The plan's existing hooks and secret sources run as they would for any other trigger |
| `wait_operation` | Waits until an operation finishes or a timeout passes, with progress notifications. Cancelling the call stops the wait, not the operation |
| `cancel_operation` | Cancels a queued or running backup started by `run_plan` or a schedule. Maintenance operations can't be cancelled from MCP, so a loop can't keep a repository from being pruned |
| `test_repository` | Tests a configured repository's connection |
| `preview_forget` | The dry run of forget for a repository this agent owns: what would be deleted, per group (§7.3) |
| `preview_import` | Takes a rustic profile's TOML as `content`, never a path, and returns the proposed plans and notices without applying them. `use-profiles` is reported as a notice rather than read from disk, and parse errors are redacted |
| `export_profile` | A plan as a rustic profile (§6.2). Fails with `inline-secret` when the repository's password is stored inline, rather than writing it out |
| `propose_setup` | Submits a proposal: typed configuration changes plus the AI agent's rationale (§16, decision 89). Returns its ID and what the submission checks found. Changes nothing until a person approves it in the web UI. Needs the `propose` scope |
| `check_proposal` | Runs the submission checks on a draft without storing it: parsing and the domain rules only, with no secret resolved, command run or location contacted |
| `dry_run_plan` | Walks a draft plan's sources, within the allowlist, through its source filter: files and bytes it would back up and what each exclude removed, as counts and sizes, never paths. Runs no hook and opens no repository |
| `get_proposal`, `withdraw_proposal` | One proposal's status, the generated summary, and the reasons a person gave for rejecting each change; withdraws a pending one |

There is deliberately no tool that restores, downloads, applies forget or prune, adopts, approves a proposal, edits config or pairs: each needs a human confirmation or could change what commands run (§10.5). They can be added later only with a confirmation that MCP can carry honestly. A proposal is not an edit: the web UI's "Pending changes" page is the confirmation, and with sign-in on, approving there needs a browser session with step-up, never a token; with sign-in off, approval is a convenience, not a safety boundary (decision 89). The proposal tools are offered in connect mode against an agent only, and left out of `tools/list` elsewhere: headless and scratch modes have no web UI to approve in, and plans are view-only from the hub (decision 2).

**Hub.** M3 drives one agent. Connect mode against a hub, with an `agent` argument on the tools that need one (plan IDs are unique per agent only), arrives with remote control in M5.

**Testing.** `features/automation/mcp.feature` runs as `@e2e` scenarios. The runner speaks JSON-RPC to `ladderback mcp --scratch`, and to `ladderback mcp --connect` against `ladderback serve --listen 127.0.0.1:0`, reading the chosen port from the `listening on` line on its stderr. Each tool's input and output schemas are checked against example calls. The I4 canary test (§10.2) scans every tool result, including `list_repositories`, `export_profile` and `preview_import` with inline secrets.
