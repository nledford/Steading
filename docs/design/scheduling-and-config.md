## 5. Scheduling

- **Schedule types:** cron expressions (`croner` syntax) or simple intervals ("every 1 h"), with optional **jitter** to spread load across machines. An interval is real time from the start of the last run, at least 1 minute and at most 366 days (`Interval`); a change of the clocks neither lengthens nor shortens it. A plan scheduled for the first time runs at its first moment after now.
- **Time zone.** Cron runs in the machine's local time by default; a schedule may set `timezone = "UTC"` or an IANA zone. A local time skipped by a DST change runs at the next valid time: the instant the clocks jump to, and every moment in the skipped stretch runs then, once. A repeated hour runs once: each of its wall-clock moments runs the first time round, whatever the expression (decision 60).
- **Jitter.** A run is put up to `jitter` after its moment, as the share of that stretch a number drawn by the `Random` port is of every `u64`, in milliseconds, and always at least a millisecond before the schedule's following moment, so it never takes that moment's place. A catch-up runs without jitter.
- **Catch-up (anacron-style).** `next_run` is stored in the DB. If the machine was asleep or off when a run was due, it runs once at startup or wake instead of being skipped. Several missed runs collapse into one. This matters for laptops. Whether a run was missed is decided from the planned run, not the last one: a planned run at or before the time the agent comes back was missed. Without catch-up, the missed runs are skipped for the first moment after now. A planned run later than any moment after now could put it, as after the clock was set back, is planned again from now. The domain service `NextRun` (`domain::execution::next_run`) answers both questions, the run after one that starts and what becomes of a planned run on startup or wake (decision 60).
- **Wake detection.** A ticker compares wall-clock time against the monotonic clock every 30 s of monotonic time (`WakeWatch` in `app`, the `WakeDetector` rule in `domain`). When wall-clock time ran more than 2 min ahead, the machine slept or the clock was set forward, and all `next_run` values are recomputed (what becomes of each planned run is `NextRun`'s answer, decision 60). A clock set back is no wake: no run was missed. (Backrest's scheduler hung after sleep without this, [#172](https://github.com/garethgeorge/backrest/issues/172).)
- **Network wait.** A catch-up run after a wake first waits, for up to 2 min of monotonic time, until the machine is online (the `Network` port, asked every 5 s; §16, decision 63). The wait ends at once when the platform can't say, and gives up at the bound even if a check hangs; the run then goes ahead either way. Runs fired before the network is up otherwise fail ([Backrest #882](https://github.com/garethgeorge/backrest/issues/882)). Which runs wait (a local repository needs no network) is the scheduler's.
- **Conditions** (optional, per plan): only on AC power, not on a metered connection, and a minimum interval since the last success. They are checked through the platform ports (`PowerSupply`, `Network`; §16, decision 63): `/sys/class/power_supply` on Linux and `pmset -g batt` on macOS. A plan on AC power only is skipped while the machine is on battery: no AC supply online and one of the machine's own batteries, or a UPS, discharging (a peripheral's battery doesn't count). A power source the platform can't report never holds a run back. The metered-connection and interval conditions are not built yet. A repository with several locations adds **location rules** (§6.1; §16, decision 80), which choose where a run goes rather than whether it starts: a scheduled run is skipped, with its reason in the log and no operation, when every location of its repository has a rule and every one is known not to hold, as it is for an unmet condition; a rule the platform can't report doesn't hold either (where a condition it can't report never holds a run back), but it never skips the run: the run starts, tries the next location, and fails `no-location-rule-holds`, recorded and retried, when none is left. The same network wait applies and no other is added: a plan whose usable location is the late one fails and is retried (decision 76). A power condition that isn't met skips the run before the link is read; a power source that can't be reported leaves the rules to decide. The link is read once for the plans due together, and a rule changed while the agent serves holds from the next run.
- **Persistent queue.** Queued jobs, including manual "run now" requests, are `operations` rows with status `queued`. They survive restarts and config reloads ([Backrest #1436](https://github.com/garethgeorge/backrest/issues/1436)). Once a restarted daemon listens, it runs each queued backup of a plan its configuration still has, on the repository it was queued for, oldest first, under the operation's own ID and trigger, with the job built from the configuration of that moment, not the one it was queued under; any other queued operation ends `failed` with `daemon-stopped`, and the daemon's log names it and says why by a code: a maintenance operation, a backup whose plan is gone or now backs up to another repository, and a backup whose job can't be built (its repository is gone, or the configuration can't be read). A backup whose secret is refused, on the repository it was queued for, ends `failed` with the refusal instead, as a refused run does (below). Then the scheduler starts (§16, decision 73).
- **The scheduler.** One loop in `app` (`app::schedule::Scheduler`) keeps each scheduled plan's planned run in `schedule_state` (§9) and sleeps until the first of them, and at most the 30 s of the wake check. Each time it wakes it reads the configuration again: a plan it first finds is planned from the run kept for it before the start, else from now; a plan whose cadence, `timezone` or jitter changed is planned again from now; a plan no longer scheduled is forgotten; a configuration that can't be read changes nothing. A cron schedule is read in its own `timezone`, or in the machine's local zone when it sets none. It checks for a wake before it starts any due run, so what became of each planned run is `NextRun`'s answer however the timers fired (decision 60, point 5). A due run's conditions and its plan's overlap policy (below) are checked as it starts, and its following run is planned from then, whether it started or was skipped; a skip is said in the daemon's log, never queued. The start page lists each plan with its planned run.
- **A refused run.** A run the schedule starts (a scheduled run, a catch-up or a retry) resolves its repository's settings before anything runs. When one can't be resolved (a secret missing or unreadable, a command that fails, a reference in a setting that becomes a process argument; security.md §10.2), nobody is there to be told, so the run is kept as a failed backup of its plan: one write of the operation queued and failed in the same instant, never started and never queued first, with the refusal's own code and arguments as its failure (`FailureReason::SecretRefused`), the same a request to start the run is refused with. Where the secret was looked for and what a platform or a command said are masked of the repository's secrets before they are kept (I4); the daemon's log names the plan, the operation, the code, the setting and where the secret was looked for, as for a refusal by hand (#483), never what was read. No hook runs, the engine is never asked, the run gives up its place in the queue, and its end is told to the scheduler as any failed run's, so the plan's retries follow it (decision 76). A run a person or another program asks for is refused to them instead, and nothing is recorded. Secrets that resolve but are too large to mask are not a refusal: that run fails as `SecretsTooLargeToMask`. A queued backup resumed after a restart is outside this rule: it ends `daemon-stopped` (#490).
- **Retry.** Per plan: `retry = { attempts, backoff }`. A failed backup the schedule started (a scheduled run, a catch-up, or a retry of one, one refused before it ran included) is retried at most `attempts` times, in a place of the persistent queue under the concurrency limit, the first `backoff` after the failure and each after twice the wait before it, capped at 1 h (`RetrySchedule` in `domain::execution::retry`). A backup a person or another program asked for (`manual`, `hub`, `mcp`) is theirs: its failure starts no retries and leaves the plan's own as they were. Retries stop at the plan's next scheduled run, as it was planned when the series began: a retry that would run at or after it isn't planned, and a pending one is dropped when that run comes due, whether it starts, is skipped, or catches up. A success or a cancel of any run of the plan ends them, a retry already started, waiting or running, included: its end plans nothing more. A plan that no longer sets `retry` ends them too, and `attempts` lowered below a pending retry drop it. A due retry is skipped while a run of its plan is going, running or waiting, whatever the plan's overlap policy: that run takes its place. Each run of a backup says how it ended to the scheduler (`app::retry`), which plans the next retry and announces it (`backup.retrying`, §11); a retry planned and not started yet is kept in `retry_state` (§9) until its run is recorded, so it runs after a restart unless its series' end came meanwhile. Retries are separate from hooks (decision 76).
- **Concurrency.** Default 1 running backup per agent, configurable with `[agent] concurrency`. Lock-free means correctness never depends on this; it only limits load. The limit counts backups across all the agent's plans, from a run's before-hooks to its last write, and a plan runs one backup at a time whatever the limit; a backup beyond it waits in the persistent queue, as queued, and the oldest waiting run that may start starts as a slot frees. Maintenance takes no slot: it stays serialized per repository by I7 (§7.3). The queue takes the limit from the configuration each time the scheduler reads it and each time a run started by hand asks for a place, so a raised limit starts the waiting runs it makes room for, and a lowered one stops nothing that runs and holds the waiting ones back (decision 75).
- **Overlap policy.** If a plan's previous run is still going, running or waiting in the queue, when its schedule starts the next: `skip` (default) or `queue`. Under `skip` the due run is skipped; under `queue` it waits for the last one to end, but a plan never has two runs waiting, so a run due while one already waits is skipped too. A skipped run records no operation; the daemon's log says why. The policy applies to the runs a schedule starts (a scheduled run or a catch-up) only: a run started by hand and a run the queue held from before the start always wait their turn, and a retry is skipped while a run of its plan is going, whatever the policy (above; decision 76). A waiting run's job is built when it is queued, from the configuration of that moment, so a change to its plan while it waits doesn't reach it. A cancel ends a waiting run at once, without its hooks (decision 75).
- **Maintenance jobs** (forget/prune/check) are scheduled only on the repo's **granted maintenance owner** and run one at a time per repo (§7.3).

## 6. Configuration

### 6.1 Source of truth

Each agent's plans live in `~/.config/ladderback/config.toml` (Linux) or `~/Library/Application Support/ladderback/config.toml` (macOS). The file is plain TOML so it's easy to review and version. The UI edits it through the API and writes it atomically, keeping the last 10 versions. Runtime state (op log, queue, schedule state, snapshot cache) lives in SQLite. Config does not.

```toml
schema = 1                       # config schema version (see below)

[agent]
hostname = "demo-laptop"         # defaults to system hostname; must be unique on the hub
concurrency = 1
nice = 10
allow-hub-restore = false        # §10.4
locale = "en-US"                 # notification text (§8.4); defaults to the POSIX locale, then en-US

[hub]                            # optional
url = "https://hub.example.lan:9899"

[hooks]                          # = rustic [global.hooks]: wraps every job on this agent
run-before = []

[repositories.nas]
repository = "sftp://backup@nas.lan/backups/rustic"   # passed to rustic_backend
repository-id = "4c6f…"          # written by Ladderback when it connects, creates or first opens the repo; one alias per ID (§7.3)
password-command = "security find-generic-password -s rustic-nas -w"
maintenance = "hub"              # requested owner: "hub" | "local" | "none" (§7.3)
group-by = "host,label,paths"    # only used to group untagged snapshots (§7.3)
options = { }                    # backend options (BTreeMap<String,String>); also options-hot/-cold
hooks = { run-before = [], run-after = [], run-failed = [], run-finally = [] }  # = [repository.hooks]

[[plans]]
id = "home"
repository = "nas"
label = "demo-laptop home"
# host = "..."                   # optional per-plan override of [agent] hostname
sources = ["/home/demo"]
tags = ["demo-laptop", "laptop", "home"]   # ladderback-* tags are added automatically
schedule = { cron = "0 * * * *", timezone = "Europe/Berlin", jitter = "5m", catch-up = true, on-ac-power = false }  # or every = "6h" in place of cron
overlap = "skip"                 # or "queue" (§5)
retry = { attempts = 3, backoff = "10m" }
git-ignore = true
exclude-if-present = [".nobackup", "CACHEDIR.TAG"]
iglobs = ["!.Trash", "!bin", "!node_modules", "!target", "!trash",
          "!/home/demo/Downloads", "!/home/demo/.cache/"]
hooks = { run-before = [], run-after = [], run-failed = [], run-finally = [] }

[plans.retention]                # = rustic_core::KeepOptions
keep-within-hourly = "1 day"
keep-within-daily = "1 week"
keep-within-weekly = "1 months"
keep-within-monthly = "1 year"
keep-within-quarter-yearly = "2 years"
keep-within-half-yearly = "3 years"
keep-within-yearly = "4 years"
```

The maintenance owner's config also holds the repo's maintenance settings. For a hub-managed repo that is the hub's own `config.toml`, together with the hub's secret for the repo (§10.2):

```toml
[repositories.nas.prune]         # Ladderback's own struct, mapped onto rustic_core::PruneOptions
schedule = { cron = "0 3 * * 0" }
keep-delete = "6d"               # minimum 23h; instant-delete is not configurable (I2)
max-unused = "5%"

[repositories.nas.check]
schedule = { cron = "0 4 * * 0" }
read-data-subset = "5%"
```

A repository reached at more than one address lists them in order: `repository` and the settings beside it are the first location, and each `[[repositories.<alias>.locations]]` table is a further one, with its own `repository`, `repo-hot`, `options`, `options-hot`, `options-cold` and an optional `when` rule (§16, decision 80):

```toml
[repositories.nas]
repository = "rest:https://nas.home.arpa:8000/laptop"        # the first location, tried first
options = { http-cacert = "/etc/ladderback/lan-ca.pem" }      # this location's options only

[[repositories.nas.locations]]
repository = "rest:https://backup.example.net/laptop"        # tried when the first isn't eligible or doesn't answer
```

This is the recommended setup for a LAN location that carries credentials (decision 80, point 7): the LAN location first, over HTTPS that verifies without the internet, with no rule, and the public address second. When the home's internet connection is down, only the LAN location can take a backup; away from home its name doesn't resolve, so the run falls through at once; on a network that answers for the name, TLS fails before any credential is sent. A rule (`when = [ { network = "wired" } ]`) can't do that: it reads only the network link, which a network made to look like the intended one passes too. The certificate comes from a public CA through split-horizon DNS (one name that the home's DNS resolves to the LAN server), or from a private CA: a leaf with the name in its Subject Alternative Name, the `serverAuth` extended key usage and at most 825 days of validity (macOS refuses a server certificate without them), signed by a CA certificate that `http-cacert` names, not a bare self-signed certificate (rustls refuses one marked as a CA on Linux). Never `http-insecure-tls`. The home's DNS must keep answering its local names while the internet is down.

Hook entries are either a command string or `{ command, args, on-failure = "error" | "warn" | "ignore" }`, as in rustic. The three hook levels follow rustic exactly (§16, decision 10): agent `[hooks]` and repository `hooks` wrap **every** job, including forget, prune and check; plan `hooks` wrap that plan's backup. Order: agent before, repository before, plan before, operation, then plan, repository, agent after/finally. On failure, `run-failed` then `run-finally`. A hook's program is a name looked up on `PATH` (`notify-send`) or an absolute path; one with a `/` that doesn't start with one (`./notify.sh`, `bin/notify`, `~/bin/notify`: nothing expands `~`) would be found from the daemon's working directory, so `HookEntry` refuses it as `Value(HookProgram)`, which keeps the program and none of its arguments (#240).

**How hooks run** (settled in M1b). The `HookRunner` port runs each entry as a process, without a shell, in a process group of its own, with the worker's scrubbed environment (§4.1 allow-list) plus `LADDERBACK_HOOK`, `LADDERBACK_PLAN`, `LADDERBACK_REPOSITORY`, `LADDERBACK_OPERATION_ID`, `LADDERBACK_SNAPSHOT_ID` (after a successful backup) and `LADDERBACK_ERROR` (the stored failure code, for the failed and finally phases) — never a secret or the repository URL. Each hook may run 5 minutes (a constant until a later milestone makes it configurable); past it, the group gets SIGTERM, then SIGKILL after 5 s if the hook is still running, the way a password command is stopped (security.md §10.2). Each signal goes once and only while the hook is unreaped (a group is named by its leader's process id, which another process may hold once the leader has been reaped and the group has no live member), so a hook that ends on the SIGTERM is not signalled again, and a process it started that ignored the SIGTERM too is left running. While it is stopped, the hook's output pipes stay open and are read and dropped until it is reaped, so a SIGTERM handler can write to them however much it says, and what it says is not part of the captured output. The wait after the SIGKILL is bounded (5 s), so a hook no signal reaches still ends the call as timed out. A hook that ends by itself is reaped when it ends, though a process it started still holds its stdout or stderr open: what is in the pipes at the exit, and what they carry for 1 s after it, is captured, then the runner lets go of them (the second is not counted against the 5 minutes: a hook that ended in time is never timed out), and a process that writes there later gets SIGPIPE (EPIPE where it ignores that), so a hook that starts something long-lived redirects its output (decision 34). Stdout and stderr are captured, capped at 64 KiB per stream with a truncated flag, and redacted against the run's secrets. Every stream is masked as a cut text however it ended, so a secret cut through leaves nothing of itself (security.md §10.2, decision 45): the cap, the timeout, the second after the exit, a failed read, or the hook itself, which can stop partway through a secret and exit on its own, can each end what was read partway through one. The truncated flag still means only the cap. A failing before-hook ends the run as its `on-failure` says: `error` fails the operation before the engine starts (`hook-failed`, with the exit status, or none when it timed out or never started), `warn` attaches the `hook-warning` warning, `ignore` goes on. After, failed and finally hooks never change how a finished operation ended: `error` and `warn` attach the same warning, `ignore` is silent. When a before-hook stopped the run, only the finally-hooks run.

**Parsing.** The `config` adapter parses each TOML table into one flat Ladderback-owned struct with `rename_all = "kebab-case"` and `deny_unknown_fields`, using the same keys rustic profiles use. Because there is no `#[serde(flatten)]`, an unknown key is reported at its own file and line. The adapter then builds domain types (`RetentionPolicy`, `SourceFilter`, …), and the engine adapter maps those onto `rustic_core`'s `KeepOptions`, `Excludes`, `LocalSourceFilterOptions` and `SnapshotOptions` (§3.2, §16 decision 15). A backup job carries its plan's whole `SourceFilter` and snapshot host to the worker, which builds the rustic options there (§4.1), so every filter key the config accepts takes effect.

A **parity test** per mapped `rustic_core` struct lists every upstream field as either mapped or deliberately unsupported, so a pin upgrade that adds a field fails until someone decides. The mechanism depends on the type:

- **serde-derived structs** (`KeepOptions`, `Excludes`, `LocalSourceFilterOptions`, `SnapshotOptions`): the test deserializes through a stub `Deserializer` that records the field list serde passes to `deserialize_struct`, and compares it with the mapped and unsupported lists.
- **Structs without serde** (`PruneOptions`, `CheckOptions`, `RestoreOptions`, `LsOptions`): the test builds each with an exhaustive struct literal, no `..`, so a new field is a compile error. If a struct is `#[non_exhaustive]`, a `cargo public-api` diff on pin bumps replaces the literal.

**Schema versioning.** `schema` is required. The versioned file formats, the migration chain and the parser live in `adapters/config` and are tested with golden files from every past schema version; `domain` keeps only the invariants (unique plan IDs, aliases that exist). Migrations run on load and write the old file to the version history first. The daemon refuses to start on a schema newer than it understands. Backrest needed four config migrations and still broke upgrades ([#389](https://github.com/garethgeorge/backrest/issues/389), [#421](https://github.com/garethgeorge/backrest/issues/421)); this is planned from M1b.

**Domain models and the `ConfigStore` port.** `domain::planning` holds the models. `AgentConfig` is the whole file: `AgentSettings`, the agent-level `Hooks`, a `BTreeMap` of `RepositoryConfig` by `RepositoryAlias`, and the `Plan`s in the order written. Its only constructor, `AgentConfig::new`, checks the rules that reach across parts (a plan ID is unique, a plan's repository exists, a plan has a source) and reports the first plan that breaks one; the default is the empty configuration. Each leaf is a type that cannot hold a wrong value (`Concurrency`, `Nice`, `Hostname`, `Source`, `GlobFile`, `Locale`, `CronExpression`, `Interval`, `ScheduleZone`, `Schedule`, `Overlap`, `RetryPolicy`, `RetentionPolicy` with `KeepCount` and `KeepWithin`, `Hooks`, `Maintenance`, `GroupBy`), and a value out of range is an `InvalidValue` that names its kind. `app::ports::ConfigStore` has `load` and `save` over the whole `AgentConfig`. `ConfigError` says what failed (`Unavailable`, `TooLarge`, `SchemaMissing`, `SchemaNewer`, `Invalid`), in which file and, for `Invalid`, at which key and position. It never carries a secret. A store that was never saved to loads `AgentConfig::default()`. The five `config-*` error codes map one to one onto these variants.

Decisions the models make where this document was silent:

- **Names.** `RetentionPolicy` and `RetryPolicy`, as in architecture.md §3.1.
- **Maintenance defaults to `none`.** A repository that doesn't say is not asking anyone to run forget, prune or check on it; owning that work is something a user grants (§7.3).
- **Cron has five fields.** Seconds and a year are refused, and nicknames such as `@daily` are read. A cron string is capped at 512 bytes. This leaves the other two fields to be allowed later without breaking a valid file. An expression that never fires (`0 0 31 2 *`) is refused; `0 0 29 2 *` fires, once in four years.
- **Durations.** A `jitter` is not negative and at most 366 days. An `every` is at least 1 minute and at most 366 days, written as a jitter is (decision 72). A `backoff` is at least 1 s and at most 1 h, the cap §5 puts on the doubling wait; **retry attempts** are 1 to 100, so that a plan with no schedule, which has no next run to stop its retries, still stops. A `keep-within` is not negative and has no cap: rustic adds it to a snapshot's time with a saturating add.
- **Limits.** `concurrency` is 1 to 64, `nice` 0 to 19. The cap on concurrency is Ladderback's, so that a number from a file can't size a pool of threads. A `keep-*` count is `-1` (all) or 0 up to `i32::MAX`, as in rustic.
- **Schedule defaults.** The machine's local time, no jitter, `catch-up = true`, `on-ac-power = false` (any power source); a plan's `overlap` is `skip`.
- **Time zones and the overlap policy** (decided 2026-11-12, decision 72). A `timezone` is `UTC` or a name in the IANA time zone database, in any case, looked up by the config adapter in the system's copy of the database or the one built in, and written as the database spells it (`europe/berlin` is saved as `Europe/Berlin`); a fixed offset, a POSIX TZ string and `Etc/Unknown` are refused as `Value(TimeZone)`. `domain` reads no database: `ScheduleZone::new` takes the zone the adapter found and keeps its name, refusing a zone that has none. Two zones are equal when their names are. An `every` schedule may name a zone, which plays no part (decision 60). `overlap` is a plan's, `skip` or `queue`, else `Value(Overlap)`. The new keys left the schema at version 1: they are a compatible change (operations.md §12.1), and a bump would rewrite every hand-written file in the daemon's layout.
- **An empty `RetentionPolicy` keeps everything.** `RetentionPolicy::is_empty` is true when no setting is set, and a plan without a policy is never forgotten from.
- **A policy that keeps nothing is refused, per plan with history** (decided 2026-11-09, decision 25). A policy that sets only counts of `0` (`keep-last = 0` and nothing else), or only a zero-length `keep-within` (`"0s"`), is not empty, and keeps nothing: forget would remove every snapshot of the plan. The model accepts it because rustic does, and `0` is a meaningful count beside others. A forget refuses such a policy before anything is selected, with `RetentionKeepsNothing` naming the plan (HTTP 422) — but only for a plan whose group holds snapshots: a plan that has never backed up has nothing a policy could remove. Rustic's own `forget` refuses a policy that sets nothing, so forget must not be asked to run when `is_empty` is true; an empty policy here keeps everything.
- **`RepositoryConfig` carries its backend settings.** `RepositorySettings` (the repository string, `repo-hot`, where the password is, and the three option maps) moved from `app::secrets` into `domain::planning`, with its masked `Debug` and `masked_options`; `app::secrets` imports it. Fields and options keep `${VAR}` and `${file:/path}` references exactly as written, to be resolved when a job starts (§10.2).
- **One alias per repository** (decided 2026-11-11, decision 49). `RepositoryConfig` has an optional `id`, written as `repository-id`, the rustic repository ID read when Ladderback connected or created the repository; a hand-written or imported entry has none until a job opens the repository (below). An entry's location is its `repository` string, `repo-hot` and its three option maps, less its password and the options that hold a credential (`RepositorySettings::same_location`; a credential is what `is_secret_option` says, the predicate the `inline-secret` warnings use), so two buckets of one `opendal:` backend are two locations, and a credential moved from text to `${VAR}`, added or removed leaves one. The exception is a drive, where only a credential names the account: on `opendal:dropbox`, `gdrive`, `onedrive` and `yandex-disk` (opendal's scheme, read without case up to a `:`; the list is `DRIVES` in `domain::planning`), the option sets that reach the drive keep their credentials (`options` and, for the `repository` half, `options-cold`, for the `repo-hot` half, `options-hot`), so two accounts with one `root` are two locations, and there a credential moved from text to `${VAR}` is another location too. Two entries are one repository when both know their ID and the IDs are equal, or, when either knows none, when they are at one location (`RepositoryConfig::is`). `AgentConfig::new` checks the repositories before the plans: two entries that are one repository are `Violation::SameRepository { first, second }` in alias order, reported at the second entry's key with both named. `AgentConfig::alias_of(settings, id)` finds the alias a repository already has, and connect, init and import refuse a second one (§6.2, §7.3). A build older than this one doesn't know the key, so it refuses a file that has it as `UnknownKey`.
- **The ID of a repository a job opened is recorded** (decided 2026-11-11, decision 57). The first job of any kind that opens a saved repository whose entry records no ID has the daemon record the ID it read: each such job carries the entry it was made from (`ResolveRepository::resolve_saved`), the engine names the repository it opened when the job starts, and `app::repositories::RecordOpened`, around the daemon's engine, asks `ConfigStore::record_id`. `AgentConfig::record_id` decides: only while the entry is the one the job read and records no ID, and only when no other entry records that ID (`NotRecorded`). The file store adds the one key to the entry as written (`toml_edit`), keeping the file's line endings and byte order mark, and writes only when the result is the old file with one run of bytes inserted, reads back as the configuration with the ID and nothing else changed, and is no larger than the store reads, the file unchanged since it was read and in the current schema version (`NotInPlace`), keeping the old file in the history first, as a save does. The record holds the daemon's configuration write lock and never waits for it; each outcome is a line in the daemon's log naming the alias and the ID or the reason (I4), and an outcome only a person's edit changes is logged once a run. A job of an entry that records no ID, other than an identify or an initialisation, runs after an identify that records it, with the ID it found, so it has a cache slot and its operation names the repository from its start; an identify that fails ends the job with its reason (decided 2026-11-12, decision 81).
- **Locations** (decided 2026-11-12, decision 80). A repository has one to four locations (`MAX_LOCATIONS`): the entry's own `repository`, `repo-hot`, `options`, `options-hot` and `options-cold`, and each `[[repositories.<alias>.locations]]` table after it, in the order written, with the same five keys and `when`, and no other. The repository's password source, `repository-id`, `maintenance`, `group-by`, `hooks`, `prune` and `check` are the repository's, not a location's, and a location's options never apply to another location, so one server's credential is never sent to another. `when` is a list of at most 8 alternatives, any of which makes the location eligible: `{ network = "wired" }`, `{ network = "wifi" }`, `{ network = "wifi", only = [names] }` or `{ network = "wifi", except = [names] }`, with at most 16 names of at most 32 bytes (`only` with `except`, an empty list, a longer name and an unknown `network` are refused as `Value(LocationRule)` at the key). No `when` is no rule. Every cap and every path rule of this section holds for each location, and what a `${…}` makes of a location is checked when a job resolves it. **The schema stays at version 1**, as for decision 72's keys: a file that doesn't use them reads as before, and one that does is refused by a build that predates them. A repository with more than one location records its ID: the table is refused on an entry with no `repository-id`, so that the first location to answer can't define the repository. Two entries are one repository (decision 49) by their ID when both know one, and otherwise when any location of one is at any location of the other (on a drive, with its credentials); two locations of one entry may not be at one location. Each refusal names its key, a further location by its index from 0: a fifth location is refused at `locations[3]`, further locations on an entry with no `repository-id` as the missing `repository-id` at `locations[0]` (the daemon's refusal says the way out: run a job on the repository once, which records its ID, or write the ID the Repositories page shows), and a location at the place of an earlier one at its own `repository` key. A `when` on a repository of one location is honoured, and its plain-HTTP credentials are warned about as any ruled location's are. Probes, the choice and what it records are §16, decision 80; the plain-HTTP warning is §10.6.
- **`ConfigError::Invalid` is typed.** It is `{ file, key, at, problem, detail }`. `problem` is a `Problem` code, never a sentence (§8.4): `NotUtf8`, `Syntax`, `UnknownKey`, `MissingKey`, `WrongType`, `SchemaNotAVersion`, `SchemaTooOld { found, oldest }`, `Migration`, `Value(ValueKind)`, `Id(IdKind)`, `ReservedTag`, `Password(PasswordProblem)`, `Cadence(CadenceProblem)`, `Violation(Violation)` and `Unwritable`. `key` is the path of the setting (`plans[1].schedule.cron`) and `at` the line and column, counted from 1, of its value, or of the key for an unknown one; a migrated file has no `at`, because its text is not the user's. `detail` holds only what the parser said: `toml::de::Error::message()`, never its `Display`, which prints the source line, with every quoted text cut out, so `password = 123456789` reports `invalid type: integer, expected a string` and nothing of the number. It is empty when `problem` says it all, and a migration step's own words for `Migration`. Hook commands and passwords are never echoed, not even by `Value(HookCommand)`.
- **Every route that reads the file refuses it the same way** (#347). Which routes, and what each answers and shows, is §4.2's "A configuration the daemon can't use". They answer a `ConfigError` through one mapping (`config_unusable` in the composition root; `MaintenanceError::Unavailable` carries the store's report to it, and a secret refusal that reads the file again uses it too): `Invalid` is `config-invalid` with `line` from `at` when there is one and `detail` as `key: detail` (the key alone when the detail is empty); the other variants keep their own `config-*` codes and arguments.
- **The password sources.** A repository has exactly one of `password`, `password-command`, `password-keyring` (`service/name`), `password-file` (an absolute path, read as rustic reads a password file: its first line) and `password-env`. None or several is `Password(Missing | Several)` at the repository; a relative file, a keyring entry without a `/`, a command that can't be split and a command that starts its program by a relative path (`./get-pass`, `bin/get-pass`: `Password(RelativeProgram)`, the rule a hook's program follows) are refused at their own key. A `${file:…}` password, which reads the whole file, has no key of its own: saving one is `Unwritable`.
- **Glob files are absolute paths.** A plan's `glob-files` and `iglob-files` are `GlobFile`s: absolute, at most 4096 bytes, without a NUL, the rule a `Source` follows. rustic reads a glob file from the working directory of the process that runs the backup, which for Ladderback is the daemon's (`/` under launchd or a system unit, the home folder under a user unit), never the folder `config.toml` is in, so a relative one would name a different file, or none, depending on how the daemon was started. It is refused at its own key (`plans[0].glob-files[1]`) as `Value(GlobFile)` (#198). Whether the file exists is for the backup: a missing one fails it.
- **A glob that can never match is said, never rewritten** (#510). rustic builds its globs with gitignore's rules on an empty root (`OverrideBuilder::new("")`) and matches them against the whole path a backup walks, so a glob with a slash in the middle is read from the root of the file system: `!.cache` matches at any depth, while `!.local/share/containers`, written from the source as a profile run from inside its source folder may have it, matches nothing. An exclude glob (with `!`) that matches nothing leaves nothing out, so the folder is backed up with no word; an include glob (without one) that matches nothing leaves out every file no other glob includes. `Plan::never_matching_globs` finds each such glob of `globs` and `iglobs` (with or without its `!`; a slash at the end alone marks a folder, and a glob that starts with `/` or `**/` is read as written) whose path, read from the root, reaches none of the plan's sources as the backup walks them; the rule is conservative, so only a literal part that differs from every source's part at its place counts, and a part with a wildcard or an escape, or the whole path less its first slash (`home/user/.cache`), is never said to match nothing.
  - *The sources as walked.* rustic resolves each source before it walks it (`PathList::sanitize`: dots removed, links followed), so the globs are read against the sources as `NormalizeSources::walked` gives them, each resolved alone by the engine's `RusticSources` through that same call, in the order written. A source that can't be resolved (it isn't there yet) is read as written, its `.`, `..` and repeated `/` read lexically as rustic reads them before it resolves links. The plan keeps its sources as written.
  - *Which source the whole path goes under* (`NeverMatchingGlob::placement`). A glob that names a source from the root as written goes on under that source as walked (`!home/user/.cache` is `!/var/home/user/.cache` where `/home` is a link to `/var/home`). Any other glob is written from a source: the plan's only one, or, of several, the one whose folder on disk holds the glob's folders up to its first wildcard (its `!` left out), which the adapter that resolves the sources tells (`NormalizeSources::holds`: whether the path resolves; existence only). When none or several hold them, no one source is the glob's, and the warning names no path: it says to write the whole path, starting with the folder of the source the glob belongs to. A first-source guess would point at a folder that may not be there: of the sources `/home/user` and `/srv/disk`, `!docker/app/cache` is for `/srv/disk` when only it holds `docker/app/cache`. The whole path is built from folders, the source's as walked then the glob's less any empty or `.` one, and keeps a slash at the end.
  - *Where it is said.* Each is the warning `glob-never-matches`, naming the plan, the glob and, when one source is the glob's, the whole path to write instead (`absolute`, `!/home/user/.local/share/containers`): in the daemon's log when it starts and loads the configuration, on the plan's row of the plans list (components.md §4.2) and from `import-profile` (§6.2), each through `app::globs::never_matching_globs`. The glob is kept as written, so a profile reads the same in rustic and here (§6.2).
  - *The disk is looked at only when it must be.* A plan with no source, or with no glob or iglob read from the root (`Plan::may_have_never_matching_globs`: `!.cache`, `/srv/a/b` and `!**/a/b` are not), is not looked at. The daemon's start and its plans list ask the disk through a `RusticSources` whose every look is given up after 1 s (`SOURCES_LOOK_LIMIT`, in the composition root), as one that can't be resolved: a source on a mount that stopped answering is then read as written and holds nothing, so neither waits on it. A glob that climbs with `..` (`!../shared/x`) gets no whole path (`Placement::Nowhere`): rustic doesn't resolve `..` in a glob, so no path written from the root names what it means. Trailing whitespace, which rustic doesn't read, is no part of the whole path.
  - *Limits.* The contents of `glob-files` and `iglob-files` are not checked: the configuration names those files and never reads them (a missing one fails the backup), so their globs are rustic's to read when the backup starts. An iglob's folders are compared with a source's in lowercase (`char::to_lowercase`), while rustic's matcher folds case by Unicode's simple case folding; the two differ only for a few non-ASCII letters (a final `ς` against `σ`, a dotted `İ`), where the warning can be wrong either way. The disk is asked for an iglob's folders as written, so on a case-sensitive file system a source that holds them in another case doesn't count as holding them.
- **Locations and options have caps** (#236). `repository` and `repo-hot` hold at most 64 KiB as written (`MAX_LOCATION_BYTES`), so does the value of each option (`MAX_OPTION_VALUE_BYTES`), and `options`, `options-hot` and `options-cold` hold at most 64 options each (`MAX_OPTIONS`), all three in `domain::secrets` beside `MAX_SECRET_BYTES`. A job reads a location or an option as a template, which holds at most 64 KiB, so a longer one could never run; and every page and log that shows one masks it first, with a redactor whose needles grow with the size and number of the options (security.md §10.2). A file is refused when it loads: a long location or option value at its own key (`repositories.nas.repo-hot`, `repositories.nas.options.endpoint`) as `Value(Location)` or `Value(OptionValue)`, and a table with one option too many at the table (`repositories.nas.options`) as `Value(Options)`. The refusal quotes nothing (`InvalidValue` with an empty `value`): a location or an option may hold a secret, and a table has no text of its own. An import refuses the same at its key and line (§6.2), and the repository routes refuse settings over a cap as `invalid-body`, before anything is tested or saved (components.md, Repositories API).
- **A repository names paths on this machine by absolute ones.** rustic, the programs it starts and the password command run in the daemon's working directory too, so `RepositorySettings::relative_path` finds the first setting that names a file or folder here by a relative path, and the reader refuses it at its key (`repositories.nas.options-cold.http-cacert`) as `Value(LocalPath)`, or `Password(RelativeProgram)` for the password command (#240). It reads the settings as rustic does:
  - A location is local when it has no `:` or starts `local:`, and must then start with `/`; `backups/repo`, `local:repo`, `~/repo` and the empty location are relative. After `rclone:`, rclone reads a path with no `remote:` before its first `/` or `\` as a folder here, so `rclone:backups/repo` and `rclone:repo` are relative and `rclone:nas:repo` and `rclone:/srv/repo` are not; an on-the-fly backend (`rclone::sftp,host=…:path`) reaches a remote, except `local`, whose path is a folder here (`rclone::local:backups` is relative). `rest:` and `opendal:` locations are not paths, and a scheme rustic doesn't know (`nas:…`, `LOCAL:…`) is rustic's to refuse. OpenDAL's service is the text up to the next `:`, as rustic reads it (`opendal:fs:demo` is `fs`).
  - An option counts only for a backend that reads it, and for each half that reads it: the cold half (`repository`) reads `options` and `options-cold`, the hot half (`repo-hot`) `options` and `options-hot`, and a half's own option replaces the shared one. The files: `http-cacert` and `http-tls-client-cert` (rest, rclone, OpenDAL; the names exact, as rustic matches them); OpenDAL's `root` and `atomic_write_dir` (`fs`, and `file`, its other name), `key` (`sftp`), `credential_path` or `google_application_credentials` (`gcs`) and `oidc_token_file` (`oss`), the service and the name in any case. An `sftp` key may start with `~` (`~/.ssh/id_ed25519`): OpenDAL hands it to `ssh -i`, which expands it to a home folder itself. The commands, whose program follows a hook's rule: `rclone-command` (rclone), whose flags follow the rules for rclone below, and `post-create-command` and `post-delete-command` (local). A command that can't be split is left to rustic.
  - rclone reads more from this machine than its path, and each is judged as rclone 1.76 documents it (`local_paths::rclone`, #249): the flags of an `rclone-command` (`--NAME VALUE` or `--NAME=VALUE`; a `--` ends nothing, as pflag gives it to a flag before it that takes a value), the settings of a connection string (`remote,NAME=VALUE:path`, a value in `'` or `"` with the quote written twice inside), and a location written in a setting, four levels deep as a redactor reads one for credentials (`MAX_RCLONE_DEPTH`), a fifth found as relative. A file must be absolute: the global flags `--config`, `--log-file`, `--ca-cert`, `--client-cert`, `--client-key`, `--cache-dir`, `--temp-dir`, `--cpuprofile`, `--memprofile`, `--rc-files`, the `--rc-` and `--metrics-` servers' `cert`, `key`, `client-ca`, `htpasswd` and `template`, and `rclone serve restic`'s `--cert`, `--key`, `--client-ca` and `--htpasswd`; the lists of the `-from` flags (`--exclude-from`, `--files-from0`, …), unless `-` (standard input); a socket an `--addr` names as `unix://path`. A program, the first word of the value as rclone splits a space-separated list (a record of comma-separated values with a space for the comma; a list rclone refuses runs nothing), follows a hook's rule: `--password-command`, `--metadata-mapper`, `--sftp-ssh`, `--webdav-bearer-token-command`; the program's own arguments are not read, as a hook's aren't. A location (`--alias-remote` and the other wrapping backends' `remote`, `--backup-dir`, `--compare-dest`, `--copy-dest`, each of `--union-upstreams` without its `:ro`, `:nc` or `:writeback`, each of `--combine-upstreams` after its `dir=`) follows the rules for an rclone location. The backends' files: azureblob's and azurefiles' `client_certificate_path` and `service_principal_file`, cache's `chunk_path`, `db_path` and `tmp_upload_path`, oos's `sse_customer_key_file`, s3's `shared_credentials_file`, smb's `kerberos_ccache` (after a `FILE:` or `DIR:`) and webdav's `unix_socket`; and, where rclone expands a leading `~` or variable itself, which may then start the value, box's `box_config_file`, drive's and gcs's `service_account_file`, oos's `config_file` and sftp's `key_file`, `pubkey_file` and `known_hosts_file`. In a connection string a backend's option is written by its name (`key_file`) and a global flag as `override.NAME` or `global.NAME` (`override.ca_cert`). rclone reads a remote's `type` from its settings before its configuration file (the last `type` when there are two), so `rclone:nas,type=local:backups` is a folder here and relative. A remote of rclone's configuration file whose settings don't say its type may be of any backend, so its setting is read as each backend with an option of that name would read it, and its path, which a remote that file makes `type = local` serves from here, can't be judged. Nor is what reaches rclone other than through its flags and its location: its `RCLONE_*` variables (a worker's environment holds none of the daemon's but `RCLONE_CONFIG`, security.md §10.2) and its configuration file itself.
  - A `${…}` is resolved only when a job starts, so a field is judged by the text before its first reference: `backups/${NAME}` is relative, while `${REPO}`, `${HOME}/repo`, `local:${REPO}`, `rclone:nas${NAME}` and `opendal:${SERVICE}` say nothing yet of the path, and a command with a reference is not split. A scheme before the reference still says the backend: `local:${REPO}` runs its `post-create-command`. What a reference makes of `repository` and `repo-hot` is checked when a job resolves them, by the rules for a location above, and a relative one is refused as `repository-path-relative` naming the setting, never what the reference held (security.md §10.2, #247). The options are checked by nothing more at job start: neither what a reference holds in one, nor a plain one whose backend only a reference in the location names (`${REPO}` resolving to `opendal:fs` beside `root = "backups"`), #310.
  - The repository routes (connect, test, create) refuse such settings, and a relative password file, with `repository-path-relative` (422), whose `field` names the setting as this file does (`repository`, `repo-hot`, `password`, `options-cold.http-cacert`), so the page shows it at its field; a saved one would stop the daemon from starting again.
  - A value both over its cap (above) and relative is refused for its length, the same at load, at import and on the routes: the caps are checked as a repository's table (or the profile) is read, and the relative paths once its settings are whole (`Value(Location)` or `Value(OptionValue)` at load, `BadValue` at import, `invalid-body` on the routes). Two different settings are refused in the order each reader reads them.
- **Load order.** The syntax; then `schema` alone, so that a file in a newer version is refused for that before anything else in it is read (`SchemaNewer`), a file with none is `SchemaMissing` even if the rest is wrong, and one older than the oldest the build migrates is `SchemaTooOld`; then the migration steps after the file's version, run on a `toml::Table`; then the strict tables, then the domain's types, then `AgentConfig::new`. The first unknown key reported is the first in the file, not the first by name. A file is read up to its cap (1 MiB) plus one byte, so a file that never ends is `TooLarge`; so is a save that would write more.
- **A table needs what it needs.** A plan has `id`, `repository` and `sources`; a repository has `repository`; a `schedule` has exactly one of `cron` and `every` (neither or both is `Cadence(Missing | Several)`, at the schedule table, decision 72); a `retry` has both `attempts` and `backoff` (neither has a default); a table hook has `command`. A missing one is `MissingKey`, at the table that lacks it.
- **Layout of the written file.** `schema` first, then `[agent]`, `[hooks]`, a table for each repository (in alias order) and each plan (in file order) with its `[plans.retention]`. Whatever is at its default isn't written: no `maintenance = "none"`, no default `group-by`, no empty hooks, no `catch-up = true`, no `overlap = "skip"`. A plan's `overlap` follows its `schedule` (an edit adds it after the plan's last setting instead, below). Small values (schedule, retry, options, hooks) are inline tables. A hook is its command line as `shell_words` joins it, unless its `on-failure` isn't `error`, and then a table. This is the whole text of a first save, of a migrated file and of a save the edit below can't make. The text is the same for the same configuration. The layout is written by the adapter because `toml`'s serializer moves a list holding tables behind the other keys of its table.
- **A save edits the file a person wrote** (decided 2026-11-12, decision 69). A save over an existing file sets, adds and removes only what it changes, where the file writes it, and keeps the rest byte for byte, comments, blank lines, key order and a value's own spelling among them: the file's configuration and the saved one are each written in the layout above, and each setting whose text differs between the two is changed in the file (`edit::saved`, with `toml_edit`). A plan is found by its ID; a repository, plan or setting removed goes with what is written in it and the comment directly above it, up to the nearest blank line, and what is above that blank line stays; a setting or table added follows the last of its kind, and a section the file didn't have goes at its end; a hook list written as `[[hooks.…]]` tables is written again whole when it changes. A repository's `[[repositories.<alias>.locations]]` tables are matched by their position, since their order is what they mean: a location kept is changed where it is written, so what a person wrote in it stays, one added follows the last, and one removed goes with what is written in it. The edit is written only when it reads back as the configuration saved and fits under the cap; otherwise, and for a file that isn't valid UTF-8 or a configuration, is in an older version or whose lines end both ways, the save writes the layout above, as before.
- **History.** A load that migrates, and every save over an existing file, first keeps the file as it was (even one nobody could read) in `history/` next to it, named `<number>-<UTC YYYYMMDDTHHMMSS.mmm>Z.toml`: a six-digit number counting up from the highest in the folder, then the time of the replacing write, which is only for a person reading the names. The number is the order: the 10 highest are kept, so a clock set back (by a person, or by NTP) never makes a save drop the newest versions. A file in `history/` whose name isn't `<number>-<stamp>.toml` is not a version: it is not counted and never forgotten. Files are 0600 and folders 0700. If the old version can't be kept, nothing is replaced: the load or save fails with `Unavailable`. A save over a file longer than the cap is `TooLarge`, because it can't be kept. A version is flushed to disk, and so is the `history/` folder (and the config folder, in which it may be new), before the file is replaced; a failure to flush is a failure to keep: the version just written is removed again, nothing is replaced, and the load or save is `Unavailable`, so a file system that refuses to flush a folder can't save. A failure to remove an old version doesn't fail the save. The replacement is atomic (a temporary file in the same folder, flushed, then renamed), and one lock serialises every load and save of a store. **A symlinked `config.toml`** (a dotfile manager's) stays a link: a save follows the link, through any chain of them, to the file at its end, which may not exist yet, and replaces that file atomically in its own folder; a chain longer than 40 links, or a loop, is `Unavailable` and changes nothing. The new file is a new inode: its mode is 0600 whatever the target's was, and its owner, ACLs and hard links aren't carried over. When it is the folder that is the link (`~/.config/ladderback` leading into a repository), `config.toml` isn't a link, and `history/` is in the folder the link leads to. The history stays in the folder of the link, `history/` next to `config.toml`, not next to the target: the target's folder is typically a repository that gets committed and pushed, and the history may hold a password the config does (decision 29).
- **A migrated file is written as the current version.** `schema = <current>` and the canonical text, byte for byte what `render` gives for it, so a second load changes nothing. A file in the current version is never rewritten by a load, so a hand-written file keeps its comments and layout: a save edits in only what it changes (decision 69), and recording an opened repository's ID adds one key to it and keeps the rest (decision 57).

**Built (C2).** The `config` adapter (`crates/adapters/config`, package `config-adapter`, as a registry crate `config` exists): `FileConfigStore` over the file with the contract suite of `ConfigStore`, the strict tables and the parity tests of the four `rustic_core` structs they map onto (and a test that the lists of mapped keys are the keys the tables take), the schema migrations on a `toml::Table` with golden files (`tests/golden/v1.toml`), the atomic write, the history and the size cap. `[hub]` is an unknown key until M4.

**Not yet.** The adapter is not wired into `main.rs`, so "the daemon refuses to start on a newer schema" holds for the adapter, not yet for the daemon. The repositories' `[prune]` and `[check]` tables are not read (§7.3, item 7), and there is no metered key (M2). Seeding the daemon-wide redactor from the config (security.md §10.2) waits for its consumer. The warning for an inline secret is built: the daemon logs it when it loads the config at start, and the repository list carries it (§16, decision 37). A golden file exists for version 1 only; the first `schema = 2` brings the second.

### 6.2 Importing rustic profiles

`ladderback import-profile <file.toml> [--repo-name nas]` reads a rustic profile and adds a repository and its plans to the configuration, in one save. Profiles named by `use-profiles` are resolved the way rustic does: the platform config dir (`~/.config/rustic` on Linux, `~/Library/Application Support/rustic` on macOS), then `/etc/rustic`, then the current directory; a file's own values beat the profiles it uses. The importer reads those files and nothing else: it never opens the repository, runs a hook or reads a password file. The UI's "Import…" dialog and the MCP `preview_import` tool (§4.6) will use the same port. Mapping for your current laptop profile:

| rustic profile | Ladderback |
|---|---|
| `[repository] repository / repo-hot / password* / key* / options / options-hot / options-cold` | `[repositories.<name>]` (secrets per §10.2); the profile's one repository is the entry's first location, with its `repo-hot` and options, and no rule and no further location are made (§16, decision 80). `<name>` is `--repo-name`, else the file name without its extension, as a slug |
| `[backup] host`, per-snapshot `host` | Per-plan `host`. If every snapshot entry agrees (and the configuration has no plans and the agent no hostname), `[agent] hostname` instead |
| `[backup] git-ignore`, `exclude-if-present`, `globs`, `iglobs`, `tags`, … (section defaults) | Each plan gets the **effective** value: the snapshot entry's own value if set, otherwise the `[backup]` value. For list fields a non-empty snapshot list **replaces** the default list; lists are never concatenated. This matches rustic |
| `[[backup.snapshots]] name / sources / label / tags / iglobs / options` | One `[[plans]]` each. `id` is a slug of `name`, else of the label, else of the last folder of the first source (below) |
| `[backup] group-by` | Not imported: it only picks the backup's parent, and Ladderback picks parents by plan tag (§7.3). Notice shown |
| `[forget] keep-*` / `keep-within-*` | `[plans.retention]` on every plan from this profile |
| `[forget] prune = true` | Not copied into plans. It decides the repo's requested `maintenance` (§7.3). The importer warns: *"Pruning will run from one place (hub or this agent), not after every forget."* |
| `[global] group-by` / `[forget] group-by` | Repo `group-by`, used only to group untagged snapshots for adoption (§7.3) |
| `[global.hooks]` | Agent `[hooks]` |
| `[repository.hooks]` | Repository `hooks` |
| `[backup.hooks]`, `[backup.snapshots.hooks]` | Plan `hooks`. `run-before`: backup-level entries, then the snapshot entry's. `run-after`, `run-failed`, `run-finally`: the snapshot entry's, then backup-level, matching rustic's order. Each plan is its own job, so backup-level hooks run once per plan rather than once per `rustic backup` call; the importer says so |
| `[global.env]` | Not imported; notice shown. Use `password-env` or `${VAR}` (§10.2) |
| `[copy]`, `[webdav]`, `[mount]`, `[init]`, `[snapshot-filter]`, `prometheus*`, `opentelemetry`, `log-*` | Ignored, with a notice. A `[snapshot-filter]` beside retention is refused instead (below) |

**What an import refuses.** A profile is input nobody vetted (§13.5), and what Ladderback can't carry over faithfully, or could only guess at, is refused rather than dropped, so nothing is imported and nothing is written:

- A key rustic doesn't know in the top level, `[global]`, `[backup]`, a snapshot entry, `[forget]`, `[snapshot-filter]` or `[global.hooks]`, which rustic 0.11.4 refuses too. The refusal names the key's path (`forget.keep-lots`) and its line. `[repository]` is the one table rustic reads leniently, and an unknown key there is a notice. A file that isn't TOML, isn't UTF-8, or can't be read is refused naming the file.
- Sizes and depth: a file over 1 MiB, more than 1000 snapshot entries, `use-profiles` nested deeper than 8 levels, more than 32 profiles in one import, a `use-profiles` list of more than 32 names (whether or not a file exists for them), and a profile that uses itself (a cycle is found by the canonical path). A name in `use-profiles` is a plain file name, never a path: `/`, `\`, `..` and a NUL byte are refused, so a profile can't reach a file outside the folders listed above.
- Amplification: the lists and hooks of `[backup]` are copied into every plan, so the plans of one import may hold 100 000 items in all (sources, globs, tags and hooks; a list of `[backup]` counts once per entry). Above that the profile is refused, at the key `backup`, before any plan is made. More than 200 different keys left out are refused too, at the 201st, so a `[repository]` that is read leniently can't be made to hold a list nobody reads.
- A location or an option value of more than 64 KiB as written, and a table of options with more than 64, refused as the configuration refuses them (§6.1), at the key and its line (`repository.repo-hot`, `repository.options.<name>`, `repository.options`). The profiles a profile uses and rustic's `RUSTIC_REPO_OPT_*` variables may add options to a table, so once they are merged the table is counted again, and one over the cap is refused at its key with no line, as no one line wrote it. A value that is more than 64 KiB once its `${` are escaped (below) is refused at its key too (`repository.repository`, `repository.repo-hot`, `repository.options.<name>`): the configuration would read it as a template and refuse it on its next load.
- A relative source or `-`, a relative `glob-files` or `iglob-files` path (rustic reads it from the folder it was started in, which a profile doesn't record; the profile's own folder would be a guess rustic doesn't make, so it is refused at its index rather than resolved), a `[backup]` that names `name` or `sources` (rustic refuses them at backup time), nested snapshot entries, `stdin-command`, a relative `password-file`, no repository, and no password source at all (Ladderback can't prompt for one).
- For the same reason, a setting that names a path on this machine by a relative one, by the rules of §6.1 (#240): a local location (`repository.repository`, `repository.repo-hot`), an option that names a file or runs a program, a hook's program (at `global.hooks.run-before[0]`, or `….command` in a table) and the program of the `password-command` that rustic would use (the profile's own, or `RUSTIC_PASSWORD_COMMAND`; one a `password` or `password-file` beats is never run, and is only a key ignored). A `${…}` the profile writes is text, so `${HOME}/repo` is relative here. Whether an option is a path depends on the location, which a used profile may set, so the refusal names the key and the line in the file that writes the option, after the profiles are merged.
- `[forget] keep-tags` and `keep-ids`: dropping them would let Ladderback's forget remove what rustic keeps.
- A non-empty `[snapshot-filter]` beside any retention, the profile's own or one it uses: rustic's forget then reaches only the snapshots the filter selects, and the same retention on a plan reaches all the plan's own, so it would remove what rustic keeps. The refusal names the first key of the filter (`snapshot-filter.filter-tags`) in the file that has it. Without retention the filter is only a notice. The one filter that is never refused is the one an export writes (a single `filter-tags` entry of a plan tag and an agent tag, below): it selects what the plan's forget reaches anyway, so an exported profile imports back.
- `[global] profile-substitute-env = true`: rustic would then read `${VAR}` in the profiles it uses as a variable, and the importer keeps that text as text (below). Turned off it is a key left out.
- Two plans that get one ID, or an ID the configuration already has; a repository alias the configuration already has for another location (another bucket of one backend included: the options other than credentials are part of the location, and on a drive its credentials too, §6.1); and the profile's repository under a new alias when the configuration already has an entry at the same location, whatever the credentials of either (on a drive, only with the same ones) (`repository-already-configured`, naming that alias: a repository has one alias, §7.3). A profile knows no repository ID, so its location is all that is compared. The alias is checked first, as in connect.

An import under the alias that already holds the profile's repository, at the same location, adds the plans to that entry and keeps the entry as it is: its settings, hooks, ID and maintenance. Each of the entry's settings the profile sets otherwise is named in a `profile-setting-kept` notice (`password`, `maintenance`, `group-by`, `options`, `options-hot`, `options-cold` or `hooks`; an option set can differ only in its credentials), and nothing is refused or merged. The profile's repository is not written, so no secret it holds as text, its password or a credential option, is said kept as text (`inline-secret`); and when the maintenance differs, the notice that it became local goes too, since the entry's did not. The entry the alias names is looked at first, since one location may hold two entries whose IDs differ (§6.1).

**Names and values.**

- A plan's ID is a slug: ASCII letters in lower case and digits, any other run a single `-`, trimmed, at most 64 bytes. It comes from the entry's `name`, else its `label`, else the last folder of its first source, else `plan`. A clash is refused, never numbered `-2`, because the person is the one who knows which plan is which (decision 27).
- The hostname rule: when every imported plan names one host, and the configuration has no plans and the agent no hostname, that host becomes `[agent] hostname` and the plans name none. When the agent already has that hostname, the plans that name it drop it. Any other host stays on its plan.
- `[global.hooks]` are appended after the agent's own hooks, so an import never replaces them.
- A tag written `a,b` is two tags, as rustic reads it. A tag of Ladderback's own (`ladderback-*`) is dropped with a notice, so that an exported profile imports back as the same plan.
- A glob with a slash in the middle that can never match (§6.1, #510) is kept as written, with the warning `glob-never-matches` naming the plan, the glob and the whole path to write instead, or, when no one of the plan's sources holds the glob's folders, saying to write the whole path from the source it belongs to.
- A password written in the profile (`password`, or a credential option such as `secret_access_key`) is kept as written, as the profile has it, with the warning `inline-secret` naming the field, never its value. `password-file` and `password-command` are kept as they are. `key`, `key-file` and `key-command` are noted, and refused when no other password source remains. The priority is rustic's: `key`, `key-file`, `key-command`, `password`, `password-file`, `password-command`.
- A password in a location the profile wrote (`repository` or `repo-hot` as `rest:https://user:password@host/repo`, or a credential in an rclone connection string) is kept as written too, with the warning `location-secret` naming the key (`repository.repository`), never the location or the password; the warning says to put a `${VAR}` or `${file:/path}` reference where the password is, or to give it in the backend's own option, and for an rclone location to set the remote up in rclone's own configuration file instead. An option whose value is a URL with a password in it gets `inline-secret`, as a credential option does (decision 37).
- `RUSTIC_PASSWORD`, `RUSTIC_PASSWORD_FILE`, `RUSTIC_PASSWORD_COMMAND`, `RUSTIC_REPOSITORY` and `RUSTIC_REPO_OPT_*` (§10.2) only fill what the profile leaves out, and they are kept as references (`password-env = "RUSTIC_PASSWORD"`, `repository = "${RUSTIC_REPOSITORY}"`), never as their values. A profile's own setting wins. The command reads the process's environment in one place, and no other code does.
- Every `${` in `repository`, `repo-hot` and the option values a profile wrote becomes `$${`, so the configuration reads it as text. Without it a hostile profile could write `${file:/etc/shadow}` into a repository string and have the daemon read the file at the next job (§10.2). Only the references the importer makes itself, from the environment above, are left as `${…}`.
- The notices go to standard error, one warning each, and a summary of what was added to standard output. A refusal exits with 1. With `--json` there is one document on standard output and nothing on standard error: the notices are its `notices`, as codes and arguments, and a refusal is its `error` (§4.5).

**Export.** `ladderback export-profile --plan home` writes the profile of one plan that the stock `rustic` CLI accepts, on standard output (the notices go to standard error, and a refusal writes nothing and exits with 1):

- Only keys rustic knows. rustic's config structs use `deny_unknown_fields`, so Ladderback-only keys (`schedule`, `retry`, `maintenance`, conditions) are dropped.
- The profile has one `[[backup.snapshots]]` entry. Its `name` is the plan's ID, so the profile imports back as the same plan even when it has a label. Its `host` is the plan's, else the agent's hostname. The tables come in a fixed order, a table with nothing in it is left out, and the same plan gives the same text every time.
- Retention goes into `[forget]` with `group-by = ""`, scoped with `[snapshot-filter] filter-tags = ["ladderback-plan:home,ladderback-agent:<id>"]`. The empty `group-by` puts every snapshot the filter selects into one group, as Ladderback's tag grouping does; with rustic's default grouping, history from before a change of sources or label would be split off and kept. The two tags must be one comma-joined entry: separate list entries are OR-ed, which would also match other agents' `home` plans. Without a filter, `rustic forget` applies the policy to **every** group in the repo. `[forget] filter-*` keys are never used: rustic 0.11.4 accepts them but ignores them. (All three behaviours checked with rustic 0.11.4.)
- A plan with no retention keeps everything. Its profile is still written, with no `keep-*` key, and the export says that rustic's `forget` refuses to run on it until one is set (rustic 0.11.4: "specify at least one keep-* option"). That is safe, because nothing is removed, but it differs from Ladderback, which never forgets from such a plan.
- The plan's `ladderback-plan` and `ladderback-agent` tags are added to the exported `tags`, so CLI backups made after leaving Ladderback are still selected by the filter. A plan tag with a comma in it fails the export, naming the tag: rustic would read it as two tags, and the filter and the person's own tags would no longer mean what they did.
- A repository with more than one location exports its first one, as `repository` with its options, and says so with a notice (`profile-locations-not-exported`, with the number left out): rustic has no fallback, and the profile points only at that address. `when` is a Ladderback-only key and is dropped (§16, decision 80).
- `prune` is not set in `[forget]`: a forget that prunes would run outside Ladderback's own maintenance (I1).
- Secrets are written as `password-command` or `password-file`, never as text (I4). A keyring source becomes a `password-command` for the platform's keyring CLI (`security find-generic-password -s <service> -a <name> -w` on macOS, `secret-tool lookup service <service> username <name>` elsewhere); an env source becomes `password-command = "printenv NAME"`. A password written in the configuration fails the export with `inline-secret`. When no folder of the `PATH` the export runs under holds that keyring CLI, the export still writes the profile and warns with `profile-keyring-command-missing`, naming the program and, for `secret-tool`, its package (`libsecret` on Fedora, `libsecret-tools` on Debian and Ubuntu; #259): the profile may run on another machine, and a refusal is kept for what would write a secret. An unset `PATH` is searched as `execvp` searches it (`/usr/bin`, `/bin`), and an empty or relative entry is skipped: it names a folder by the one rustic will run in, which the export can't know.
- An `options` value containing `${…}`, and an option whose name holds a credential (`is_secret_option`, whatever its value), is left out of the profile, and the export prints the environment variable to set instead: `RUSTIC_REPO_OPT_<KEY>` for a name without `_`, `OPENDAL_<KEY>` for a snake_case name, with the `HOT` and `COLD` forms for `options-hot` and `options-cold`. An option whose name no variable could carry (upper case, spaces, both `-` and `_`) fails the export, naming the key. An option whose value is an address with a user or a password in it is left out the same way, whether it has a scheme or not: `endpoint = "https://user:secret@host"`, a proxy written `user:secret@host:3128`, and a token used as the user name (`token@host`) are all credentials. (A value with an `@` in a path or an e-mail address is left out too: that is the safe side of the guess.)
- A `repository` or `repo-hot` containing `${…}` fails the export with an error naming the key, and so does one that holds a password in its URL (`rest:https://user:secret@host/path`): the profile would have to repeat the password as text. The error names the key and never the value. A user name without a password is written: it is part of the address, and where it is a token, the config holds it as text already. An `rclone:` connection string (`rclone::s3,provider=AWS,secret_access_key=…:bucket`) is refused the same way when one of its `key=value` pieces, split at `,` and `:`, has a key that names a credential in a connection string (`is_rclone_secret_option`, the list the redactor reads: rclone's `pass`, and `key`, are found too); the value is never shown. That split reads the path and the inside of quotes as pieces too, so it refuses more than the redactor masks, never less.
- Hooks are placed back into `[global.hooks]`, `[repository.hooks]` and `[backup.snapshots.hooks]`. With one plan per profile, putting the plan's combined hooks at snapshot level runs them in the same order. A hook is its command line as a shell would split it, as a string when its `on-failure` is `error` and as a table when it isn't.

**Tests.** `features/interop/import.feature` and `export.feature` hold the scenarios; the use cases run against fakes, and the `@e2e` scenarios run the real command on real files, the reader and the writer each with a contract suite of their own port (`contract::profiles`). Parity tests pin the key lists of the reader to the structs of the pinned `rustic_core` (§6.1). Two golden checks use the stock `rustic` and skip, with `testkit::skip!`, where it isn't installed: `rustic -P <exported> show-config` reads a profile that sets every key the writer knows, and on a scratch repo `rustic -P <exported> forget --dry-run --json` removes exactly the snapshot IDs that Ladderback's own forget removes.
